Section 01

What Is Oracle RAC?

Architecture, components, and the "one database, many instances" mental model — explained simply.

High Availability

If one node fails, other nodes continue serving the database instantly. No single compute point of failure. Node VIPs fail over in seconds so clients get fast "connection refused" instead of TCP timeouts.

Horizontal Scalability

Add nodes to increase throughput without replacing hardware. Each new node adds its own SGA and processing power to the cluster. Workloads distribute across all active instances via SCAN load balancing.

Workload Distribution

Separate OLTP, reporting, and batch workloads onto different instances using services. Each service routes to preferred/available instances, keeping workloads isolated while sharing the same data.

Oracle RAC Architecture — The Big Picture

Oracle Grid Infrastructure Stack

Grid Infrastructure = Oracle Clusterware + Oracle ASM. It runs two stacked layers of daemons, each managed by a parent daemon.

Lower Stack Managed by OHASD

OHASD (Oracle High Availability Services Daemon) starts first at OS boot and manages the lower layer.

OHASD

Oracle HA Services Daemon

Root of the stack. Started by OS init/systemd on every boot. Manages all lower-stack daemons.

CSSD

Cluster Synchronization Services

The heartbeat engine. Sends network heartbeats every second; writes disk heartbeats to voting disks. Detects node failures and triggers eviction after misscount seconds (default 30s).

GPNPD

Grid Plug & Play Profile Daemon

Provides the GPNP profile (XML): ASM diskstring, private/public network names, voting disk location. Read before ASM starts.

CTSSD

Cluster Time Sync Services

OBSERVER mode if NTP is present; ACTIVE mode if NTP is absent. Keeps cluster-wide time in sync.

GIPCD

Grid IPC Daemon

Communications infrastructure for all inter-node daemon messaging within the cluster.

Upper Stack Managed by CRSD

CRSD (Cluster Ready Services Daemon) starts after ASM and manages all Oracle database resources.

CRSD

Cluster Ready Services Daemon

The resource manager. Starts, stops, monitors, and fails over ALL Oracle resources: DB instances, ASM, listeners, services, VIPs. Reads/writes OCR for resource configuration.

EVMD

Event Manager Daemon

Publishes FAN (Fast Application Notification) events to ONS. Applications learn about instance UP/DOWN events in real time.

MDNSD

Multicast DNS Daemon

Assists GNS (Grid Naming Service) for dynamic cluster name resolution without external DNS.

Startup Sequence (simplified)

OS init OHASD GPNPD CSSD ASM CRSD DB Instances

OCR — Oracle Cluster Registry

The cluster's configuration database

OCR is the shared configuration store for the entire cluster. Stored inside ASM (recommended) or on a shared raw device.

What it stores: node membership, resource configs (DBs, instances, services, VIPs, listeners), ASM disk group info, SCAN VIP details, resource dependencies and start/stop policies.

Voting Disks — The Tie-Breaker

Split-brain prevention via quorum

Each node writes a heartbeat block to voting disks every second. In a split-brain scenario (nodes can't talk to each other), the sub-cluster that can write to the majority of voting disks survives. The minority self-evicts.

Section 02

Cache Fusion — Deep Dive

How Oracle transfers blocks between instances at memory speed — the technology that makes RAC work.

The Problem Cache Fusion Solves

Before Cache Fusion (pre-Oracle 8i): If Instance 2 needed a block that Instance 1 had modified, Instance 1 had to flush the block to disk. Instance 2 then read it from disk. This "ping" was painfully slow — it happened at disk I/O speed (~10ms per ping).

With Cache Fusion (Oracle 8i+): Blocks are shipped directly between buffer caches over the private interconnect. No disk I/O. Block transfers happen at network speed (~0.2ms). The combined buffer cache of all instances acts as a virtual "global buffer cache."

Key Cache Fusion Processes

LMS (0-9)Lock Manager Server — ships blocks between buffer caches; manages PCM locks; the primary Cache Fusion workhorse. Up to 10 LMS processes.
LMONGlobal Enqueue Monitor — manages GES; detects node failures; orchestrates GRD reconfigurations and dynamic remastering.
LMDGlobal Enqueue Daemon — services remote lock requests; handles distributed deadlock detection.
ACMSAtomic Controlfile Memory Service — ensures distributed SGA memory updates either commit cluster-wide or fully roll back.
LMHBGC/GE Heartbeat Monitor — monitors LMS, LMD, and LMON for health; triggers alerts if they hang.
GCS

Global Cache Service

Manages data block coherency across all instances. Tracks which instance holds each block and in what mode. Coordinates all block transfers via LMS processes.

  • Maintains the GRD (Global Resource Directory)
  • Manages PCM lock modes: Null → Shared → Exclusive
  • Handles CR (Consistent Read) and Current block transfers
  • Coordinates Dynamic Resource Mastering (DRM)
GES

Global Enqueue Service

Manages all non-block resources cluster-wide. Ensures consistent locking semantics for transactions, DDL, dictionary entries, and library cache objects.

  • Transaction locks (TX), DML locks (TM)
  • Dictionary cache locks and row cache locks
  • Library cache locks and pins (shared SQL)
  • Sequence number coordination across instances

Block Transfer Types

Cache Fusion block transfers are classified by how many nodes are involved. 2-way is optimal; 3-way indicates the master and holder are different nodes.

Scenario: Instance 2 needs block X. Instance 1 is both master and holder.

This is the optimal case — only 1 message + 1 block transfer. Wait event: gc cr block 2-way or gc current block 2-way.

Normal and expected. High rates simply mean lots of read traffic across nodes — consider application-level instance affinity if you want to reduce them.

2-way block transfer
Instance 2                    Instance 1
(requester)                (master + holder)
     |                            |
     |-- REQUEST block X ------>|
     |                            |
     |<-- SHIP block X ----------|
     |   (1 msg + 1 transfer)     |
     |                            |
 Wait: gc cr block 2-way

Scenario: Instance 2 needs block X. Instance 3 is the master. Instance 1 is the holder.

Requires 2 messages + 1 block transfer — slightly slower. Wait event: gc cr block 3-way. Normal but less optimal.

Consistently high 3-way rates suggest mastering is not aligned with usage. Dynamic Remastering (DRM) should self-correct over time by moving the master to the most frequent user.

3-way block transfer
Inst 2        Inst 3 (master)  Inst 1 (holder)
  |                |                |
  |-- REQUEST -->|                |
  |               |-- FWD req -->|
  |               |                |
  |<------------- SHIP block X ---|
  |  (2 msgs + 1 transfer)
Wait: gc cr block 3-way

DML Scenario: Node 2 wants to UPDATE a row in block B that Node 1 currently holds dirty (XCUR).

current block transfer (DML)
1. Node 2 session: UPDATE table SET ... WHERE pk=100
2. LMD on Node 2 sends BL (Buffer Lock) request to GRD master for block B
3. GRD master (Node 1) sees it holds block B in XCUR (dirty)
4. Master sends "downgrade and ship" to Node 1's LMS
5. Node 1 LMS: downgrades lock → PI (Past Image), ships block to Node 2
6. Node 2 receives block in XCUR mode → makes modification
7. Node 1 retains PI until checkpoint → then PI is discarded
What is a PI (Past Image)? When a node transfers its current dirty block to another node, it keeps a copy of the pre-transfer state. This is the Past Image. It enables faster instance recovery — the recovering instance can find the pre-crash image in the former holder's buffer cache rather than reading from disk.

Global Resource Directory (GRD)

A distributed in-memory directory split across all instances' SGAs. Tracks every block held in any instance's buffer cache: which instance holds it, in what lock mode, and its SCN.

Dynamic Resource Mastering (DRM)

When one instance issues 50+ more BL requests than others for an object, GRD ownership for that object "remasters" to that instance. This converts 3-way transfers to 2-way. Managed by LMON + LMS0.

PCM Lock Modes: N — Null S — Shared (read) X — Exclusive (write) PI — Past Image CR — Consistent Read

kernel.shmmax — Max shared memory segment size. Set to ~50% of RAM (in bytes). For 64GB RAM: 34359738368.
kernel.shmall — Total shared memory pages. Formula: shmmax ÷ page_size (4096). For 34GB shmmax: ≈8388608.
kernel.sem — SEMMSL SEMMNS SEMOPM SEMMNI. Oracle requires 250 32000 100 128.
net.ipv4.ip_local_port_range — Start at 9000 to avoid conflicts with Oracle/cluster ports (below 9000).
rp_filter = 2 — "Loose" reverse path filtering. Required for multi-homed RAC servers where interconnect traffic uses a different routing path than client traffic.

Section 04

Oracle RAC on AWS EC2

Running Oracle RAC in the cloud — architecture differences, networking solutions, shared storage options, and real-world limitations.

The Core AWS Challenge: No Multicast

Standard AWS VPC networking is Layer 3 only — it does not support multicast. Oracle Clusterware interconnect traditionally needs multicast for cluster membership messaging. The solution used by most production RAC-on-AWS deployments is FlashGrid CLAN (Cloud Area Network), which emulates a virtual Layer 2 network on top of EC2 networking, enabling multicast and cluster-aware interconnect.

AWS Networking Setup

Cluster Placement Group

All RAC nodes must be in a cluster placement group (same AZ). Provides up to 10Gbps between instances, lowest available latency. Required for Cache Fusion performance.

Enhanced Networking (SR-IOV)

Enable on all instances. Reduces network latency and CPU overhead. Use ENA (Elastic Network Adapter) on R5/C5/M5 instances.

ENI Layout per Node

eth1 — Private subnet (Cache Fusion interconnect)
eth2 — (optional) second private NIC for HAIP

UDP  42424 — CSS

Shared Storage Options

Option 1EBS io2 Multi-Attach

A single io2 EBS volume attached to up to 16 EC2 instances simultaneously. Used as ASM raw disks. Requires cluster-aware I/O (ASM handles this). Single AZ only.

aws ec2 create-volume \
  --availability-zone us-east-1a \
  --size 500 --volume-type io2 \
  --iops 16000 \
  --multi-attach-enabled

aws ec2 attach-volume \
  --volume-id vol-xxxx \
  --instance-id i-node1 --device /dev/sdb
aws ec2 attach-volume \
  --volume-id vol-xxxx \
  --instance-id i-node2 --device /dev/sdb
Option 2FSx for NetApp ONTAP (NFS)

Fully managed NFS with cross-AZ replication. Used with Oracle Direct NFS (dNFS). Best for simpler HA or cross-AZ setups. Not traditional ASM-based RAC.

Option 3FlashGrid Storage Fabric

Software that aggregates per-node EBS volumes into shared storage. Works alongside FlashGrid CLAN for networking. Most complete AWS RAC solution — available via AWS Marketplace.

FlashGrid CLAN Architecture

FlashGrid CLAN runs as a software layer on each RAC node. It creates a virtual private network between nodes with multicast emulation — making AWS EC2 behave like an on-premises environment for Oracle Clusterware.

CloudFormation Deployment: Subscribe to FlashGrid on AWS Marketplace → upload Oracle ZIPs to S3 → configure template (node count, instance types, storage) → FlashGrid Launcher generates CloudFormation stack → deploy → Clusterware + DB installed automatically.
Recommended Instance Types: R5.4xlarge or larger for DB nodes (memory-optimized). C5n for network-heavy workloads. Always in same cluster placement group.

srvctl & crsctl — Complete Command Reference

Every command you need to manage Oracle RAC cluster resources from the command line.

srvctl vs crsctl — Rule of Thumb: Use srvctl for Oracle application resources (databases, instances, services, listeners, VIPs, ASM). Use crsctl for Clusterware infrastructure (daemons, voting disks, OCR, CSS parameters). Most srvctl commands run as oracle/grid; most crsctl destructive ops need root.
srvctl — database
# Start / Stop database (all instances)
srvctl start database -d racdb
srvctl start database -d racdb -o mount
srvctl stop database -d racdb
srvctl stop database -d racdb -o immediate
srvctl stop database -d racdb -o abort

# Status and config
srvctl status database -d racdb
srvctl status database -d racdb -v   # verbose
srvctl config database -d racdb      # full config
srvctl config database               # list all DBs

# Enable / Disable auto-start
srvctl enable database -d racdb
srvctl disable database -d racdb
srvctl — instance
# Start / Stop specific instance
srvctl start instance -d racdb -i racdb1
srvctl stop instance -d racdb -i racdb1
srvctl stop instance -d racdb \
  -i racdb1 -o abort

# Status per instance
srvctl status instance -d racdb -i racdb1

# Add / Remove instance
srvctl add instance -d racdb \
  -i racdb1 -n node1
srvctl add instance -d racdb \
  -i racdb2 -n node2

# Enable / Disable

RAC Wait Events & Performance Tuning

Understanding and fixing gc wait events — the most common RAC-specific performance bottlenecks.

What it means

A session on the local node needs a block, but another session on the same node already sent a request for that block and is waiting for it to arrive from a remote node. You're queued behind a local requester.

Root Causes

  • Hot blocks — high concurrency on same data blocks
  • Right-hand index growth (sequence-based inserts)
  • Small sequence cache causing frequent cross-node coordination
  • Insufficient PCTFREE / freelist contention

Diagnosis & Fix

-- Find hot blocks causing this wait
SELECT current_obj#, o.object_name,
       current_file#, current_block#,
       count(*) samples
FROM   gv$active_session_history ash
JOIN   dba_objects o
  ON ash.current_obj#=o.object_id
WHERE  event='gc buffer busy acquire'
  AND  sample_time > sysdate-1/24
GROUP BY current_obj#,o.object_name,
         current_file#,current_block#
ORDER BY samples DESC;

-- Fix: increase sequence cache
ALTER SEQUENCE my_seq CACHE 1000 NOORDER;

-- Fix: use ASSM tablespace
-- Avoids freelist contention automatically

Different from acquire: Here, a session on the local node needs a block, but a remote instance is currently requesting that block from the local node. The local session waits while the block is being "released" to the remote requester.

Root causes are the same as gc buffer busy acquire — hot blocks, high cross-node DML traffic. Both events together indicate the same objects need attention. Fixes: application partitioning (pin each workload to its own instance using services), reverse-key indexes, partitioning tables.

2-way: Consistent Read block transferred directly between 2 nodes (requester = master + holder). Normal and optimal. One message + one transfer. If very high — consider instance affinity for heavy-reader workloads.

3-way: Master and holder are different nodes — 2 messages + one transfer. Slightly slower but normal in a multi-node cluster. Consistently high 3-way rates suggest DRM hasn't aligned mastering with usage patterns yet. If problematic: let DRM run or tune _gc_policy_minimum.

-- 2-way vs 3-way ratio check
SELECT inst_id, event,
       total_waits, average_wait
FROM   gv$system_event
WHERE  event IN (
  'gc cr block 2-way',
  'gc cr block 3-way',
  'gc current block 2-way',
  'gc current block 3-way')
ORDER BY inst_id, event;

-- Ideal: 2-way >> 3-way in ratio

Congested = GCS is backed up. Requests are piling up — LMS processes can't keep up with block transfer demand. This indicates a systemic problem.

Causes:

  • Interconnect bandwidth saturation
  • LMS process count too low for workload
  • Server CPU starvation
  • Extremely high block transfer rate (application design)
-- Increase LMS processes (default auto-scales)
ALTER SYSTEM SET
  gcs_server_processes = 4 SCOPE=SPFILE;

-- Set LMS as high-priority OS thread
ALTER SYSTEM SET
  "_high_priority_processes"='LMS*|LGWR*'
  SCOPE=SPFILE;

-- Upgrade interconnect bandwidth
-- Reduce cross-node traffic via
-- application partitioning / services
-- PARALLEL_FORCE_LOCAL=TRUE for parallel SQL

If a requested block is not received within 0.5 seconds, it is considered "lost" and must be re-requested. Even occasional occurrences indicate a serious interconnect problem — packet loss, network congestion, faulty NIC/switch, or MTU mismatch.

SELECT inst_id, event, total_waits, time_waited
FROM   gv$system_event
WHERE  event = 'gc block lost';

Services, FAN, TAF & Application Continuity

How applications connect to RAC, survive failures, and get load-balanced — from services to FAN events to full transactional replay.

Database Services — The Right Way to Connect

Never use the default service (same as DB_NAME) for production. It has no HA properties — if the instance it's on dies, clients don't fail over. Always create dedicated services for each workload type.
Service creation options
-- srvctl: preferred/available instances
srvctl add service -d racdb \
  -s oltp_svc \
  -r racdb1,racdb2 \         -- preferred
  -a racdb3 \                -- available (failover)
  -clbgoal SHORT \           -- conn-time LB: OLTP
  -rlbgoal SERVICE_TIME \    -- runtime LB
  -notification TRUE         -- enable FAN

-- Or via SQL (DBMS_SERVICE)
BEGIN
  DBMS_SERVICE.CREATE_SERVICE(
    service_name    => 'OLTP_SVC',
    network_name    => 'OLTP_SVC',
    failover_method => DBMS_SERVICE.FAILOVER_METHOD_BASIC,
    failover_type   => DBMS_SERVICE.FAILOVER_TYPE_SELECT,
    failover_retries=> 30,
    failover_delay  => 10,
    clb_goal        => DBMS_SERVICE.CLB_GOAL_SHORT,
    rlb_goal        => DBMS_SERVICE.RLB_GOAL_SERVICE_TIME
  );
END;
/
EXEC DBMS_SERVICE.START_SERVICE('OLTP_SVC');
CLBGOAL (Connection Load Balancing Goal)

SHORT — for OLTP (short-lived sessions): balance by active sessions + CPU. LONG — for long-lived connections: balance by session count only.

RLBGOAL (Runtime Load Balancing Goal)

SERVICE_TIME — routes by response time (OLTP). THROUGHPUT — routes by CPU/throughput (batch). NONE — no runtime LB.

FAN — Fast Application Notification

FAN publishes real-time events when cluster topology changes. Applications learn about node/service failures in milliseconds — not after TCP timeout (which can take 30+ minutes).

DOWN events — instance/service went offline → application abandons connections to that instance immediately
UP events — instance/service came online → application can route new connections there
Load Balancing Advisory events — published every 30s with current load per instance → UCP rebalances connections

From Oracle 12c, FAN is auto-configured when connecting via JDBC Thin, ODP.NET, OCI to a 12c+ RAC database. No manual setup needed for modern drivers.

TAF vs Application Continuity — Side by Side

TAF

Transparent Application Failover

Oracle Net-level failover. Automatically reconnects the client to a surviving instance when the current instance fails.

  • Replays current SELECT transparently
  • Recreates session on new instance
  • Does NOT replay uncommitted DML
  • OCI driver only (no modern JDBC Thin)
tnsnames.ora with TAF
RACDB_TAF =
  (DESCRIPTION =
    (ADDRESS_LIST =
      (FAILOVER = ON)
      (LOAD_BALANCE = YES)
      (ADDRESS = (PROTOCOL=TCP)
        (HOST=node1-vip)(PORT=1521))
      (ADDRESS = (PROTOCOL=TCP)
        (HOST=node2-vip)(PORT=1521)))
    (CONNECT_DATA =
      (SERVICE_NAME = oltp_svc)
      (FAILOVER_MODE =
        (TYPE = SELECT)   -- or SESSION
        (METHOD = BASIC)  -- or PRECONNECT
        (RETRIES = 30)
        (DELAY = 10))))
AC

Application Continuity (12c+)

Masks ALL outages by rebuilding the session state AND replaying the entire in-flight request — including uncommitted DML. Zero visible disruption.

  • Replays SELECT + uncommitted DML
  • Reconstructs full session state
  • Works with planned + unplanned outages
  • Requires JDBC Thin Replay Driver + UCP

Top Oracle RAC Interview Questions & Answers

Q1: What is Oracle RAC and what are its primary purposes?
Oracle RAC (Real Application Clusters) allows multiple instances running on different servers to simultaneously access a single shared database (shared-everything architecture). Primary purposes: High Availability — if one node fails, others continue; Horizontal Scalability — add nodes for more throughput; Load Distribution — route workloads across instances via services. Key concept: one database, many instances.
Q2: Explain Cache Fusion. What problem does it solve?
Pre-Oracle 8i: when Instance 2 needed a block that Instance 1 had modified, Instance 1 had to write it to disk and Instance 2 had to read it from disk — very slow ("ping"). Cache Fusion eliminates this by shipping blocks directly between buffer caches over the private interconnect (memory-to-memory transfer). The Global Cache Service (GCS), driven by LMS processes, manages all transfers and maintains the GRD (Global Resource Directory) to track where every block is cached across all nodes.
Q3: What is SCAN and how many IPs does it need? How is it different from VIP?
SCAN (Single Client Access Name) is a single DNS name that resolves to exactly 3 IPs (Oracle recommendation). Three SCAN listeners run on cluster nodes, not tied to specific nodes. Clients use only the SCAN name — tnsnames.ora never changes when nodes are added/removed. SCAN also routes to the least-loaded instance via Load Balancing Advisory. VIP (Virtual IP) is one per node; if a node fails, its VIP moves to another node so clients get fast "connection refused" rather than TCP timeout. VIPs were the pre-SCAN solution — clients had to list all VIPs in tnsnames.
Q4: What is OCR and what does it store?
OCR (Oracle Cluster Registry) is the shared configuration repository for all Clusterware resources. Stored in ASM (recommended). Stores: node membership, all resource configs (databases, instances, services, VIPs, listeners, their start/stop policies and dependencies), ASM disk group info, SCAN VIP details. Auto-backed up every 4 hours. Key commands: ocrcheck, ocrconfig -showbackup, ocrconfig -manualbackup.
Q5: What is the voting disk and why should you have 3 or 5?
Voting disks prevent split-brain: each node writes a heartbeat block every second. When network communication fails, the sub-cluster with access to the majority of voting disks survives — the minority self-evicts. Formula: 2N+1 gives you N failures tolerated. With 1 disk: 0 failures tolerated. With 3: 1 failure tolerated. With 5: 2 failures tolerated. Always use 3 minimum, 5 preferred for production.
Q6: What happens when a node fails in Oracle RAC?
Sequence: (1) CSS on surviving nodes detects missed heartbeats → declares node dead after misscount seconds; (2) Failed node's VIP immediately fails over → clients get fast "connection refused"; (3) FAN DOWN event published via ONS → applications abandon connections to dead node instantly; (4) Services fail over to available instances; (5) GCS/GES reconfiguration — GRD redistributed among survivors; (6) SMON on a surviving instance mounts the failed instance's redo thread and performs crash recovery: roll forward, then rollback uncommitted transactions. Database is available throughout for surviving instances.
Q7: What is the difference between GCS and GES?
GCS (Global Cache Service) manages DATA BLOCK coherency — tracks which instance holds each block and in what lock mode (N/S/X), coordinates all block transfers via LMS processes. GES (Global Enqueue Service) manages all NON-BLOCK resources: transaction locks (TX), DDL locks (TM), dictionary cache locks, library cache locks, sequence coordination. Think: GCS = data blocks, GES = everything else (locks, latches, shared cursors).
Q8: What is the difference between srvctl and crsctl?
srvctl manages Oracle application resources built on top of Clusterware: databases, instances, services, listeners, VIPs, ASM, disk groups. Used by oracle/grid OS user. crsctl manages Clusterware infrastructure: start/stop the CRS stack, manage voting disks, query/set CSS timing parameters (misscount, disktimeout), check daemon health. Most crsctl destructive operations require root.
Q9: What is TAF vs Application Continuity? When would you use each?
TAF (Transparent Application Failover): Oracle Net-level, OCI driver only, replays SELECT queries, does NOT replay uncommitted DML. Good for simple read-heavy apps using OCI. Application Continuity (AC): 12c+, JDBC Thin Replay Driver + UCP, rebuilds full session state AND replays the entire in-flight request including uncommitted DML. Works for planned (rolling patching) and unplanned outages. Use TAF for legacy OCI apps; use AC for modern Java apps with Oracle's JDBC stack.
Q10: What is dynamic remastering (DRM)?
DRM redistributes GRD block ownership (mastering) based on actual access patterns. When one instance issues 50+ more BL (Buffer Lock) requests for an object than the current master, the master is relocated to that instance. This converts 3-way block transfers to 2-way, reducing interconnect overhead. Managed by LMON and LMS0. Can be disabled with _lm_dynamic_remastering=FALSE if it causes GRD freeze issues in older versions.
Q11: What is HAIP and when was it introduced?
HAIP (High Availability IP) was introduced in Oracle 11.2.0.2. It uses link-local addresses (169.254.x.x) to provide automatic load balancing and failover for interconnect traffic across multiple physical NICs. Managed by Clusterware — not OS bonding. Requires 2+ physical interfaces on the private network. When one NIC fails, traffic automatically routes to the other. Appears transparent to Cache Fusion.
Q12: Why is MTU 9000 recommended for the interconnect?
Default MTU is 1500 bytes. An 8KB Oracle data block fragmented at 1500 bytes requires 5-6 network packets per block transfer. With jumbo frames (MTU 9000), an 8KB block fits in approximately 1 packet. This dramatically reduces fragmentation overhead, CPU usage, and latency for Cache Fusion block transfers. Must be configured consistently on ALL nodes and the network switch. Verify with: ping -s 8192 -M do node2-priv.
Q13: Why do sequences show gaps in RAC and how do you configure them properly?
Each RAC instance receives its own cache block of sequence numbers (e.g., Instance 1 gets 1-20, Instance 2 gets 21-40). When instances switch between cache blocks, sequence values appear out of order. This is normal and expected in RAC. Best practice: use large CACHE values to reduce the frequency of cross-instance coordination, and always use NOORDER (default) unless strict ordering is required: ALTER SEQUENCE s CACHE 1000 NOORDER;. NOORDER means sequence values are unique but not necessarily monotonically increasing across all instances.
Q14: What is the GPNP profile and why is it important?
The GPNP (Grid Plug and Play) profile is a small XML file at $GRID_HOME/gpnp/<hostname>/profiles/peer/profile.xml on each node. It contains: ASM diskstring, ASM spfile location, public/private network interface names, voting disk storage info. It is read by the GPNPD daemon during Clusterware startup BEFORE ASM is accessible — so CSSD can find voting disks. It is the bootstrap configuration for the cluster. Corruption = cluster can't start.
Q15: How do you add a new node to an Oracle RAC cluster?
Steps: (1) Prepare the new node — same OS config, kernel params, users/groups, /etc/hosts entries, SSH equivalence; (2) Extend Grid Infrastructure: run gridSetup.sh from existing node, select "Add Cluster Member Nodes", then run root scripts on new node; (3) Extend Oracle RDBMS home: run addNode.sh from existing Oracle home; (4) Add instance via DBCA: dbca -addInstance -gdbName racdb -nodeName node3 -instanceName racdb3; (5) Verify: olsnodes -v, srvctl status database -d racdb.

Interview Q&A

Oracle RAC — Interview Questions

Frequently asked RAC interview questions covering Cache Fusion, cluster services, and high-availability design.

Q1What is Cache Fusion and why is it needed in Oracle RAC?

In Oracle RAC, all nodes share the same database files on shared storage but each node has its own independent buffer cache. Cache Fusion is Oracle's protocol that allows nodes to transfer dirty (modified) data blocks directly between buffer caches over the private interconnect, avoiding the need to write the block to disk first.

Without Cache Fusion, if Node 1 modifies a block and Node 2 needs that block, Node 1 would have to write the block to disk and Node 2 would read from disk — a slow and wasteful operation. Cache Fusion makes this a fast in-memory transfer. The Global Cache Service (GCS) and Global Enqueue Service (GES) coordinate all block transfers and locking. High latency or lost packets on the interconnect are the #1 cause of RAC performance problems.

Q2What is the difference between Oracle RAC and Oracle Data Guard?

RAC is a High Availability + Scale-Out solution: multiple active nodes share one database on shared storage. All nodes are read-write and serve production traffic simultaneously. Protection is against node failure, not datacenter failure.

Data Guard is a Disaster Recovery solution: a standby database on separate storage (possibly at a different datacenter) receives redo from the primary. The standby is passive (Physical Standby) or used for read-only reporting (Active Data Guard). Protection is against datacenter/storage failure. Many enterprises deploy both: RAC for HA on the primary site, Data Guard for DR to a secondary site.

Q3What is Transparent Application Failover (TAF) and how does it work?

TAF is a client-side failover mechanism configured in the TNS descriptor (tnsnames.ora or connection string). If the node a client is connected to fails, TAF automatically reconnects the session to a surviving node and re-executes any active query in progress — without the application receiving a fatal error.

TAF has two modes: SELECT (refetches rows already returned to the application; the query continues from where it was) and SESSION (reconnects only; running queries are re-executed from scratch). TAF is transparent to SELECT statements only — uncommitted DML at the time of failover is lost and must be resubmitted.

Q4How does Oracle RAC achieve load balancing?

Oracle RAC uses two load balancing methods:

  • Client-side LB: Configured in TNS with LOAD_BALANCE=ON. The JDBC/OCI driver randomly picks an address from the address list in the connection descriptor. Simple round-robin, no awareness of actual node load.
  • Server-side LB (SCAN): SCAN (Single Client Access Name) resolves to 3 IP addresses managed by GNS/DNS. LREG publishes each node's connection load metrics to the SCAN listener. New connections are routed to the least-loaded node. This is the recommended approach for 11gR2+ and above.

Services can also be configured with preferred/available instances to control which workloads land on which nodes (e.g., OLTP on node 1, reports on node 2).

Q5What is the importance of the private interconnect in Oracle RAC?

The private interconnect is a dedicated high-speed network (typically 10GbE or InfiniBand bonded) used exclusively for inter-node communication in RAC. All Cache Fusion block transfers, GCS/GES messages, and cluster heartbeats travel over this network. It must be isolated from public traffic to guarantee low, consistent latency.

If the private interconnect becomes saturated or unreliable: (1) "gc buffer busy acquire/release" wait events will spike; (2) cache fusion transfers slow down; (3) in worst case, the cluster heartbeat misses its deadline and Oracle Clusterware triggers a node eviction (node reboot) to protect database integrity. Monitoring via V$CLUSTER_INTERCONNECTS and V$GES_STATISTICS is essential in RAC environments.
