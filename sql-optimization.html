Section 1

SQL Tuning Methodology

Follow a systematic approach: identify → understand → diagnose → fix → validate. Never tune blindly.

1

Identify the Bad SQL

Use AWR Top SQL, ASH, or V$SQL to find the highest-impact statements by elapsed time, CPU, logical reads, or executions.

-- Top 10 SQL by elapsed time
SELECT sql_id, elapsed_time/executions/1e6 avg_sec,
       executions, sql_text
FROM   v$sql
WHERE  executions > 0
ORDER BY elapsed_time/DECODE(executions,0,1,executions) DESC
FETCH FIRST 10 ROWS ONLY;
2

Understand the Execution Plan

Read the plan from bottom-up, left-to-right. Look for full table scans on large tables, Cartesian joins, high cardinality estimates vs. actuals.

-- Real plan from library cache
SELECT * FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(
    '&sql_id', 0,
    'ALLSTATS LAST'
  )
);
3

Fix & Validate

Apply fix (index, rewrite, hint, stat refresh). Measure before/after: compare elapsed time, logical reads, and row source operations.

-- Compare two SQL IDs
SELECT sql_id, elapsed_time,
       buffer_gets, disk_reads,
       executions
FROM   v$sql
WHERE  sql_id IN ('&old','&new');
Section 2

Cost-Based Optimizer & Statistics

The CBO chooses the execution plan using statistics. Stale or missing stats are the #1 cause of bad plans.

How CBO Picks a Plan

  • 1.Parse: SQL is parsed, transformed (view merging, subquery unnesting, predicate pushdown).
  • 2.Statistics lookup: CBO reads table/column/index stats from the data dictionary.
  • 3.Cardinality estimation: CBO estimates rows for each operation using selectivity formulas and histograms.
  • 4.Cost calculation: Each candidate plan gets a cost score (I/O + CPU + network). Lowest cost wins.
  • 5.Plan generation: Winning plan stored in library cache. Reused on soft parse.

Statistics Collection Best Practices

-- Gather schema stats (auto sample size)
EXEC DBMS_STATS.GATHER_SCHEMA_STATS(
  ownname     => 'MYSCHEMA',
  estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
  method_opt  => 'FOR ALL COLUMNS SIZE AUTO',
  cascade     => TRUE
);

-- Check stale objects
SELECT owner, table_name, stale_stats, last_analyzed
FROM   dba_tab_statistics
WHERE  stale_stats = 'YES'
ORDER BY last_analyzed;

-- Lock stats on staging/volatile tables
EXEC DBMS_STATS.LOCK_TABLE_STATS('MYSCHEMA','BIG_TABLE');

Section 3

Reading Execution Plans

Reading plans is the core skill of SQL tuning. Read bottom-up, left-to-right. Compare E-Rows vs A-Rows for cardinality errors.

Key Plan Operations

TABLE ACCESS FULLWatch out

Full scan — acceptable for small tables or when >10-15% rows returned. Bad on large tables with selective predicates.

INDEX RANGE SCANGood

Reads a range of index entries. Efficient for selective predicates returning <5% of rows.

INDEX UNIQUE SCANBest

Single-row lookup via primary key or unique index. Most efficient access path.

NESTED LOOPSContext

Good for OLTP — small outer row set + indexed inner table. Bad for large data sets (use HASH JOIN instead).

HASH JOINDW/Batch

Builds hash table from smaller side, probes with larger side. Best for large-table equi-joins in data warehouse queries.

Cardinality Feedback & Adaptive Plans

Spot cardinality misestimates 
-- E-Rows vs A-Rows tells the whole story
-- Use /*+ GATHER_PLAN_STATISTICS */ hint
SELECT /*+ GATHER_PLAN_STATISTICS */
       e.employee_id, d.department_name
FROM   employees e, departments d
WHERE  e.department_id = d.department_id
AND    e.job_id = 'SA_REP';

-- Then display with actual rows
SELECT * FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(NULL,NULL,
    'ALLSTATS LAST'));

-- Look for huge E-Rows vs A-Rows gaps
-- E-Rows=1000, A-Rows=1 → bad index skip
-- E-Rows=1, A-Rows=50000 → missing histogram
Section 4

SQL Hints

Hints are directives to the optimizer. Use sparingly — fix root cause first (stats, indexes). Hints are last resort or testing tools.

HintPurposeExample
/*+ FULL(t) */Force full table scanWhen index is slower (bulk load queries)
/*+ INDEX(t idx_name) */Force specific indexWhen CBO chooses wrong index
/*+ NO_INDEX(t) */Suppress index useForce FTS for large % row access
/*+ USE_NL(t) */Force nested loops joinOLTP, small result sets with indexed lookups
/*+ USE_HASH(t) */Force hash joinLarge table equi-joins, DW queries
/*+ LEADING(a b c) */Control join orderForce CBO to start with smallest table
/*+ PARALLEL(t 4) */Enable parallel queryLarge table scans, DW aggregations
/*+ APPEND */Direct-path INSERTBulk inserts — bypasses buffer cache
/*+ CARDINALITY(t 500) */Override cardinalityFix bad estimates without stat change
Hint Usage Examples 
-- Force index + hash join
SELECT /*+ INDEX(e EMP_DEPT_IDX) USE_HASH(d) */
       e.employee_id, d.department_name
FROM   employees e, departments d
WHERE  e.department_id = d.department_id;

-- Parallel aggregation
SELECT /*+ PARALLEL(s 8) */
       region, SUM(sales_amount)
FROM   sales_fact s
GROUP BY region;

-- Direct-path bulk insert
INSERT /*+ APPEND */ INTO sales_archive
SELECT * FROM sales WHERE sale_date < ADD_MONTHS(SYSDATE,-12);
Section 5

Indexing Strategies

Correct indexing solves 80% of SQL performance problems. Know when to add, when to drop, and how to choose index type.

Index Types

  • B-Tree (default): Balanced tree. Best for high-cardinality columns, range scans, OLTP equality lookups.
  • Bitmap: Compressed bitmaps per value. Best for low-cardinality (gender, status) DW columns. Never use in OLTP (row-level lock contention).
  • Function-Based: Index on UPPER(name), TO_CHAR(date). Query must match expression exactly.
  • Composite: Multi-column. Column order matters — most selective or equality first. Cover leading-edge prefix queries.
  • Partial (12c+): WHERE status='ACTIVE' — indexes only matching rows. Smaller, faster.

Index Anti-Patterns

  • Leading wildcard: LIKE '%Smith' — cannot use B-Tree index. Use Oracle Text.
  • Function on indexed column: UPPER(name) = 'JOHN' — use FBI instead.
  • Implicit type conversion: WHERE number_col = '100' — forces conversion, suppresses index.
  • OR on multiple indexed columns: CBO may skip both indexes. Rewrite as UNION ALL.
  • NOT NULL or NOT IN: B-Tree index doesn't store NULL — predicates may force FTS.
Index Creation Examples 
-- Composite index (department_id leading for range, salary for filter)
CREATE INDEX emp_dept_sal_idx ON employees(department_id, salary);

-- Function-based index for case-insensitive search
CREATE INDEX emp_name_upper_idx ON employees(UPPER(last_name));

-- Partial index (12c+): only active employees
CREATE INDEX emp_active_idx ON employees(hire_date)
  WHERE status = 'ACTIVE';

-- Find unused indexes (candidates for removal)
SELECT object_name, object_type
FROM   v$object_usage
WHERE  used = 'NO'
AND    monitoring = 'YES';
Section 6

Bind Variables & Cursor Sharing

Bind variables are the single biggest scalability improvement for OLTP applications. Literal SQL causes hard parses and library cache contention.

Literals vs. Bind Variables

-- BAD: Literal SQL — hard parse every time
SELECT * FROM orders WHERE order_id = 1001;
SELECT * FROM orders WHERE order_id = 1002;
-- Each is a unique SQL_ID → library cache bloat

-- GOOD: Bind variable — soft parse every time
SELECT * FROM orders WHERE order_id = :order_id;
-- Same SQL_ID, plan reused → zero hard parse cost

-- Check bind variable usage in library cache
SELECT sql_id, executions, parse_calls, sql_text
FROM   v$sql
WHERE  sql_text LIKE '%orders%'
ORDER BY executions DESC;

Bind Peeking & Adaptive Cursor Sharing

Oracle peeks at bind values on first execution to choose a plan. If data is skewed, the initial plan may be wrong for other values.

Adaptive Cursor Sharing (11g+) solves this: Oracle detects bind-sensitive plans, creates multiple child cursors for different value ranges, and picks the right one per execution.

-- Check if cursor is bind-sensitive/aware
SELECT sql_id, child_number,
       is_bind_sensitive, is_bind_aware,
       executions, rows_processed
FROM   v$sql
WHERE  sql_id = '&sql_id';
Section 7

SQL Plan Management (SPM)

SPM prevents plan regressions after upgrades, stat refreshes, or parameter changes. Plans only change when you approve a better alternative.

SPM Workflow

  • Capture: Oracle records plans into SQL Plan Baselines (enabled or auto-capture).
  • Select: Only accepted baseline plans are used. New plans go to "not accepted" state.
  • Evolve: SPM Evolve Advisor tests new plans. If better, promotes to accepted.
  • Protect: Upgrade-safe — baselines survive across Oracle version upgrades.

SPM Commands

-- Enable automatic capture
ALTER SYSTEM SET optimizer_capture_sql_plan_baselines=TRUE;

-- Load baseline from cursor cache
DBMS_SPM.LOAD_PLANS_FROM_CURSOR_CACHE(
  sql_id => '&sql_id'
);

-- View existing baselines
SELECT sql_handle, plan_name, accepted,
       enabled, executions, elapsed_time
FROM   dba_sql_plan_baselines
WHERE  sql_text LIKE '%orders%';

-- Run SPM Evolve (auto-promote better plans)
SELECT DBMS_SPM.EVOLVE_SQL_PLAN_BASELINE(
  sql_handle => 'SQL_xxxxx',
  verify     => 'YES',
  commit     => 'YES'
) FROM dual;
Section 8

SQL Optimization — Interview Q&A

Top questions asked in Oracle DBA / developer interviews on SQL tuning topics.

EXPLAIN PLAN generates the estimated plan before execution and stores it in PLAN_TABLE. DBMS_XPLAN.DISPLAY_CURSOR retrieves the actual plan that was used during execution from the library cache (V$SQL_PLAN). The cursor cache version shows actual row counts (A-Rows) vs estimates (E-Rows), revealing cardinality errors. Always prefer DISPLAY_CURSOR for tuning real performance problems.

Common reasons the CBO skips an index:

  • Query returns too many rows (>15%) — FTS is cheaper
  • Stale statistics — CBO underestimates selectivity
  • Function applied to indexed column without FBI
  • Implicit data type conversion on the predicate column
  • Missing or wrong histogram (skewed data)
  • Index not covering leading edge of composite key

Oracle peeks at the actual bind value on the first hard parse to generate a plan. The same plan is then reused for all subsequent executions with different bind values. If the data is skewed (e.g., status='ACTIVE' returns 90% of rows but status='CLOSED' returns 0.1%), the plan chosen for the first value may be terrible for others. Adaptive Cursor Sharing (11g+) partially solves this by generating multiple child cursors for different bind value ranges.

SPM captures accepted execution plans as SQL Plan Baselines. New plans (after upgrades, stat refreshes, or parameter changes) are only used after they're verified as equal or better. Use SPM: (1) before Oracle upgrades to capture known-good plans; (2) for critical OLTP SQL that cannot afford plan regressions; (3) after tuning to lock in an improved plan permanently.

  • Refresh statistics (DBMS_STATS.GATHER_TABLE_STATS)
  • Create a new index matching the query's predicate/join columns
  • Create a SQL Patch (DBMS_SQLDIAG) to inject hints without source changes
  • Use SQL Plan Management to load a better plan baseline
  • Create a Function-Based Index if expression is blocking index use
  • Adjust optimizer parameters at session/system level
