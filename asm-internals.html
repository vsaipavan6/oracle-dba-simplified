Section 1

What Is Oracle ASM?

ASM is Oracle's built-in volume manager and clustered filesystem — available since Oracle 10g. It replaces the need for OS-level LVM, hardware RAID configuration, and manual striping by handling storage management directly within the Oracle software stack.

No More Manual LVM

OS-level LVM (Logical Volume Manager) required deep knowledge of volume groups, physical volumes, and logical volumes — a separate skillset. ASM eliminates this: DBAs manage storage entirely through SQL and ASMCMD.

Automatic I/O Balancing

ASM automatically distributes data across all disks in a disk group (round-robin striping). When you add a disk, ASM rebalances extents online — no window, no downtime. Old approach: manually migrate files or reconfigure RAID sets.

Oracle-Aware Redundancy

Hardware RAID applies the same protection to all data. ASM applies per-file-type mirroring — 3-way for control files, 2-way for datafiles, unprotected for archive logs (already recoverable). Far more intelligent than hardware RAID.

ASM Instance vs Database Instance — Critical Distinction

+ASM / +ASM1 ASM Instance
  • INSTANCE_TYPE=ASM in init parameter (mandatory)
  • Lightweight — no buffer cache, no redo logs, no undo segments
  • Small SGA (~512MB–2GB) — only ASM metadata cache
  • Must start before any database instance
  • Manages disk groups exclusively — no user data stored here
  • Connect with: sqlplus / AS SYSASM
  • ORACLE_SID = +ASM (or +ASM1, +ASM2 on RAC)
ORCL / DB_SID Database Instance
  • Full SGA: buffer cache, redo buffer, shared pool, large pool
  • Has undo, redo logs, SYSTEM/SYSAUX tablespaces
  • Connects to ASM instance via the ASMB background process
  • DBWR writes blocks directly to ASM-managed devices
  • References files as: +DATA/orcl/DATAFILE/system.262.1234
  • Requires ASM instance to be running — if ASM crashes, DB crashes

Section 2

Disk Groups & Failure Groups

A disk group is a logical pool of physical disks managed by ASM as a single unit. The redundancy level and failure group design are the two most critical architectural decisions — they cannot be changed after creation.

Most Common

NORMAL REDUNDANCY — 2-Way Mirror

  • Stores 2 copies of every extent (primary + mirror)
  • Requires minimum 2 failure groups (Oracle recommends 3+)
  • Tolerates 1 disk failure (or 1 entire failure group)
  • Usable space ≈ 50% of raw capacity
  • Standard choice for OLTP databases
CREATE DISKGROUP DATA
  NORMAL REDUNDANCY
  FAILGROUP FG1 DISK '/dev/sdb' NAME diska1,
                       '/dev/sdc' NAME diska2
  FAILGROUP FG2 DISK '/dev/sdd' NAME diskb1,
                       '/dev/sde' NAME diskb2
  FAILGROUP FG3 DISK '/dev/sdf' NAME diskc1,
                       '/dev/sdg' NAME diskc2
  ATTRIBUTE 'AU_SIZE'='4M',
            'COMPATIBLE.ASM'='19.0.0.0',
            'COMPATIBLE.RDBMS'='19.0.0.0',
            'DISK_REPAIR_TIME'='12h';

Failure Group Layout (3 FGs — Recommended)

No ASM Mirroring

EXTERNAL REDUNDANCY — Hardware-Protected

Advantages

  • 100% of raw capacity is usable — highest efficiency
  • Performance: no mirroring write overhead
  • Suitable when hardware RAID provides protection

Risks

  • ASM cannot protect against disk failure — 100% reliant on hardware
  • Requires exactly 1 failure group (multiple disks, same FG)
  • Hardware RAID failure = data loss
-- All disks in one implicit failure group
CREATE DISKGROUP DATA
  EXTERNAL REDUNDANCY
  DISK '/dev/sdb' NAME diska1,
       '/dev/sdc' NAME diska2,
       '/dev/sdd' NAME diska3
  ATTRIBUTE 'COMPATIBLE.ASM'='19.0.0.0',
            'COMPATIBLE.RDBMS'='19.0.0.0';
Mission Critical

HIGH REDUNDANCY — 3-Way Mirror

  • Stores 3 copies of every extent (primary + 2 mirrors)
  • Requires minimum 3 failure groups (Oracle recommends 5+)
  • Tolerates 2 simultaneous disk failures in different failure groups
  • Usable space ≈ 33% of raw capacity (3x overhead)
  • Ideal for: voting disks, OCR, SYSTEM tablespace, mission-critical data
-- Requires exactly 3 failure groups for initial creation
CREATE DISKGROUP VOTE
  HIGH REDUNDANCY
  FAILGROUP FG1 DISK '/dev/sdb' NAME vote1
  FAILGROUP FG2 DISK '/dev/sdc' NAME vote2
  FAILGROUP FG3 DISK '/dev/sdd' NAME vote3
  ATTRIBUTE 'COMPATIBLE.ASM'='19.0.0.0';

-- Tolerance: 2 entire FGs can fail; data on 3rd FG survives
Oracle 18c+

FLEX REDUNDANCY — File-Level Mirroring

FLEX disk groups allow redundancy to be set per file (not per disk group). Some files can be unprotected, some NORMAL, some HIGH — all within the same disk group. Introduces File Groups and Quota Groups for fine-grained space management.

New Concepts in FLEX

  • File Group: Named set of files with same redundancy within a FLEX disk group
  • Quota Group: Space allocation limit for a file group (prevents one DB consuming all space)
  • MIRROR attribute: Set UNPROTECTED/NORMAL/HIGH per file during creation
CREATE DISKGROUP DATA
  FLEX REDUNDANCY
  FAILGROUP FG1 DISK '/dev/sdb'
  FAILGROUP FG2 DISK '/dev/sdc';

-- V$ASM_FILEGROUP, V$ASM_QUOTAGROUP
SELECT * FROM v$asm_quotagroup;

Failure Groups — The Most Critical ASM Design Decision

A failure group is a logical grouping of disks that share a common failure domain — they could all fail at the same time due to a shared dependency (SAN controller, power supply, rack, network switch, cooling system).

BAD Design — Hidden Failure Domain

6 disks, 2 failure groups, but both groups share the same SAN controller. If the controller fails, both FG1 and FG2 disks are offline simultaneously — NORMAL redundancy offers NO protection.

GOOD Design — Isolated Failure Domains

FG1: Disks on Controller A, Rack 1, Power Circuit 1. FG2: Disks on Controller B, Rack 1, Power Circuit 2. FG3: Disks on Controller A, Rack 2, Power Circuit 3. Each FG isolated.

Interview answer: A failure group is a collection of ASM disks that represent a single point of failure. ASM ensures that no two redundant copies of the same extent are placed on disks in the same failure group. For NORMAL redundancy: 2 FGs required, 3+ recommended. For HIGH: 3 FGs required, 5+ recommended. Failure groups should align with physical failure domains (SAN controllers, racks, power supplies) to ensure the mirroring actually provides protection.

Section 3

Allocation Units & Striping

The AU is ASM's fundamental storage atom — every extent, every stripe, every file is built from AU-sized chunks. Understanding AU size directly determines your I/O pattern and performance.

What Is an Allocation Unit?

An Allocation Unit (AU) is the smallest unit of space that ASM allocates to a file. When ASM needs to extend a file, it allocates one or more AUs — it cannot give partial AUs. Every disk in a disk group is divided into a sequence of fixed-size AU slots, numbered from 0. ASM tracks which slots are used and which are free using its internal metadata (stored in the disk group header disks).

The AU size is set at disk group creation time using the AU_SIZE attribute and cannot be changed later without recreating the disk group. This makes the initial choice critical for long-running production systems.

-- Set AU size at creation (cannot change later)
CREATE DISKGROUP DATA NORMAL REDUNDANCY
DISK '/dev/sdb', '/dev/sdc', '/dev/sdd'
ATTRIBUTE 'AU_SIZE' = '4M';
-- Verify AU size
SELECT name, allocation_unit_size/1024/1024 au_mb
FROM v$asm_diskgroup;

AU Size Options & Guidelines

AU Size Use Case Notes
1 MBOLTP, small random I/OSmaller metadata overhead
2 MBMixed workloadsRarely used
4 MB ★Default (12c+), most workloadsBest balance — use this
8 MBLarge sequential scansDW, analytics
16 MBVery large streamingUncommon
32 MBSequential mediaRare
64 MBVideo/large object streamingVery rare

Before 12c, the default was 1MB. From 12c onward, Oracle changed the default to 4MB for improved performance on modern storage.

Striping: Coarse vs Fine

ASM stripes every file across all disks in a disk group to distribute I/O load. The stripe width depends on the file type — Oracle automatically uses the correct stripe type based on the file template.

Coarse vs Fine Striping: Quick Comparison

Property Coarse Striping Fine Striping
Stripe Width 1 AU (e.g., 4MB) 128KB (always fixed)
Best For Large sequential I/O Small random I/O, latency-sensitive
File Types Datafiles, Tempfiles, Archive Logs, Backup Sets Redo Logs, Control Files, OCR, Voting Disk
Oracle Sets It Automatically via file template Automatically via file template
Why Large stripes minimize overhead for sequential workloads — fewer I/O operations per MB Tiny stripes ensure even distribution of tiny redo writes — reduces write latency
Can You Change? Yes — via custom template Yes — via custom template (rarely needed)

Key Insight

You never need to manually set striping. ASM templates (see Section 4) automatically apply the correct stripe type for each file type. Fine striping for redo logs is critical because LGWR must commit transactions quickly — spreading 500KB writes across 32 disks in 128KB chunks means every disk gets a small, fast write instead of one disk getting a large sequential write.

Oracle Managed Files (OMF) + ASM

Oracle Managed Files (OMF) and ASM work together. When you set DB_CREATE_FILE_DEST to an ASM disk group, Oracle automatically creates, names, and manages all database files — no manual path specification needed.

-- Set OMF to use ASM disk group
ALTER SYSTEM SET
DB_CREATE_FILE_DEST = '+DATA';
-- Now just do this — Oracle picks name
CREATE TABLESPACE users;
-- Oracle creates in +DATA/ORCL/DATAFILE/
-- For redo logs
ALTER SYSTEM SET
DB_CREATE_ONLINE_LOG_DEST_1 = '+REDO';
-- For a SPFILE in ASM
CREATE SPFILE = '+DATA' FROM PFILE;

Best Practice

Always use OMF with ASM. Manual file naming is error-prone and creates maintenance burden. Let ASM manage the file namespace automatically.

Stores the control file. In RAC or NORMAL redundancy, ASM keeps two copies automatically (one per failure group).

Redo log members. Fine striped for low-latency LGWR writes. Always store multiplexed copies in a second disk group.

Archived redo logs organized by date. Coarse striped. Can be large; often stored in a separate RECO disk group.

ASM Templates: What They Are and Why They Matter

An ASM Template is a named set of properties (striping type + redundancy level) attached to a disk group. Every disk group ships with a default set of system templates — one for each file type Oracle creates. When a new file is written to ASM, ASM looks up the appropriate template and applies its settings automatically. This is how ASM "knows" to fine-stripe redo logs and coarse-stripe datafiles without you doing anything.

Section 5

Rebalancing Deep Dive

Rebalancing is ASM's ability to automatically redistribute data across disks when you add or remove storage — all online with zero downtime. Understanding how to control and monitor it is a key DBA skill.

Add Disk

ASM moves existing AU extents FROM old disks TO the new disk to equalize storage utilization across all members.

Remove Disk

ASM evacuates all extents FROM the disk being dropped TO remaining disks, then removes it from the group.

Disk Failure

If a disk fails beyond DISK_REPAIR_TIME, ASM drops it and rebalances, rebuilding mirror copies on remaining disks.

How ASM Rebalancing Works: Step by Step

1

Trigger — ADD or DROP DISK

A rebalance is triggered when you issue ALTER DISKGROUP ... ADD DISK or DROP DISK. It also triggers automatically when a disk exceeds its repair time after failure.

2

RBAL Plans the Work

The RBAL (ReBalance coordinator) background process calculates which AU extents need to move and to where. It creates a rebalance plan and divides work into parallel chunks.

3

Phase 1: Compact

ASM moves extents within disks to create contiguous free space. This reduces fragmentation inside existing disks before data moves across disks.

4

Phase 2: Relocate (ARBn workers)

ARB0, ARB1, ARB2... ARBn background processes perform the actual data movement. Each ARB worker handles a subset of extents. The POWER level controls how many ARB workers are spawned (1–1024). Higher POWER = more workers = faster rebalance = more I/O impact on production.

5

Phase 3: Flush

ASM flushes metadata changes to disk (updates extent maps, clears the free extent bitmap). After flush completes, the rebalance is committed — the disk group reflects the new layout.

POWER Level: Controlling Rebalance Speed

The POWER parameter (0–1024) controls how aggressively ASM rebalances. It maps directly to the number of ARBn worker processes spawned:

  • POWER 0 — rebalance paused (ASM queues the work but does nothing)
  • POWER 1 — minimal workers, minimal I/O impact, slowest
  • POWER 8 — default in most configs, good balance
  • POWER 1024 — maximum workers, fastest, maximum I/O impact

The default POWER for new disk groups is set by ASM_POWER_LIMIT init parameter (default = 1 in older releases, 8 from 11.2.0.4+, platform-dependent).

-- Check default power limit
SHOW PARAMETER asm_power_limit;
-- Change default at instance level
ALTER SYSTEM SET
ASM_POWER_LIMIT = 4;
-- Override for specific rebalance op
ALTER DISKGROUP DATA
REBALANCE POWER 11;
-- Add disk with explicit power
ALTER DISKGROUP DATA
ADD DISK '/dev/sde'
REBALANCE POWER 8;
-- Pause ongoing rebalance
ALTER DISKGROUP DATA
REBALANCE POWER 0;

FAST_MIRROR_RESYNC (11g+)

Introduced in 11g, Fast Mirror Resync dramatically speeds up recovery when a disk temporarily fails and comes back online. Without it, ASM would treat the returning disk as brand-new and copy ALL data back (full resync). With FAST_MIRROR_RESYNC, ASM tracks only the extents that changed during the outage using a stale extent bitmap — and only resyncs those.

-- Configure repair time (per disk group attribute)
ALTER DISKGROUP DATA
SET ATTRIBUTE 'DISK_REPAIR_TIME' = '12.0h';
-- For a whole failure group (18c+)
ALTER DISKGROUP DATA
SET ATTRIBUTE 'FAILGROUP_REPAIR_TIME' = '24.0h';
-- Check current setting
SELECT name, value FROM v$asm_attribute
WHERE name LIKE '%REPAIR%'
AND group_number =
(SELECT group_number FROM v$asm_diskgroup
WHERE name = 'DATA');
DISK_REPAIR_TIME: How long ASM waits for a missing disk to come back before dropping it. Default: 3.6h. Set longer for disks that take a while to recover (e.g., SAN path failover).
If disk returns within repair time: Only changed extents are resynced (fast). If it exceeds repair time: full drop + full rebalance of all data to remaining disks (slow).
Force drop immediately: ALTER DISKGROUP DATA DROP DISKS IN FAILGROUP FG1 FORCE — used when disk is permanently dead and you don't want to wait.

Common Rebalancing Scenarios & Commands

Add a new disk (capacity expansion)

ALTER DISKGROUP DATA
ADD FAILGROUP FG3 DISK '/dev/sdg'
NAME DATA_0007
REBALANCE POWER 8;

Remove a disk gracefully (planned)

ALTER DISKGROUP DATA
DROP DISK DATA_0007
REBALANCE POWER 11;
-- Wait for completion
SELECT est_minutes FROM v$asm_operation;

Undrop (cancel disk removal in progress)

ALTER DISKGROUP DATA
UNDROP DISKS;
-- Only works before drop completes

Speed up rebalance (off-hours maintenance)

ALTER DISKGROUP DATA
REBALANCE POWER 32;

Throttle rebalance (peak hours)

ALTER DISKGROUP DATA
REBALANCE POWER 2;
-- Pause completely during peak
ALTER DISKGROUP DATA
REBALANCE POWER 0;

Check disk group after rebalance

ALTER DISKGROUP DATA CHECK ALL;
-- View results in alert log
SELECT * FROM v$asm_operation
WHERE opera = 'CHECK';

Critical: Redundancy During Rebalance

During a rebalance (especially after a disk failure), your disk group may temporarily have reduced redundancy. For NORMAL redundancy, losing a second disk during this window can cause data loss. Monitor v$asm_diskgroup.state — it shows REBALANCING. Never add and drop disks simultaneously in an unplanned way. Always ensure enough surviving disks + failure groups before starting major disk operations.

Section 6

Disk Management, Discovery & States

Before ASM can use a disk, it needs to find it (discovery) and know it's available. Understanding ASM disk discovery mechanisms — ASMLIB vs ASMFD vs raw devices — is critical for storage troubleshooting.

ASM Disk Discovery: How ASM Finds Disks

ASM discovers candidate disks at instance startup and whenever you issue ALTER DISKGROUP ... ADD DISK. The ASM_DISKSTRING initialization parameter tells ASM where to look. If a disk isn't matched by ASM_DISKSTRING, ASM never sees it — it's invisible.

-- View current disk string
SHOW PARAMETER asm_diskstring;
-- Widen discovery at runtime (non-persistent)
ALTER SYSTEM SET
ASM_DISKSTRING = '/dev/sd*', 'ORCL:*'
SCOPE = MEMORY;
-- Persist across restarts
ALTER SYSTEM SET
ASM_DISKSTRING = '/dev/sd*'
SCOPE = BOTH;
-- Discover and list candidate disks
SELECT path, name, header_status, state
FROM v$asm_disk
ORDER BY group_number, disk_number;

Default ASM_DISKSTRING values by OS

  • Linux: /dev/oracleasm/disks/* (ASMLIB), /dev/sd* (raw)
  • AIX: /dev/rhdisk* (raw), ORCL:* (ASMLIB)
  • Solaris: /dev/rdsk/c*t*d*s6
  • HP-UX: /dev/rdisk/disk*
  • Windows: \\.\ORCLDISK* (ASMFD)

Performance Tip

Don't set ASM_DISKSTRING = '*' or very broad patterns — ASM must scan every matched device at startup. A narrow pattern (like /dev/asm/*) keeps startup fast by limiting the search scope.

Storage Interfaces: ASMLIB vs ASMFD vs Raw Devices

Raw Devices

Traditional approach
  • Works on all Linux/Unix versions — no extra software needed
  • Disk at OS path like /dev/sdb, /dev/mapper/mpathb
  • Permissions managed manually (chmod/chown to oracle/dba)
  • Disk names can change after reboot (udev rules required)
  • No protection against accidental overwrite by OS
# Prepare raw device
dd if=/dev/zero of=/dev/sdb bs=1M count=1
chown oracle:dba /dev/sdb
chmod 0660 /dev/sdb

ASMLIB

11g–18c era, Linux-focused
  • Kernel module (oracleasmlib): stamps disks with Oracle header — ASM "owns" the disk
  • Persistent names across reboots (/dev/oracleasm/disks/DISK1)
  • Managed via oracleasm CLI: createdisk, listdisks, deletedisk
  • Linux-only, requires kernel module install per kernel version upgrade
  • Deprecated in favor of ASMFD for new installs
# ASMLIB commands
oracleasm createdisk DISK1 /dev/sdb
oracleasm listdisks
oracleasm querydisk DISK1
oracleasm scandisks

ASMFD (Filter Driver)

★ Recommended (12.1+)
  • Kernel-level I/O filter that intercepts writes — rejects non-Oracle writes to ASM disks
  • Cross-platform (Linux, Windows, Solaris, AIX)
  • No external kernel module needed beyond Grid Infrastructure
  • Persistent names, simpler management via asmcmd afd_* commands
  • Protects against split-brain and accidental overwrites
# ASMFD via asmcmd
asmcmd afd_label DISK1 /dev/sdb
asmcmd afd_lslbl '/dev/sd*'
asmcmd afd_state
asmcmd afd_unlabel /dev/sdb

ASM Disk States Explained

Every disk ASM discovers has two state indicators: the MODE_STATUS (operational status) and the HEADER_STATUS (what ASM stamp is on the disk). Both are visible in v$asm_disk.

MODE_STATUS (Operational)

ONLINE Disk is mounted, active, and serving I/O. Normal state when everything is working.
SYNCING Disk returned after transient failure, undergoing FAST_MIRROR_RESYNC. Changed extents being replayed.
OFFLINE Disk is unreachable but still within DISK_REPAIR_TIME. ASM is tracking changed extents for fast resync.
DROPPING Disk is being removed. Extents are being evacuated. Cannot be cancelled by UNDROP once mostly done.
UNKNOWN Disk not accessible at all (I/O error). Check OS-level disk path and multipathing.

HEADER_STATUS (Disk Header)

MEMBER Disk belongs to a disk group. Has a valid ASM header with group membership info.
CANDIDATE Disk found by ASM discovery but not assigned to any group. Ready to be added. Safe to use.
PROVISIONED Like CANDIDATE but explicitly marked for ASM use (ASMLIB/ASMFD stamped). Not yet in a group.
FORMER Disk was previously in a group but was dropped. Header still has ASM stamp but group number is 0. Safe to reassign.
CONFLICT Disk has ASM header but from a different cluster. Indicates split-brain or incorrect disk added. Do NOT use.
UNKNOWN Cannot read header (I/O error) or blank header (new unformatted disk). Check disk health.

SELECT d.group_number, dg.name dg_name, d.disk_number,

d.reads, d.writes, d.read_errs, d.write_errs
FROM v$asm_disk d

Top ASM Interview Questions

Q: What is ASM and what problem does it solve?

ASM (Automatic Storage Management) is Oracle's built-in volume manager and filesystem designed specifically for Oracle database files. It solves three problems that existed before: (1) DBAs had to manually balance datafiles across disks for I/O distribution, (2) adding storage required complex manual file relocation, and (3) no built-in high availability for storage without OS-level LVM or expensive SAN features. ASM handles striping, mirroring, and rebalancing automatically.

Q: How is an ASM instance different from a DB instance?

The ASM instance has INSTANCE_TYPE=ASM in its SPFILE. It has NO SGA buffer cache (no data block caching), NO redo logs, and NO datafiles of its own. It's much more lightweight. Key background processes: RBAL (rebalance coordinator), ARBn (rebalance workers), GMON (group monitor), MARK (marks extents stale on offline disks), ASMB (connection bridge in the DB instance). The DB instance connects to the ASM instance via the ASMB background process.

Q: What is a Failure Group and why does it matter?

A Failure Group is a logical grouping of disks that share a common failure domain — for example, all disks on the same controller, same SAN port, or same RAID array. ASM ensures mirror copies of data are placed in different failure groups. If an entire failure group fails (controller dies), the other failure group(s) have complete copies. Without proper failure group planning — even with NORMAL redundancy — you can lose data if two "separate" disks are actually on the same failed controller.

Q: Can you change AU_SIZE after creating a disk group?

No. AU_SIZE is set at disk group creation and is permanently stored in the disk group header. It can never be changed without recreating the disk group. The default is 4MB since 12c (was 1MB before). Larger AU sizes benefit sequential workloads (DW/analytics); smaller sizes benefit OLTP with small random I/O. Choose carefully before creating production disk groups.

Q: What is Fast Mirror Resync and how does it work?

Fast Mirror Resync (11g+) is a feature where ASM tracks which AU extents were modified while a disk was offline (within DISK_REPAIR_TIME). When the disk comes back, instead of copying ALL data back (full resync), ASM only resyncs the changed extents — dramatically faster. The MARK background process maintains a "stale extent" bitmap. If the disk doesn't return within DISK_REPAIR_TIME, ASM drops it and does a full rebalance instead.

Q: What is the POWER parameter and what does POWER 0 do?

POWER (0–1024) controls the rebalance speed by determining how many ARBn background worker processes are spawned. POWER 0 pauses the rebalance — no workers run, but the operation remains queued. This is used to pause rebalance during peak hours without cancelling it. POWER 1 is slowest (minimum I/O impact). Higher values complete faster but consume more I/O bandwidth, potentially impacting production workloads.

Q: What is the difference between SYSASM and SYSDBA on an ASM instance?

SYSASM (introduced in 11g) is the dedicated ASM administrative privilege. It allows full ASM administration: create/drop disk groups, add/drop disks, manage templates, mount/dismount disk groups. SYSDBA on an ASM instance has limited capabilities — it can only start/stop the ASM instance and mount/dismount disk groups. It CANNOT create disk groups. Oracle strongly recommends using SYSASM for ASM DBA work and separating ASM admin (asmadmin group) from DB admin (dba group) responsibilities.

Q: What is the difference between COARSE and FINE striping?

COARSE striping uses 1 AU (e.g., 4MB) per stripe width — large chunks suitable for sequential I/O like datafiles and archive logs. FINE striping uses a fixed 128KB per stripe regardless of AU size — very small chunks that spread tiny writes across all disks, used for redo logs and control files where LGWR must commit quickly with low latency. Oracle applies the correct stripe type automatically via ASM templates — you never need to set this manually unless creating custom templates.
