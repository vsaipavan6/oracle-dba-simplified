Section 1

What Is a Tablespace?

A tablespace is Oracle's logical storage unit — it groups related database objects together. You assign tables, indexes, and other objects to tablespaces. Physically, a tablespace is made up of one or more datafiles on disk. This separation of logical and physical storage is what makes Oracle storage management so flexible.

Logical Layer

What the DBA sees and manages

  • Tablespace — the named container (e.g., USERS, SYSAUX)
  • Segment — all space for one object (one table = one segment)
  • Extent — a chunk of contiguous blocks allocated together
  • Data Block — the smallest unit Oracle reads/writes (8KB default)

Physical Layer

What lives on the operating system

  • Datafile — an actual .dbf file on disk, belongs to exactly one tablespace
  • One tablespace can have many datafiles (up to 1,022 for smallfile TS)
  • Datafiles can be on local disk, SAN, NFS, or Oracle ASM
  • Bigfile TS: exactly one datafile, up to 128TB (8KB blocks)

Interview Question: "What is the difference between a tablespace and a datafile?"

Answer: A tablespace is a logical storage unit visible to Oracle — you assign objects to tablespaces. A datafile is the physical OS file on disk. One tablespace can consist of multiple datafiles, but one datafile belongs to exactly one tablespace. This separation means you can add more space to a tablespace by simply adding another datafile — without touching application code or table definitions.

Section 2

The 5-Layer Storage Hierarchy

Oracle organizes storage in 5 layers — from the database itself down to individual 8KB data blocks. Every query, every row, every index entry ultimately lives inside a data block. Understanding this hierarchy is essential for every Oracle DBA interview.

Layer 1: Database

Top Level

The Oracle Database is the top-level container. One database instance manages all tablespaces. The physical database consists of: the data files (tablespace data), redo log files (change records for recovery), and the control file (database metadata — where everything is).

SELECT name, db_unique_name, open_mode, log_mode
FROM   V$DATABASE;

Layer 2: Tablespace

Logical Container

A tablespace is a logical grouping of storage. When you create a table, you tell Oracle which tablespace to store it in. The tablespace tracks which datafiles belong to it and manages how space is allocated from those files. Every database has at minimum: SYSTEM, SYSAUX, TEMP, and UNDO.

SELECT tablespace_name, contents, status, extent_management, segment_space_management
FROM   DBA_TABLESPACES
ORDER BY tablespace_name;

Layer 3: Segment

One per Object

A segment is all the storage space for a single database object. When you create a table, Oracle creates a table segment. When you create an index, Oracle creates an index segment. A segment grows by acquiring new extents from its tablespace. Segment types include: table segments, index segments, undo segments, temporary segments, and LOB segments.

SELECT segment_name, segment_type, tablespace_name,
       bytes/1024/1024 mb, extents, blocks
FROM   DBA_SEGMENTS
WHERE  owner = 'HR'
ORDER BY bytes DESC;

Layer 4: Extent

Allocation Unit

An extent is a contiguous set of data blocks. When a segment needs more space, Oracle allocates a new extent. Extents must be contiguous within a datafile — no gaps. With Locally Managed Tablespace AUTOALLOCATE (the default), Oracle automatically chooses the extent size, starting small and increasing as the segment grows. With UNIFORM SIZE, all extents are the same size you specify.

SELECT segment_name, extent_id, file_id, block_id, bytes, blocks
FROM   DBA_EXTENTS
WHERE  owner='HR' AND segment_name='EMPLOYEES'
ORDER BY extent_id;

Layer 5: Data Block

Smallest I/O Unit

The data block is the smallest unit Oracle reads from and writes to disk. Set by DB_BLOCK_SIZE at database creation — cannot be changed afterwards. Valid values: 2KB, 4KB, 8KB (default), 16KB, 32KB. Each block has a header (block address, type), table directory, row directory, and row data. Oracle's Buffer Cache in the SGA caches blocks in memory to avoid repeated disk I/O.

Section 3

Tablespace Types

Oracle has three types of tablespaces based on what they store, and Oracle ships with specific required tablespaces in every database. Knowing when to use each type is a key DBA interview topic.

PERMANENT

Default type

Stores persistent data — tables, indexes, views, procedures, and other permanent objects. Data survives instance restarts and crashes (backed by redo logs). Most tablespaces you create are permanent.

UNDO

One per instance

Stores undo data — the "before images" of changed rows. Enables ROLLBACK, read consistency (other sessions see data as it was before your transaction), and Flashback queries. Oracle recommends Automatic Undo Management (AUM).

TEMPORARY

Sort workspace

Stores temporary data for sort operations (ORDER BY, GROUP BY, DISTINCT, hash joins). Temporary segments are automatically released when the operation completes. All users share the same temp tablespace (default: TEMP). Temp tablespace uses temp files, not data files.

Smallfile vs Bigfile Tablespace

Smallfile Tablespace (Default)

  • Up to 1,022 datafiles per tablespace
  • Max datafile size: ~32GB (8KB blocks, 4M blocks × 8KB)
  • Each datafile managed individually (RESIZE, AUTOEXTEND)
  • Better for most environments — more flexibility
  • Can be spread across multiple mount points / disks
CREATE TABLESPACE app_data -- SMALLFILE is default DATAFILE '/data/app_data01.dbf' SIZE 1G;

Bigfile Tablespace (12c+)

  • Exactly ONE datafile per tablespace (always)
  • Max size: 128TB (8KB blocks), 32TB (2KB), 512TB (32KB)
  • Simpler management — ALTER TABLESPACE instead of ALTER DATABASE DATAFILE
  • Ideal for: Oracle ASM, large data warehouses, VLDB
  • Not suitable for raw devices on many platforms
CREATE BIGFILE TABLESPACE dw_data DATAFILE '+DATA/dw_data01.dbf' SIZE 10G AUTOEXTEND ON NEXT 10G MAXSIZE 100G;

Interview Question: "When would you use a Bigfile tablespace?" — Answer: When using Oracle ASM with very large data warehouses where you want simpler datafile management and can have a single, huge datafile. Not recommended for traditional file systems with smallfile-sized volume limits.

Section 4

CREATE TABLESPACE

The full CREATE TABLESPACE syntax with every important clause explained. Most of these options have intelligent defaults, but understanding each one lets you optimize storage for your specific workload.

CREATE [BIGFILE | SMALLFILE] TABLESPACE tablespace_name -- DATA FILE clause (for PERMANENT and UNDO tablespaces) DATAFILE '/path/to/file.dbf' SIZE size[K|M|G|T] [REUSE] -- reuse existing file [AUTOEXTEND {OFF | ON [NEXT size] [MAXSIZE {size | UNLIMITED}]}] [, '/path/to/file2.dbf' SIZE size ...] -- multiple datafiles -- EXTENT MANAGEMENT (how extents are tracked) EXTENT MANAGEMENT { LOCAL -- DEFAULT in 9i+: bitmap in tablespace header [AUTOALLOCATE -- DEFAULT: Oracle chooses extent size | UNIFORM [SIZE size]] -- all extents same size (default 1MB) | DICTIONARY -- legacy; deprecated in 12c+ } -- SEGMENT SPACE MANAGEMENT (how free blocks tracked inside a segment) SEGMENT SPACE MANAGEMENT { AUTO -- DEFAULT (ASSM): bitmap in segment header blocks | MANUAL -- freelist-based (legacy, not recommended) } -- TABLESPACE TYPE [DEFAULT STORAGE (...)] -- only for DICTIONARY managed (legacy) [ONLINE | OFFLINE] [LOGGING | NOLOGGING] -- LOGGING is default (redo generated) [FORCE LOGGING] -- override NOLOGGING for all operations [ENCRYPTION USING 'AES256'] -- Transparent Data Encryption (TDE) [DEFAULT COMPRESS FOR OLTP] -- Advanced Compression ;
Real-world CREATE TABLESPACE examples
-- 1. Standard application tablespace (best practice defaults)
CREATE TABLESPACE app_data
  DATAFILE '/oradata/ORCL/app_data01.dbf' SIZE 2G
           AUTOEXTEND ON NEXT 512M MAXSIZE 20G
  EXTENT MANAGEMENT LOCAL AUTOALLOCATE   -- Oracle picks extent sizes
  SEGMENT SPACE MANAGEMENT AUTO          -- ASSM (bitmap-based free block tracking)
  LOGGING;                               -- generate redo (data protection)

-- 2. Index tablespace (separate from data is a best practice)
CREATE TABLESPACE app_idx
  DATAFILE '/oradata/ORCL/app_idx01.dbf' SIZE 1G
           AUTOEXTEND ON NEXT 256M MAXSIZE 10G
  EXTENT MANAGEMENT LOCAL AUTOALLOCATE
  SEGMENT SPACE MANAGEMENT AUTO;

-- 3. UNDO tablespace (for AUM)
CREATE UNDO TABLESPACE undotbs2
  DATAFILE '/oradata/ORCL/undotbs02.dbf' SIZE 4G
           AUTOEXTEND ON NEXT 1G MAXSIZE 50G;

-- 4. TEMP tablespace (for sort operations)
--    Note: uses TEMPFILE not DATAFILE
CREATE TEMPORARY TABLESPACE temp2
  TEMPFILE '/oradata/ORCL/temp02.dbf' SIZE 2G
           AUTOEXTEND ON NEXT 512M MAXSIZE 10G
  EXTENT MANAGEMENT LOCAL UNIFORM SIZE 1M;  -- UNIFORM is best for TEMP

-- 5. Data Warehouse tablespace (NOLOGGING for bulk loads)
CREATE TABLESPACE dw_data
  DATAFILE '/oradata/ORCL/dw_data01.dbf' SIZE 10G
           AUTOEXTEND ON NEXT 2G MAXSIZE UNLIMITED
  EXTENT MANAGEMENT LOCAL AUTOALLOCATE
  SEGMENT SPACE MANAGEMENT AUTO
  NOLOGGING;  -- faster bulk inserts, but NO redo = not recoverable without rman

-- 6. Encrypted tablespace (TDE - Transparent Data Encryption)
CREATE TABLESPACE secure_data
  DATAFILE '/oradata/ORCL/secure01.dbf' SIZE 1G
  ENCRYPTION USING 'AES256'
  DEFAULT STORAGE(ENCRYPT)
  EXTENT MANAGEMENT LOCAL AUTOALLOCATE
  SEGMENT SPACE MANAGEMENT AUTO;
AUTOEXTEND ON NEXT size MAXSIZE Recommended

When the tablespace fills, Oracle automatically expands the datafile by NEXT bytes, up to MAXSIZE. Always set MAXSIZE — UNLIMITED can fill the entire filesystem and crash the host.

EXTENT MANAGEMENT LOCAL AUTOALLOCATE Default

Oracle picks extent sizes automatically — starts at 64KB for small segments, increases to 1MB, 8MB, then 64MB as the segment grows. Best for OLTP and mixed workloads.

EXTENT MANAGEMENT LOCAL UNIFORM SIZE For TEMP

All extents are the same fixed size. Best for temporary tablespaces (avoids fragmentation of sort space). Oracle recommends 1MB UNIFORM for TEMP. Less ideal for OLTP permanent tablespaces.

SEGMENT SPACE MANAGEMENT AUTO ASSM

Automatic Segment Space Management — uses bitmaps in the segment header to track which blocks have free space. Far better than MANUAL (freelist) for concurrent DML workloads. Default for locally managed tablespaces.

LOGGING vs NOLOGGING Performance

LOGGING (default) means all changes generate redo log entries for recovery. NOLOGGING skips redo for direct-path inserts — much faster for bulk loads, but the data cannot be media-recovered without a full backup first.

REUSE (datafile clause) Rare

If the datafile already exists, REUSE allows Oracle to overwrite it. Without REUSE, Oracle raises an error if the file exists. Used during database rebuild scenarios. Use with caution.

Section 5

Space Management Deep Dive

Space management in Oracle has two independent dimensions: how extents are tracked at the tablespace level (LMT vs DMT), and how free blocks are tracked within a segment (ASSM vs MANUAL). Both were redesigned in Oracle 9i and are now the standard approach.

Locally Managed Tablespace (LMT)

Default since Oracle 9i — use this always

  • Extent tracking uses a bitmap stored in the tablespace header — no data dictionary reads for extent allocation
  • Faster space allocation — no recursive SQL against SYS tables
  • No space fragmentation (bitmap recycles freed extents automatically)
  • No rollback segment contention during space allocation
  • All tablespaces created today are LMT by default

Dictionary Managed Tablespace (DMT)

Legacy — deprecated in Oracle 12c+

  • Extent tracking via SYS.FET$ and SYS.UET$ tables in SYSTEM tablespace
  • Every extent allocation = recursive SQL = contention on SYSTEM tablespace
  • Prone to space fragmentation (free extents not automatically reusable)
  • Required specifying INITIAL, NEXT, MINEXTENTS, MAXEXTENTS storage parameters
  • You may still see DMT in old databases — convert with DBMS_SPACE_ADMIN
Check tablespace extent management type
SELECT tablespace_name, extent_management, allocation_type
FROM   DBA_TABLESPACES
ORDER BY tablespace_name;

-- EXTENT_MANAGEMENT: LOCAL or DICTIONARY
-- ALLOCATION_TYPE: SYSTEM (AUTOALLOCATE) or UNIFORM

-- Convert DMT tablespace to LMT (run as SYSDBA)
EXEC DBMS_SPACE_ADMIN.TABLESPACE_MIGRATE_TO_LOCAL('OLD_DMT_TS');

Segment Space Management controls how Oracle tracks free blocks within a segment. ASSM (Automatic Segment Space Management) replaced the old freelist mechanism.

AUTOMATIC (ASSM)

Uses a bitmap block hierarchy (Level 1, Level 2, and Level 3 bitmap blocks — also called "BMBs") to track which data blocks in each segment have free space. The bitmap is stored in the first few blocks of each extent.

No contention under concurrent DML — each session uses different bitmap blocks
Eliminates "freelist contention" waits (db file sequential read on header)
Better space utilization — Oracle reclaims space from deleted rows automatically
Required for partitioned tables with compression
Default for all new LMT tablespaces — use this always

MANUAL (Freelist-based)

Uses a linked list of free blocks (freelist) maintained in the segment header. All sessions inserting into the segment compete for the same segment header block.

Freelist contention — heavy INSERT workloads create hot segment headers
FREELISTS and FREELIST GROUPS parameters need tuning
Required for SYSTEM tablespace (SYSTEM is MANUAL by default)
Required for IOTs (Index-Organized Tables) in some configurations
Deprecated — only use when Oracle requires it (SYSTEM tablespace)
Check segment space management type
SELECT tablespace_name, segment_space_management
FROM   DBA_TABLESPACES
ORDER BY tablespace_name;
-- SEGMENT_SPACE_MANAGEMENT: AUTO or MANUAL

-- SYSTEM is always MANUAL; all others should be AUTO

What Undo Does (3 Critical Functions)

ROLLBACK

When a transaction is rolled back, Oracle uses the before-image from undo to restore rows to their original state.

Read Consistency

If your query started at 3:00PM, you see the database AS IT WAS at 3:00PM — even if other sessions changed data since. Oracle rebuilds old images from undo.

Flashback

Flashback Query, Flashback Table, Flashback Database all depend on undo data being available for the lookback period.

Undo management commands
-- Check current undo tablespace and retention
SHOW PARAMETER undo_tablespace;
SHOW PARAMETER undo_retention;     -- seconds (default: 900 = 15 minutes)

-- How much undo space do you actually need?
-- Formula: Undo_space_bytes = undo_retention * undo_blocks_per_sec * block_size
SELECT (undoblks / ((end_time - begin_time) * 86400)) * 900 * 8192 / 1024 / 1024
         AS recommended_mb
FROM   V$UNDOSTAT
ORDER BY begin_time DESC
FETCH FIRST 1 ROW ONLY;

-- Switch to a new undo tablespace (online, without restart)
ALTER SYSTEM SET UNDO_TABLESPACE = 'UNDOTBS2';

-- Monitor undo space usage and tuning
SELECT begin_time, end_time, undoblks, txncount, maxquerylen, ssolderrcnt,
       nospaceerrcnt, activeblks, unexpiredblks, expiredblks
FROM   V$UNDOSTAT
ORDER BY begin_time DESC;
-- SSOLDERRCNT: ORA-01555 errors (snapshot too old) -- increase UNDO_RETENTION
-- NOSPACEERRCNT: ORA-30036 errors (undo full) -- increase undo tablespace size

-- Enable RETENTION GUARANTEE (prevent undo overwrite even if undo fills)
ALTER TABLESPACE undotbs1 RETENTION GUARANTEE;
-- WARNING: This can cause ORA-30036 if undo fills. Use only when Flashback critical.
ALTER TABLESPACE undotbs1 RETENTION NOGUARANTEE; -- back to default

Interview: "What is ORA-01555 Snapshot Too Old?"

Answer: ORA-01555 occurs when a query reads a data block and needs the old "before image" from undo to get read-consistent data, but that undo has already been overwritten by newer transactions. The fix is to either increase UNDO_RETENTION (keep undo longer), increase the undo tablespace size, or optimize the query to run faster so it needs less undo history.

Temporary tablespaces store sort data for SQL operations that cannot fit in the PGA (sort_area_size or pga_aggregate_target). Every user must have a default temporary tablespace.

What Uses Temp Space?

  • ORDER BY (when result set too large for PGA)
  • GROUP BY, DISTINCT, UNION
  • Hash joins and sort-merge joins
  • CREATE INDEX (build phase)
  • Analytic functions with large windows
  • Global Temporary Tables

Temp Tablespace Facts

  • Uses TEMPFILE, not DATAFILE
  • Not backed up (data is temporary — always recreatable)
  • Not protected by redo logs (no LOGGING option)
  • Temp segments auto-released when statement completes
  • Default allocation: UNIFORM SIZE 1M
Temp tablespace management
-- Who is using temp space right now?
SELECT s.username, s.sid, s.serial#, s.sql_id,
       t.blocks * 8192 / 1024 / 1024 AS mb_used,
       t.tablespace
FROM   V$SESSION s JOIN V$SORT_USAGE t ON s.saddr = t.session_addr
ORDER BY mb_used DESC;

-- Total temp tablespace usage vs free
SELECT tablespace_name,
       ROUND(tablespace_size * 8192 / 1024 / 1024, 0) AS total_mb,
       ROUND(free_space      * 8192 / 1024 / 1024, 0) AS free_mb,
       ROUND((tablespace_size - free_space) * 8192 / 1024 / 1024, 0) AS used_mb
FROM   V$TEMP_SPACE_HEADER;

-- Assign a default temp tablespace to a user
ALTER USER heavy_report_user TEMPORARY TABLESPACE temp_big;

-- Temp tablespace groups (12c+) — multiple temp tablespaces in a group
CREATE TEMPORARY TABLESPACE temp2
  TEMPFILE '/oradata/ORCL/temp02.dbf' SIZE 4G
  TABLESPACE GROUP temp_grp;
ALTER DATABASE DEFAULT TEMPORARY TABLESPACE temp_grp;

High Water Mark (HWM)

The High Water Mark is the highest block ever used in a segment. Oracle's full table scans read all blocks up to the HWM — even empty ones! If you delete 90% of rows from a table, the HWM doesn't move down. Full scans still read all the original blocks, making them slow.

HWM detection and segment shrink commands
-- Estimate how much space can be reclaimed by shrinking
SELECT segment_name, segment_type,
       bytes/1048576   AS allocated_mb,
       ROUND((bytes - DBMS_SPACE.SPACE_USAGE(:owner,:seg,:type)) / 1048576, 2) reclaimable_mb
FROM   DBA_SEGMENTS
WHERE  owner = 'HR';

-- Method 1: SHRINK SPACE (ASSM only, keeps segment in place, resets HWM)
-- Step 1: Enable row movement (allows Oracle to move rows to compact)
ALTER TABLE hr.employees ENABLE ROW MOVEMENT;
-- Step 2: Compact and lower HWM
ALTER TABLE hr.employees SHRINK SPACE CASCADE;  -- CASCADE shrinks indexes too
-- Step 3: Disable row movement
ALTER TABLE hr.employees DISABLE ROW MOVEMENT;

-- Method 2: MOVE (compacts but segment stays at same HWM until rebuild)
ALTER TABLE hr.employees MOVE TABLESPACE app_data;  -- also compacts
-- Note: MOVE invalidates all indexes — must rebuild!
ALTER INDEX hr.emp_pk REBUILD;

-- Method 3: DBMS_SPACE.SPACE_USAGE (check block fill levels)
SET SERVEROUTPUT ON
DECLARE
  unformatted_blocks NUMBER; unformatted_bytes NUMBER;
  fs1_blocks NUMBER; fs1_bytes NUMBER;
  fs2_blocks NUMBER; fs2_bytes NUMBER;
  fs3_blocks NUMBER; fs3_bytes NUMBER;
  fs4_blocks NUMBER; fs4_bytes NUMBER;
  full_blocks NUMBER; full_bytes NUMBER;
BEGIN
  DBMS_SPACE.SPACE_USAGE('HR','EMPLOYEES','TABLE',
    unformatted_blocks, unformatted_bytes,
    fs1_blocks, fs1_bytes, fs2_blocks, fs2_bytes,
    fs3_blocks, fs3_bytes, fs4_blocks, fs4_bytes,
    full_blocks, full_bytes);
  DBMS_OUTPUT.PUT_LINE('Full blocks: '    || full_blocks);
  DBMS_OUTPUT.PUT_LINE('75-100% full: '  || fs4_blocks);
  DBMS_OUTPUT.PUT_LINE('50-75% full: '   || fs3_blocks);
  DBMS_OUTPUT.PUT_LINE('Unformatted: '   || unformatted_blocks);
END;

Section 6

Tablespace Operations

Day-to-day DBA tasks — adding datafiles, resizing, monitoring, taking tablespaces offline, and dropping them. These commands are used constantly in production environments.

ALTER TABLESPACE — all essential operations
═══ ADDING SPACE ════════════════════════════════════════════════════

-- Add a new datafile to an existing tablespace
ALTER TABLESPACE app_data
  ADD DATAFILE '/oradata/ORCL/app_data02.dbf' SIZE 2G
  AUTOEXTEND ON NEXT 512M MAXSIZE 20G;

-- Resize an existing datafile (increase or decrease)
ALTER DATABASE
  DATAFILE '/oradata/ORCL/app_data01.dbf'
  RESIZE 4G;
-- Note: Cannot RESIZE below the High Water Mark

-- Change AUTOEXTEND settings on existing datafile
ALTER DATABASE
  DATAFILE '/oradata/ORCL/app_data01.dbf'
  AUTOEXTEND ON NEXT 1G MAXSIZE 30G;

-- For BIGFILE tablespace (ALTER TABLESPACE instead of ALTER DATABASE DATAFILE)
ALTER TABLESPACE dw_bigfile RESIZE 50G;
ALTER TABLESPACE dw_bigfile AUTOEXTEND ON NEXT 10G MAXSIZE 100G;

═══ AVAILABILITY ════════════════════════════════════════════════════

-- Take tablespace offline (maintenance, recovery)
ALTER TABLESPACE app_data OFFLINE;           -- normal (checkpoint first)
ALTER TABLESPACE app_data OFFLINE IMMEDIATE; -- no checkpoint (needs recovery)
ALTER TABLESPACE app_data OFFLINE TEMPORARY;-- checkpoint each datafile separately

-- Bring tablespace online
ALTER TABLESPACE app_data ONLINE;

-- Make tablespace READ ONLY (prevent writes, allow reads)
ALTER TABLESPACE archive_data READ ONLY;    -- useful for read-only reference data
ALTER TABLESPACE archive_data READ WRITE;   -- back to normal

═══ RENAMING ════════════════════════════════════════════════════════

-- Rename a tablespace (10g+)
ALTER TABLESPACE old_name RENAME TO new_name;
-- Note: Cannot rename SYSTEM or SYSAUX

-- Rename a datafile (when file has been moved at OS level)
ALTER TABLESPACE app_data
  RENAME DATAFILE '/old/path/app_data01.dbf'
  TO '/new/path/app_data01.dbf';

═══ DROPPING ════════════════════════════════════════════════════════

-- Drop an empty tablespace
DROP TABLESPACE old_app_ts;

-- Drop tablespace with all objects AND datafiles
DROP TABLESPACE old_app_ts
  INCLUDING CONTENTS AND DATAFILES
  CASCADE CONSTRAINTS;  -- removes FK constraints pointing to objects in this TS

Monitoring Tablespace Space

Space monitoring queries
-- 1. Tablespace usage summary (most important query for DBAs)
SELECT
  df.tablespace_name,
  ROUND(df.total_mb, 1)                             AS total_mb,
  ROUND(df.total_mb - NVL(fs.free_mb, 0), 1)        AS used_mb,
  ROUND(NVL(fs.free_mb, 0), 1)                      AS free_mb,
  ROUND((df.total_mb - NVL(fs.free_mb,0)) / df.total_mb * 100, 1) AS pct_used
FROM
  (SELECT tablespace_name, SUM(bytes/1048576) total_mb
   FROM DBA_DATA_FILES GROUP BY tablespace_name) df
  LEFT JOIN
  (SELECT tablespace_name, SUM(bytes/1048576) free_mb
   FROM DBA_FREE_SPACE  GROUP BY tablespace_name) fs
  ON df.tablespace_name = fs.tablespace_name
ORDER BY pct_used DESC;

-- 2. Including AUTOEXTEND headroom (what's actually available)
SELECT tablespace_name,
       ROUND(SUM(bytes)/1048576, 1)         AS current_mb,
       ROUND(SUM(maxbytes)/1048576, 1)       AS max_mb,
       ROUND(SUM(DECODE(autoextensible,'YES',maxbytes,bytes))/1048576,1) AS effective_max_mb
FROM   DBA_DATA_FILES
GROUP BY tablespace_name
ORDER BY tablespace_name;

-- 3. All datafiles for a tablespace
SELECT file_name, bytes/1048576 mb, autoextensible, maxbytes/1048576 max_mb, status
FROM   DBA_DATA_FILES
WHERE  tablespace_name = 'APP_DATA'
ORDER BY file_name;

-- 4. Temp tablespace usage
SELECT tablespace_name,
       ROUND(tablespace_size * 8192/1048576, 1) AS total_mb,
       ROUND(free_space      * 8192/1048576, 1) AS free_mb
FROM   V$TEMP_SPACE_HEADER;
Section 7

Real-Time Issues & Resolutions

These are the exact ORA errors you will encounter in production Oracle environments. Every DBA must know these cold — they are also top interview questions. Each error includes the root cause, how to detect it, and the exact commands to fix it.

Interview Tip: When asked about any ORA error, always answer in 3 parts: (1) what it means, (2) common causes, (3) resolution steps. This structure shows you know how to handle incidents, not just recognize error codes.

ORA-01653: unable to extend table SCHEMA.TABLE_NAME by 128 in tablespace APP_DATA

What Happened & Why

  • An INSERT, UPDATE, or the database's space allocator tried to allocate a new extent for a table segment
  • No contiguous free space available in the tablespace large enough for the new extent
  • Could be: tablespace truly full, AUTOEXTEND hit MAXSIZE limit, or AUTOEXTEND is OFF
  • Application sees an error and the DML statement is rolled back

Immediate Resolution Steps

1.Identify which tablespace is full and confirm the error
2.Add a new datafile (fastest fix — doesn't require restart)
3.OR resize existing datafile if filesystem has room
4.OR enable/increase AUTOEXTEND MAXSIZE if it was the limit
ORA-01653 Resolution commands
-- Step 1: Confirm which tablespace is full and by how much
SELECT df.tablespace_name,
       ROUND(SUM(df.bytes)/1048576,1) total_mb,
       ROUND(NVL(SUM(fs.bytes),0)/1048576,1) free_mb,
       ROUND((SUM(df.bytes)-NVL(SUM(fs.bytes),0))/SUM(df.bytes)*100,1) pct_used
FROM  DBA_DATA_FILES df
      LEFT JOIN DBA_FREE_SPACE fs ON df.tablespace_name=fs.tablespace_name
                                 AND df.file_id=fs.file_id
GROUP BY df.tablespace_name
HAVING NVL(SUM(fs.bytes),0)/SUM(df.bytes)*100 < 10  -- less than 10% free
ORDER BY pct_used DESC;

-- Step 2a: Add a new datafile (RECOMMENDED - fastest fix)
ALTER TABLESPACE app_data
  ADD DATAFILE '/oradata/ORCL/app_data02.dbf' SIZE 4G
  AUTOEXTEND ON NEXT 1G MAXSIZE 20G;

-- Step 2b: Resize an existing datafile (if filesystem has space)
ALTER DATABASE
  DATAFILE '/oradata/ORCL/app_data01.dbf'
  RESIZE 8G;

-- Step 2c: Increase AUTOEXTEND MAXSIZE if that was the bottleneck
ALTER DATABASE
  DATAFILE '/oradata/ORCL/app_data01.dbf'
  AUTOEXTEND ON NEXT 512M MAXSIZE 30G;

-- Long-term: Check AUTOEXTEND settings for all files in tablespace
SELECT file_name, bytes/1048576 mb, autoextensible, maxbytes/1048576 maxsize_mb
FROM   DBA_DATA_FILES
WHERE  tablespace_name = 'APP_DATA';

ORA-01652: unable to extend temp segment by 128 in tablespace TEMP

Root Cause

  • A sort, hash join, or GROUP BY operation used all available temp space
  • Often caused by large full-table scans being joined or sorted
  • Can occur when many users run reporting queries simultaneously
  • The failing SQL is identified in the error message by SQL_ID

Resolution Steps

1.Find who is using temp space and which SQL is causing it
2.Add tempfile or resize existing one for immediate relief
3.Long-term: optimize the SQL or increase PGA allocation
4.Consider a separate temp tablespace for heavy reporting users
ORA-01652 Resolution commands
-- Step 1: Find who is using temp space right now
SELECT s.username, s.sid, s.serial#, s.status, s.sql_id,
       ROUND(su.blocks * 8192 / 1048576, 1) AS temp_mb,
       su.tablespace
FROM   V$SESSION s JOIN V$SORT_USAGE su ON s.saddr = su.session_addr
ORDER BY temp_mb DESC;

-- Step 2: How full is TEMP right now?
SELECT tablespace_name,
       ROUND(tablespace_size * 8192/1048576,1) total_mb,
       ROUND(free_space * 8192/1048576,1) free_mb,
       ROUND((tablespace_size-free_space)*8192/1048576,1) used_mb
FROM   V$TEMP_SPACE_HEADER;

-- Step 3: Add a tempfile to TEMP tablespace (immediate fix)
ALTER TABLESPACE temp
  ADD TEMPFILE '/oradata/ORCL/temp02.dbf' SIZE 4G
  AUTOEXTEND ON NEXT 1G MAXSIZE 20G;

-- Step 4: For specific heavy users — assign dedicated temp tablespace
CREATE TEMPORARY TABLESPACE temp_reporting
  TEMPFILE '/oradata/ORCL/temp_rpt01.dbf' SIZE 8G
  AUTOEXTEND ON NEXT 2G MAXSIZE 40G
  EXTENT MANAGEMENT LOCAL UNIFORM SIZE 1M;
ALTER USER report_user TEMPORARY TABLESPACE temp_reporting;

-- Step 5: Check if the SQL can be optimized (look for huge sorts)
SELECT sql_id, elapsed_time/1000000 secs, disk_reads,
       direct_writes, buffer_gets, sql_text
FROM   V$SQL
WHERE  sql_id = '&sql_id';

ORA-01654: unable to extend index HR.EMP_PK by 128 in tablespace APP_IDX

This is the same root cause as ORA-01653 but for an index segment. Occurs during INSERT (index leaf block splits), during index creation, or REBUILD operations. Resolution is identical — add space to the index tablespace.

ORA-01654 Resolution
-- Add space to the index tablespace
ALTER TABLESPACE app_idx
  ADD DATAFILE '/oradata/ORCL/app_idx02.dbf' SIZE 2G
  AUTOEXTEND ON NEXT 512M MAXSIZE 10G;

-- Or: find and drop unused/duplicate indexes (review first!)
SELECT owner, index_name, table_name, last_analyzed,
       monitoring, used, start_monitoring
FROM   DBA_OBJECT_USAGE
WHERE  used = 'NO'
AND    owner = 'HR';

-- Or: rebuild index in a tablespace with more space
ALTER INDEX hr.emp_pk REBUILD TABLESPACE app_data;

ORA-30036: unable to extend segment by 8 in undo tablespace 'UNDOTBS1'

Root Cause Analysis

  • Undo tablespace is full — no more room for transaction undo data
  • Often caused by a very large or long-running transaction (mass UPDATE/DELETE)
  • Can happen if RETENTION GUARANTEE is on — unexpired undo cannot be overwritten
  • Check V$TRANSACTION for runaway transactions

Key Difference from ORA-01653

Unlike ORA-01653 which blocks only the failing session, ORA-30036 can affect ALL sessions trying to do DML on the database, since all transactions share the same undo tablespace. Treat this as a P1 incident.

ORA-30036 Resolution commands
-- Step 1: Check undo tablespace size and usage
SELECT tablespace_name, ROUND(SUM(bytes)/1048576,1) total_mb,
       ROUND(SUM(DECODE(autoextensible,'YES',maxbytes,bytes))/1048576,1) max_mb
FROM   DBA_DATA_FILES
WHERE  tablespace_name = 'UNDOTBS1'
GROUP BY tablespace_name;

-- Step 2: Find the large/runaway transaction causing the issue
SELECT s.username, s.sid, s.serial#, s.status,
       t.used_ublk * 8192/1048576 AS undo_mb_used,
       t.start_time, t.used_urec undo_records
FROM   V$TRANSACTION t JOIN V$SESSION s ON t.addr = s.taddr
ORDER BY undo_mb_used DESC;

-- Step 3: Immediate fix — add datafile to undo tablespace
ALTER TABLESPACE undotbs1
  ADD DATAFILE '/oradata/ORCL/undo02.dbf' SIZE 4G
  AUTOEXTEND ON NEXT 1G MAXSIZE 30G;

-- Step 4: If RETENTION GUARANTEE is blocking, disable it temporarily
ALTER TABLESPACE undotbs1 RETENTION NOGUARANTEE;

-- Step 5: Check V$UNDOSTAT for history (NOSPACEERRCNT column)
SELECT begin_time, end_time, txncount, maxquerylen,
       ssolderrcnt,    -- ORA-01555 count (undo too small for long queries)
       nospaceerrcnt,  -- ORA-30036 count (undo tablespace full)
       activeblks, unexpiredblks, expiredblks
FROM   V$UNDOSTAT
WHERE  nospaceerrcnt > 0
ORDER BY begin_time DESC;

ORA-01555: snapshot too old: rollback segment number 4 with name "_SYSSMU4_123456$" too small

A long-running query started reading data at time T1. By the time it revisited a block, the undo records needed to reconstruct the old image (read-consistent view at T1) had been overwritten by newer transactions. Oracle cannot reconstruct the consistent view and raises this error.

Common Causes

  • UNDO_RETENTION too low for the duration of long queries
  • Undo tablespace too small — unexpired undo being overwritten
  • Very active transaction system with high DML rate
  • Slow queries with table scans + heavy concurrent DML

Resolution

  • Increase UNDO_RETENTION (match to longest query duration)
  • Increase undo tablespace size so unexpired undo isn't overwritten
  • Enable RETENTION GUARANTEE (prevents overwrite, requires larger undo TS)
  • Optimize slow queries to finish faster (better execution plan)
ORA-01555 Resolution
-- Increase UNDO_RETENTION (unit: seconds)
ALTER SYSTEM SET UNDO_RETENTION = 3600;  -- 1 hour (was 900 = 15 min)

-- Check max query length in last 30 intervals (~5 hours)
SELECT MAX(maxquerylen) max_query_secs,
       MAX(ssolderrcnt) total_1555_errors
FROM   V$UNDOSTAT
WHERE  begin_time > SYSDATE - 1;
-- Set UNDO_RETENTION >= max_query_secs to prevent ORA-01555

-- Guarantee undo is never overwritten (requires sized undo TS)
ALTER TABLESPACE undotbs1 RETENTION GUARANTEE;

-- Calculate recommended undo size:
-- Undo_MB = UNDO_RETENTION * undo_blocks_per_sec * block_size / 1048576
SELECT ROUND(
         MAX(undoblks / ((end_time - begin_time) * 86400))  -- undo blocks/sec
         * 3600    -- target retention: 3600 seconds (1 hour)
         * 8192    -- block_size
         / 1048576 -- to MB
       , 0) recommended_undo_mb
FROM V$UNDOSTAT;

ORA-01658: unable to create INITIAL extent for segment in tablespace APP_DATA

This happens when you CREATE TABLE or CREATE INDEX and the tablespace cannot find a single contiguous run of free blocks large enough for the INITIAL extent. The tablespace may have lots of total free space but it's all fragmented into small pieces. This can happen in heavily used DMT tablespaces (LMT is immune because AUTOALLOCATE handles fragmentation automatically).

ORA-01658 Resolution
-- Step 1: Check largest contiguous free extent in the tablespace
SELECT tablespace_name,
       COUNT(*) fragment_count,
       MAX(bytes)/1048576 largest_free_mb,
       SUM(bytes)/1048576 total_free_mb
FROM   DBA_FREE_SPACE
WHERE  tablespace_name = 'APP_DATA'
GROUP BY tablespace_name;
-- If total_free_mb is large but largest_free_mb is small = fragmentation

-- Step 2a: Add a new datafile (provides fresh contiguous space)
ALTER TABLESPACE app_data
  ADD DATAFILE '/oradata/ORCL/app_data03.dbf' SIZE 2G;

-- Step 2b: LMT coalesces free space automatically — verify it's LMT
SELECT tablespace_name, extent_management FROM DBA_TABLESPACES
WHERE  tablespace_name = 'APP_DATA';
-- If DICTIONARY (DMT), coalesce manually:
ALTER TABLESPACE app_data COALESCE; -- merges adjacent free extents in DMT

ORA-01157: cannot identify/lock data file 7 - see DBWR trace file
ORA-01110: data file 7: '/oradata/ORCL/app_data01.dbf'

The datafile physically disappeared from the OS (deleted, moved, or filesystem unmounted). Oracle's DBWR process cannot access it. If the tablespace is not SYSTEM/SYSAUX/UNDO, you can take it offline and keep the rest of the database up while you restore from backup.

Datafile missing — emergency procedure
-- Step 1: Identify the missing file
SELECT file#, name, status FROM V$DATAFILE WHERE status != 'ONLINE';

-- Step 2a: If file was just moved — rename in Oracle's control file
ALTER TABLESPACE app_data
  RENAME DATAFILE '/old/path/app_data01.dbf'
  TO '/new/path/app_data01.dbf';

-- Step 2b: If file is lost — take tablespace offline for recovery
ALTER DATABASE DATAFILE 7 OFFLINE;   -- datafile offline

-- Step 3: Restore from RMAN backup
-- RMAN> RESTORE DATAFILE 7;
-- RMAN> RECOVER DATAFILE 7;
-- RMAN> SQL 'ALTER DATABASE DATAFILE 7 ONLINE';

-- Verify database is still up while recovery happens on that tablespace
SELECT status FROM V$INSTANCE; -- Should show OPEN

-- Check file status after fix
SELECT file#, name, status, enabled FROM V$DATAFILE
WHERE  file# = 7;
Section 8

Tablespace Best Practices

These are Oracle-recommended best practices from official documentation — the guidelines followed by senior DBAs at enterprise companies. Apply these from day one to avoid space issues, performance problems, and management headaches.

Storage Design

  • Always use Locally Managed Tablespaces (LMT) — default and required in 19c
  • Use SEGMENT SPACE MANAGEMENT AUTO (ASSM) for all user tablespaces — it's default and Oracle's explicit recommendation
  • Use AUTOALLOCATE for general purpose tablespaces; UNIFORM only for dedicated temp tablespaces
  • Create fewer, larger datafiles rather than many small ones — easier to manage
  • Separate data from indexes into different tablespaces for I/O distribution
  • Never store application data in SYSTEM or SYSAUX tablespaces

AUTOEXTEND Configuration

  • Enable AUTOEXTEND ON for critical tablespaces (app data, undo, temp)
  • Always set MAXSIZE — never use UNLIMITED in production (can fill filesystem)
  • Set NEXT to 10-20% of current size — avoid too-small increments that cause frequent extension
  • Monitor AUTOEXTEND events — each extension is a warning that capacity planning is needed
  • Alert when tablespace reaches 80% used — time to plan; alert at 90% for emergency action
  • Keep at least 30 days of headroom based on growth rate

Undo Tablespace

  • Use Automatic Undo Management (AUM) — default in 19c, never use manual rollback segments
  • Size undo tablespace based on UNDO_RETENTION × undo blocks per second query from V$UNDOSTAT
  • Enable AUTOEXTEND on undo to prevent ORA-30036 during peak activity
  • Only use RETENTION GUARANTEE when Flashback operations are critical — it can cause ORA-30036 if undo fills
  • Set UNDO_RETENTION to cover your longest running query duration

Temp Tablespace

  • Create temp tablespace with UNIFORM SIZE 1M (Oracle's recommendation for temp)
  • Use multiple temp tablespace groups (12c+) for high-concurrency reporting databases
  • Consider separate temp tablespace for heavy reporting users vs OLTP users
  • Temp tablespace doesn't need to be backed up — but must exist at startup
  • If temp fills up frequently → tune the SQL first, then increase temp size

Space Reclamation Rules

After Bulk DELETEs

Run SHRINK SPACE CASCADE on the table (ASSM required) to reclaim space and reset the HWM. This improves full-table scan performance significantly.

After TRUNCATE

TRUNCATE automatically resets the HWM and releases all extents back to the tablespace — no SHRINK needed. Preferred over DELETE for total data removal.

Table Reorganization

Use ALTER TABLE MOVE for tables you cannot shrink online (LONG columns, clustered). Remember to rebuild all indexes after MOVE — they become UNUSABLE.

Tablespace & Datafile Views

DBA_TABLESPACES

All tablespaces: CONTENTS (PERMANENT/TEMPORARY/UNDO), STATUS (ONLINE/OFFLINE/READ ONLY), EXTENT_MANAGEMENT (LOCAL/DICTIONARY), SEGMENT_SPACE_MANAGEMENT (AUTO/MANUAL), BLOCK_SIZE

Free extents in permanent tablespaces: TABLESPACE_NAME, FILE_ID, BLOCK_ID, BYTES (free extent size), BLOCKS. Used to calculate total free space and detect fragmentation (high row count = many small free fragments).

DBA_SEGMENTS

All segments: OWNER, SEGMENT_NAME, SEGMENT_TYPE (TABLE/INDEX/UNDO/TEMP/LOB/CLUSTER/etc.), TABLESPACE_NAME, BYTES (total allocated), BLOCKS, EXTENTS. Use to find space hogs.

DBA_EXTENTS

All extents: OWNER, SEGMENT_NAME, SEGMENT_TYPE, TABLESPACE_NAME, EXTENT_ID (sequence within segment), FILE_ID, BLOCK_ID (starting block), BYTES, BLOCKS

Dynamic views from control file. V$DATAFILE: FILE#, NAME, STATUS (OK/OFFLINE/ONLINE/RECOVER), BYTES, CHECKPOINT_CHANGE#. V$TABLESPACE: TS#, NAME, INCLUDED_IN_DATABASE_BACKUP

Active sort operations: USER, SESSION_ADDR (join to V$SESSION.SADDR), TABLESPACE, CONTENTS (SORT/LOB/etc.), BLOCKS (blocks used). Shows who is using temp space right now.

Top Interview Questions & Model Answers

Oracle organizes storage in 5 levels. At the top is the Database — the entire Oracle instance. Inside the database are Tablespaces — logical containers that group related objects. Tablespaces are physically made up of Datafiles on disk. Inside each tablespace are Segments — one per database object (one table = one segment, one index = one segment). Each segment is made up of Extents — contiguous sets of data blocks allocated together. And finally, Data Blocks are the smallest unit Oracle reads and writes — typically 8KB, set by DB_BLOCK_SIZE at database creation.

The High Water Mark is the highest block number ever used in a segment. Oracle's full table scans read ALL blocks up to the HWM, even empty ones. If you DELETE 90% of rows from a large table, the HWM stays at the original high point — full scans still read all those empty blocks, wasting I/O and memory in the buffer cache. To fix this: use ALTER TABLE ... SHRINK SPACE CASCADE (ASSM tablespaces only, requires ENABLE ROW MOVEMENT) to compact rows and reset the HWM, or use ALTER TABLE ... MOVE which also resets HWM but invalidates all indexes.

They operate at different levels. LMT (Locally Managed Tablespace) controls how extents are tracked at the tablespace level — using a bitmap stored in the tablespace header, so no data dictionary updates are needed for space allocation. The opposite is DMT (Dictionary Managed), now deprecated. ASSM (Automatic Segment Space Management) controls how free blocks within a segment are tracked — using bitmaps in the segment header blocks instead of the old freelist linked-list approach. ASSM eliminates freelist contention under concurrent inserts. Both are the default in Oracle 19c. You specify: EXTENT MANAGEMENT LOCAL for LMT and SEGMENT SPACE MANAGEMENT AUTO for ASSM.

Three options, all online with no downtime. Option 1 (preferred): Add a new datafile — ALTER TABLESPACE app_data ADD DATAFILE '/path/new.dbf' SIZE 4G AUTOEXTEND ON NEXT 1G MAXSIZE 30G;. This is immediate and the safest. Option 2: Resize an existing datafile (if the filesystem has space) — ALTER DATABASE DATAFILE '/path/existing.dbf' RESIZE 8G;. Option 3: Enable or increase AUTOEXTEND MAXSIZE — ALTER DATABASE DATAFILE '/path/file.dbf' AUTOEXTEND ON NEXT 512M MAXSIZE 30G;. All three are fully online with no impact on users.

Undo stores "before images" — the previous values of data rows before they were changed. It serves three purposes: 1. ROLLBACK — if a transaction is rolled back, Oracle uses undo to restore rows to their pre-change state. 2. Read Consistency — if your query started at 3PM, you see the database exactly as it was at 3PM, even if other sessions changed data since then. Oracle uses undo to reconstruct the old images. 3. Flashback — Flashback Query, Flashback Table, and related features use undo to show historical data. The undo retention period (UNDO_RETENTION parameter, default 900 seconds) controls how long undo is kept before it can be overwritten.

══════ DAILY HEALTH CHECK QUERIES ══════════════════════════════════

-- 1. Tablespace usage (% used — alert at 80%)
SELECT
  df.tablespace_name,
  ROUND(SUM(df.bytes)/1048576,1)                           total_mb,
  ROUND(SUM(df.bytes)-NVL(SUM(fs.bytes),0),0)/1048576    used_mb,
  ROUND(NVL(SUM(fs.bytes),0)/1048576,1)                    free_mb,
  ROUND((SUM(df.bytes)-NVL(SUM(fs.bytes),0))/SUM(df.bytes)*100,1) pct_used,
  ROUND(SUM(DECODE(df.autoextensible,'YES',df.maxbytes,df.bytes))/1048576,1) max_mb
FROM
  (SELECT tablespace_name, file_id, bytes, autoextensible, maxbytes FROM DBA_DATA_FILES) df
  LEFT JOIN
  (SELECT tablespace_name, file_id, SUM(bytes) bytes FROM DBA_FREE_SPACE GROUP BY tablespace_name, file_id) fs
  ON df.tablespace_name=fs.tablespace_name AND df.file_id=fs.file_id
GROUP BY df.tablespace_name
ORDER BY pct_used DESC;

-- 2. Top 10 largest segments in the database
SELECT owner, segment_name, segment_type, tablespace_name,
       ROUND(bytes/1048576,1) mb, extents
FROM   DBA_SEGMENTS
ORDER BY bytes DESC
FETCH FIRST 10 ROWS ONLY;

-- 3. Datafiles approaching MAXSIZE
SELECT tablespace_name, file_name,
       ROUND(bytes/1048576,1)    current_mb,
       ROUND(maxbytes/1048576,1) max_mb,
       ROUND(bytes/maxbytes*100,1) pct_of_max
FROM   DBA_DATA_FILES
WHERE  autoextensible = 'YES'
AND    maxbytes > 0
AND    bytes/maxbytes > 0.75  -- 75%+ of MAXSIZE used
ORDER BY pct_of_max DESC;

-- 4. Undo tuning health check
SELECT
  MAX(maxquerylen)    max_query_secs,
  (SELECT value FROM v$parameter WHERE name='undo_retention') undo_retention_secs,
  SUM(nospaceerrcnt)  total_30036_errors,
  SUM(ssolderrcnt)   total_01555_errors
FROM   V$UNDOSTAT
WHERE  begin_time > SYSDATE - 7; -- last 7 days

-- 5. Fragmentation check (high fragment_count = fragmented)
SELECT tablespace_name,
       COUNT(*) fragment_count,
       ROUND(MAX(bytes)/1048576,2) largest_free_mb,
       ROUND(SUM(bytes)/1048576,2) total_free_mb
FROM   DBA_FREE_SPACE
GROUP BY tablespace_name
HAVING COUNT(*) > 100    -- flag tablespaces with many free fragments
ORDER BY fragment_count DESC;

Tablespace Management — Interview Questions

Frequently asked tablespace and storage management questions in Oracle DBA interviews.

The SYSTEM tablespace stores Oracle's core data dictionary — the metadata that defines every object in the database (DBA_TABLES, DBA_USERS, DBA_INDEXES, etc.). It contains the SYS schema. It must always be online; if it goes down, the database cannot function.

The SYSAUX tablespace (introduced in 10g) is an auxiliary tablespace for Oracle's built-in components that used to crowd SYSTEM: AWR/STATSPACK, Enterprise Manager, LogMiner, Streams, XML DB, etc. Separating these keeps SYSTEM lean. If SYSAUX goes offline, the database continues running but features like AWR, ADDM, and other Oracle-managed tools stop working until it's brought back online.

Best practice: Never store application data in SYSTEM or SYSAUX. Monitor their growth — SYSAUX can grow unexpectedly if AWR retention is too high or Streams capture is left running unused.

Dictionary-Managed Tablespaces (DMT) are the legacy Oracle storage model (pre-9i). Free and used extents are tracked in data dictionary tables (UET$ and FET$). This requires recursive SQL for every extent allocation, causing contention on data dictionary tables and fragmentation issues. Deprecated since Oracle 10g.

Locally Managed Tablespaces (LMT) track extent allocation in a bitmap stored in each tablespace's own datafile header. No dictionary contention; self-managing; eliminates fragmentation when using UNIFORM or AUTOALLOCATE. LMT is the default and strongly preferred since Oracle 9i. All newly created tablespaces should be LMT.

Migration: Use DBMS_SPACE_ADMIN.TABLESPACE_MIGRATE_TO_LOCAL to convert DMT to LMT.

ASSM (Automatic Segment Space Management) uses a hierarchical bitmap structure within each data block to track free space at the row level within a block. Multiple processes can insert into different blocks simultaneously without contention — ideal for high-concurrency OLTP inserts. ASSM is the default since Oracle 10g.

MSSM (Manual Segment Space Management) uses Freelist structures — linked lists of blocks with free space. A single freelist per segment (or a configurable number with FREELISTS and FREELIST GROUPS) was the traditional approach. High concurrent inserts could cause freelist contention (wait event: "buffer busy waits").

Bottom line: Always create tablespaces with ASSM (SEGMENT SPACE MANAGEMENT AUTO) unless there's a specific reason to use MSSM (e.g., compatibility with very old Oracle versions).

The UNDO tablespace stores before-images of data changed by DML (INSERT, UPDATE, DELETE). It serves three critical purposes: (1) Transaction rollback — if you ROLLBACK, Oracle uses undo to restore original data; (2) Read consistency — long-running queries see a consistent snapshot of data as of their SCN, regardless of concurrent changes; (3) Flashback queries — AS OF TIMESTAMP queries use undo to reconstruct older data versions.

ORA-01555 ("snapshot too old") occurs when a query needs old undo data for read consistency, but that undo has already been overwritten by newer transactions. Causes: (1) UNDO tablespace too small; (2) UNDO_RETENTION set too low; (3) Very long-running queries. Fix: increase UNDO tablespace size, increase UNDO_RETENTION, or enable the RETENTION GUARANTEE option.

A bigfile tablespace consists of a single, very large datafile (up to 128TB with 32KB blocks). Traditional smallfile tablespaces contain up to 1022 datafiles of up to 32GB each.

Bigfile advantages: (1) Simple administration — one file per tablespace means simpler ALTER TABLESPACE RESIZE without specifying a datafile; (2) Better for ASM — larger files align better with ASM striping; (3) Supports full range SQL: ALTER TABLESPACE data RESIZE 10T. Bigfile disadvantages: RMAN recovery must restore the entire single large file (no partial file restore); parallel recovery is limited. Best for: Very large data warehouses on ASM or ASM-managed storage. For OLTP, smallfile is still preferred for recovery flexibility.
