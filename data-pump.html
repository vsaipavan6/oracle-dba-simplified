Section 1

What Is Oracle Data Pump?

Data Pump is a server-centric framework for high-speed export and import of Oracle database objects. Unlike the legacy exp/imp utilities, all processing happens inside the database server using the DBMS_DATAPUMP PL/SQL API.

Architecture: How a Data Pump Job Runs

↓

Shadow Process
Foreground process. Creates job infrastructure, AQ queues & Master Table. Relays commands between client and MCP.
Master Control Process (MCP)
One per job. Sequences metadata + data phases. Distributes work to Worker Processes. Updates Master Table.
Worker Processes (×N)
N workers = PARALLEL setting. Each loads/unloads via Direct Path API. Can spawn PQ slaves for partitioned tables.
Master Table — A real user table created in the operator's schema. Tracks every object's state, dump file offset, job parameters. Enables restart. Dropped automatically on success unless KEEP_MASTER=YES.

Server-Centric — Files Live on the Server

All Data Pump processing occurs inside the Oracle server. The expdp/impdp client is a thin shell that submits requests to DBMS_DATAPUMP. Dump files are written to the server's filesystem, not the client machine — which is why a Directory Object is mandatory.

Direct Path API — Why It's 10–100× Faster

Data Pump uses the Direct Path API to read/write data in native Oracle block format — bypassing SQL parsing, undo generation, and redo generation. Legacy exp read data with a conventional SQL SELECT row by row. Data Pump reads entire blocks. Combined with PARALLEL workers, the throughput difference is dramatic.

Job Restartability via Master Table

The Master Table tracks every object's export/import status. If a job fails at 80% — due to a crash, ORA error, or manual stop — you can resume from where it stopped. Attach with expdp ATTACH=job_name and issue START_JOB. Legacy exp had no equivalent: a failure meant starting from scratch.

DBMS_DATAPUMP — Full PL/SQL API

Everything expdp/impdp does, you can control programmatically via the DBMS_DATAPUMP PL/SQL package. Schedule exports in DBMS_SCHEDULER, add conditional logic, handle errors, loop over schemas — all without shell scripting. The expdp/impdp binaries are thin wrappers around this API.

Monitor running Data Pump jobs 
-- All active jobs
SELECT job_name, operation, job_mode, state, degree attached_sessions
FROM   dba_datapump_jobs
WHERE  state != 'NOT RUNNING'
ORDER BY job_name;

-- Real-time progress (tables transferred)
SELECT opname, target_desc, sofar, totalwork,
       ROUND(100*sofar/DECODE(totalwork,0,1,totalwork),2) pct_done,
       time_remaining
FROM   v$session_longops
WHERE  opname LIKE 'Data Pump%'
  AND  totalwork > 0
ORDER BY start_time DESC;

Interview Question: Why is Data Pump faster than exp/imp?

Answer: Data Pump uses the Direct Path API which reads and writes data in native Oracle block format — bypassing SQL layer parsing, undo generation, and redo logging for the data movement itself. Legacy exp used conventional SQL SELECT to fetch rows one by one. Additionally, Data Pump supports PARALLEL execution with multiple Worker Processes simultaneously processing different objects, whereas exp/imp was single-threaded. For large databases, this makes Data Pump 10–100× faster.

Section 3

Directory Objects — Required One-Time Setup

Data Pump requires a Directory Object — a database object mapping a logical name to a physical OS path on the server. All dump files and log files are read/written through directory objects.

Critical: OS Directory Must Exist BEFORE CREATE DIRECTORY

CREATE DIRECTORY only registers the logical name in the Oracle data dictionary — it does NOT create any folder on the OS. You must create the physical directory on the server first and ensure the oracle OS user has read/write permissions. If the folder doesn't exist, Data Pump will fail with ORA-39070.

1

Create the OS directory

On the server as root or oracle OS user:

mkdir -p /u01/datapump
chown oracle:oinstall /u01/datapump
chmod 750 /u01/datapump
2

Create the Directory Object in DB

Requires CREATE ANY DIRECTORY system privilege:

CREATE OR REPLACE DIRECTORY dpump_dir
  AS '/u01/datapump';
3

Grant READ and WRITE privileges

Grant to users who will run expdp / impdp:

GRANT READ, WRITE ON DIRECTORY dpump_dir
  TO myuser;

-- For full export/import, also grant roles:
GRANT datapump_exp_full_database TO myuser;
GRANT datapump_imp_full_database TO myuser;
4

Verify with DBA_DIRECTORIES

Confirm the directory is registered:

SELECT directory_name, directory_path
FROM   dba_directories
WHERE  directory_name = 'DPUMP_DIR';

-- Check privileges on the directory
SELECT grantee, privilege
FROM   dba_tab_privs
WHERE  table_name = 'DPUMP_DIR';

DATA_PUMP_DIR — The Default Directory Object

Oracle automatically creates a directory object named DATA_PUMP_DIR during database creation. Privileged users (SYSDBA/DBA role) can use it without specifying DIRECTORY — it's the default when none is specified. Its physical location:

Unix / Linux
$ORACLE_BASE/admin/$ORACLE_SID/dpdump/
Windows
%ORACLE_BASE%\admin\%ORACLE_SID%\dpdump\

Best practice: Never use DATA_PUMP_DIR for production jobs — the default location is usually on the OS drive with limited space. Create a dedicated directory on a separate disk or NFS mount. Also create separate directories per job type: DPUMP_FULL, DPUMP_SCHEMA, DPUMP_TABLE.

Section 4

Export with expdp — 5 Modes

Data Pump export supports 5 different modes depending on scope — from a full database down to selected tables. Choose the mode that matches what you need to move.

FULL=Y

Full Database Export

Exports the entire database — all schemas, all objects, all data. Requires the DATAPUMP_EXP_FULL_DATABASE role. Used for full database migration or point-in-time backup.

Includes

  • All schemas and their objects
  • System grants and roles
  • User definitions and profiles
  • All table data
  • Database links and synonyms

Excludes (by default)

  • SYS / SYSTEM schema objects
  • Passwords (stored separately)
  • BFILE actual files on disk
Full database export
expdp system/password@ORCL \
  DIRECTORY=dpump_dir \
  DUMPFILE=fulldb_%U.dmp \
  LOGFILE=full_exp.log \
  FULL=Y \
  PARALLEL=8 \
  COMPRESSION=ALL \
  FILESIZE=10G

-- With consistent point-in-time export:
expdp system/password@ORCL FULL=Y \
  FLASHBACK_TIME="TO_TIMESTAMP('2025-05-01 02:00:00','YYYY-MM-DD HH24:MI:SS')" \
  DIRECTORY=dpump_dir DUMPFILE=full_pit.dmp LOGFILE=full_pit.log
SCHEMAS=

Schema Export (Default Mode)

Exports one or more complete schemas. This is the default mode when no mode parameter is specified. Includes all objects owned by the schema: tables, indexes, triggers, sequences, packages, views, constraints, grants.

Most common mode for DEV/TEST refresh — export PROD schema, import with REMAP_SCHEMA to DEV. No full database access required.

Schema export examples
-- Single schema export
expdp hr/password@ORCL \
  DIRECTORY=dpump_dir DUMPFILE=hr_%U.dmp \
  LOGFILE=hr_exp.log SCHEMAS=HR \
  PARALLEL=4

-- Multiple schemas in one dump
expdp system/password@ORCL \
  SCHEMAS=HR,SALES,FINANCE \
  DIRECTORY=dpump_dir DUMPFILE=app_schemas_%U.dmp \
  LOGFILE=app_exp.log PARALLEL=4

-- Schema export excluding indexes + stats (faster; rebuild on import)
expdp hr/password@ORCL SCHEMAS=HR \
  EXCLUDE=INDEX,STATISTICS \
  DIRECTORY=dpump_dir DUMPFILE=hr_noindex.dmp LOGFILE=hr_noindex.log
TABLES=

Table-Level Export

Exports specific tables and their dependent objects (indexes, constraints, triggers, grants on those tables). Use the QUERY parameter to filter rows from specific tables.

Table-level export examples
-- Export specific tables
expdp hr/password@ORCL \
  TABLES=HR.EMPLOYEES,HR.DEPARTMENTS,HR.JOBS \
  DIRECTORY=dpump_dir DUMPFILE=hr_tables.dmp LOGFILE=hr_tables.log

-- Export with row filter (QUERY) — subset of data
expdp hr/password@ORCL \
  TABLES=HR.EMPLOYEES \
  QUERY=HR.EMPLOYEES:"WHERE department_id IN (10,20,30)" \
  DIRECTORY=dpump_dir DUMPFILE=emp_subset.dmp LOGFILE=emp_subset.log

-- Estimate size before export (dry run)
expdp hr/password@ORCL TABLES=HR.ORDER_ITEMS \
  ESTIMATE_ONLY=Y DIRECTORY=dpump_dir LOGFILE=estimate.log
TABLESPACES=

Tablespace-Level Export

Exports all tables (and their dependent objects) whose data segments reside in the specified tablespaces. If a table is included, all its indexes and constraints are also included — even if those segments are in other tablespaces.

Tablespace export
-- Export all objects in APP_DATA and APP_IDX tablespaces
expdp system/password@ORCL \
  TABLESPACES=APP_DATA,APP_IDX \
  DIRECTORY=dpump_dir DUMPFILE=app_tbs.dmp \
  LOGFILE=app_tbs.log PARALLEL=4

-- Note: data AND metadata are exported (unlike TRANSPORT_TABLESPACES)
-- Use this when you want table data in the dump file
TRANSPORT_TABLESPACES=

Transportable Tablespace Export

Exports metadata only — the actual data blocks are moved by copying the datafiles directly. This is the fastest method for large tablespaces because Oracle doesn't read and write individual rows; it just copies raw datafiles. The tablespace must be placed READ ONLY before export (or use TTS_CLOSURE_CHECK=TEST_MODE in 19c+).

Advantages

  • ✔ Fastest for large tablespaces (TB-scale in minutes)
  • ✔ Only metadata in dump file (tiny dump)
  • ✔ Works across platforms (with CONVERT step for endianness)

Requirements

  • ⚠ Tablespace must be READ ONLY (or TEST_MODE in 19c)
  • ⚠ Must pass TRANSPORT_FULL_CHECK self-containment
  • ⚠ Manual datafile copy step required
Transportable Tablespace workflow
-- Step 1: Make tablespace READ ONLY on source
ALTER TABLESPACE app_data READ ONLY;

-- Step 2: Export metadata only
expdp system/password@SOURCE \
  TRANSPORT_TABLESPACES=app_data \
  TRANSPORT_FULL_CHECK=Y \
  DIRECTORY=dpump_dir DUMPFILE=tts_meta.dmp LOGFILE=tts_exp.log

-- Step 3: Copy datafiles to target server (OS level)
scp /u01/oradata/ORCL/app_data01.dbf oracle@target:/u01/oradata/ORCL/

-- Step 4: Import metadata on target (plugs in the datafiles)
impdp system/password@TARGET \
  TRANSPORT_TABLESPACES=app_data \
  DATAFILES='/u01/oradata/ORCL/app_data01.dbf' \
  DIRECTORY=dpump_dir DUMPFILE=tts_meta.dmp LOGFILE=tts_imp.log

-- Step 5: Return source tablespace to READ WRITE
ALTER TABLESPACE app_data READ WRITE;
%U Substitution

Use DUMPFILE=file_%U.dmp to split across multiple files. Oracle replaces %U with 01, 02, 03, etc. Required when PARALLEL > 1 — each worker needs its own file to write to simultaneously.

ESTIMATE_ONLY=Y

Run a dry-run to estimate dump file size without actually exporting. Useful for disk space planning before a large export. Does NOT account for COMPRESSION — run the estimate then apply a compression ratio factor.

CONTENT= Filter

CONTENT=ALL (default), METADATA_ONLY (schema only, no rows), DATA_ONLY (rows only, no DDL). METADATA_ONLY is ideal for documenting schema design or cloning a schema structure.

Section 5

Import with impdp — Key Parameters

impdp is the import counterpart to expdp. It reads a dump file set and recreates objects and data. The most powerful features are the REMAP parameters and TABLE_EXISTS_ACTION.

TABLE_EXISTS_ACTION — What to do if the table already exists

This is one of the most critical import parameters. It controls behavior when impdp finds a table in the target database that already exists:

Value Action DDL Loaded? Data Loaded? When to Use
SKIP Skip the table entirely — do nothing No No Only import objects that don't already exist
APPEND Insert new rows; keep existing rows No Yes (adds) Merge data without deleting existing records
TRUNCATE DELETE existing rows, then insert dump rows No Yes (replaces data) Refresh data but keep existing table structure
REPLACE DROP and recreate table, then insert all rows Yes Yes (full refresh) Complete table rebuild — DEV/TEST refresh 
-- DEV refresh: drop-and-replace everything
impdp system/password@DEVDB DUMPFILE=prod_hr.dmp DIRECTORY=dpump_dir \
  REMAP_SCHEMA=HR:HR_DEV TABLE_EXISTS_ACTION=REPLACE

-- Append mode: add missing rows without touching existing data
impdp system/password@DEVDB DUMPFILE=delta.dmp DIRECTORY=dpump_dir \
  TABLE_EXISTS_ACTION=APPEND

REMAP Parameters — Transform on Import

REMAP_SCHEMA

Redirects all objects from source schema into a different target schema. Target schema does not need to pre-exist — impdp creates it.

-- Import PROD schema into DEV schema
impdp ... REMAP_SCHEMA=PROD_HR:DEV_HR

-- Multiple remaps in one job
impdp ... REMAP_SCHEMA=SALES:SALES_TEST \
         REMAP_SCHEMA=FINANCE:FINANCE_TEST
REMAP_TABLESPACE

Remaps all objects from source tablespace to target tablespace during import. Essential when target database has different tablespace names or when consolidating storage.

-- Remap PROD_DATA → DEV_DATA, PROD_IDX → DEV_IDX
impdp ... REMAP_TABLESPACE=PROD_DATA:DEV_DATA \
         REMAP_TABLESPACE=PROD_IDX:DEV_IDX

-- Consolidate multiple tablespaces into one
impdp ... REMAP_TABLESPACE=TS1:USERS \
         REMAP_TABLESPACE=TS2:USERS
REMAP_DATAFILE

Redefines datafile path references in all DDL statements. Used during transportable tablespace imports when the physical file locations differ between source and target servers.

-- Remap datafile path for transportable import
impdp ... \
  REMAP_DATAFILE='/old/path/app_data01.dbf':'/new/path/app_data01.dbf'
TRANSFORM

Applies transformations to DDL statements. The most useful is DISABLE_ARCHIVE_LOGGING:Y which sets NOLOGGING before import and LOGGING after — dramatically reduces redo generation for large data loads.

-- Reduce redo during bulk import
impdp ... TRANSFORM=DISABLE_ARCHIVE_LOGGING:Y

-- Apply only to tables (not indexes)
impdp ... TRANSFORM=DISABLE_ARCHIVE_LOGGING:Y:TABLE

NETWORK_LINK — Import Without Dump Files

No Disk Space Needed

The NETWORK_LINK parameter performs a direct database-to-database import over a database link — no dump files required. Data flows directly from source to target. A directory object is still required for the log file.

-- Step 1: Create DB link from target pointing to source
CREATE DATABASE LINK source_prod
  CONNECT TO system IDENTIFIED BY password
  USING 'PROD_TNS_ALIAS';

-- Step 2: Import directly from source into target (no dump file)
impdp system/password@DEVDB \
  NETWORK_LINK=source_prod \
  SCHEMAS=HR \
  REMAP_SCHEMA=HR:HR_DEV \
  REMAP_TABLESPACE=PROD_DATA:DEV_DATA \
  DIRECTORY=dpump_dir LOGFILE=net_imp.log \
  TABLE_EXISTS_ACTION=REPLACE PARALLEL=4
Section 6

Key Parameters Reference

Master these parameters to control performance, security, filtering, and consistency for both expdp and impdp jobs.

PARALLEL=N Enterprise Ed. only

Number of Worker Processes. Default is 1 (no parallelism). Requires Oracle Enterprise Edition for N > 1. Recommended: set to 1.5× to 2× the number of CPUs. Must use DUMPFILE=file%U.dmp when PARALLEL > 1 so each worker has its own file.

-- 8-core system: use 12 workers
expdp ... PARALLEL=12 DUMPFILE=exp_%U.dmp

-- Change PARALLEL dynamically in interactive mode
Export> PARALLEL=16
COMPRESSION= Advanced Compression option

Compresses dump file contents. Requires the Advanced Compression option license. Values: NONE (default), METADATA_ONLY, DATA_ONLY, ALL. METADATA_ONLY is free for Standard Edition. DATA_ONLY and ALL require the license.

-- Maximum compression (smallest dump)
expdp ... COMPRESSION=ALL

-- Free: only compress metadata
expdp ... COMPRESSION=METADATA_ONLY

-- Set compression algorithm (12.1+)
expdp ... COMPRESSION=ALL \
         COMPRESSION_ALGORITHM=HIGH
FILESIZE=

Maximum size of each dump file. When a file reaches this size, Oracle automatically starts the next file (using %U substitution). Useful for keeping files below filesystem or storage limits.

-- Split into 10GB files
expdp ... FILESIZE=10G DUMPFILE=full_%U.dmp
EXCLUDE=STATISTICS Always use on import

Skips loading optimizer statistics during import. Dramatically speeds up imports. Statistics can be gathered post-import with DBMS_STATS.GATHER_SCHEMA_STATS. A best practice for all DEV/TEST imports.

impdp ... EXCLUDE=STATISTICS

-- Gather stats after import
EXEC DBMS_STATS.GATHER_SCHEMA_STATS('HR_DEV');
ENCRYPTION=

What to encrypt in the dump file. Values: NONE, METADATA_ONLY, DATA_ONLY, ENCRYPTED_COLUMNS_ONLY, ALL. Use ALL for compliance scenarios (HIPAA, PCI-DSS, SOX).

-- Full encryption with AES-256
expdp ... \
  ENCRYPTION=ALL \
  ENCRYPTION_ALGORITHM=AES256 \
  ENCRYPTION_PASSWORD=SecurePass123! \
  ENCRYPTION_MODE=PASSWORD

-- Import encrypted dump
impdp ... \
  ENCRYPTION_PASSWORD=SecurePass123!
ENCRYPTION_ALGORITHM=

Encryption algorithm. Valid values: AES128 (default), AES192, AES256. AES256 provides the strongest encryption — required for most compliance frameworks. Higher bit count = slightly more CPU overhead.

ENCRYPTION_MODE values:
PASSWORD — only accessible with password
DUAL — accessible with password OR Oracle Encryption Wallet
TRANSPARENT — uses wallet only (no password needed at export)

Security Roles Required

DATAPUMP_EXP_FULL_DATABASE

Required for privileged exports: FULL=Y, other schemas, SYS-owned objects. Also required as source user for NETWORK_LINK exports. Supersedes the deprecated EXP_FULL_DATABASE role.

DATAPUMP_IMP_FULL_DATABASE

Required for privileged imports: FULL=Y, REMAP_SCHEMA to different schema, NETWORK_LINK imports. Supersedes the deprecated IMP_FULL_DATABASE role.

INCLUDE=

Include only specified object types. When INCLUDE is specified, nothing else is included. Syntax: INCLUDE=object_type[:name_clause]. INCLUDE and EXCLUDE are mutually exclusive (before 21c).

-- Include only tables and their indexes
expdp ... INCLUDE=TABLE,INDEX

-- Include only tables matching a pattern
expdp ... INCLUDE=TABLE:"LIKE 'ORDER%'"

-- Include specific procedures
expdp ... INCLUDE=PROCEDURE:"IN ('CALC_SALARY','SEND_MAIL')"
EXCLUDE=

Exclude specified object types from the export/import. When an object type is excluded, all its dependents are also excluded (e.g., excluding TABLE also excludes its indexes and triggers).

-- Skip indexes and triggers (rebuild on target)
expdp ... EXCLUDE=INDEX,TRIGGER

-- Skip specific table by name
expdp ... EXCLUDE=TABLE:"= 'AUDIT_LOG'"

-- Skip stats + grants on import
impdp ... EXCLUDE=STATISTICS,GRANT
CONTENT=

Controls what is included: ALL (default — metadata + data), METADATA_ONLY (DDL only, no rows — great for schema cloning), DATA_ONLY (rows only, schema must already exist on target).

-- Schema definition only (no data)
expdp ... CONTENT=METADATA_ONLY

-- Data only (schema already on target)
expdp ... CONTENT=DATA_ONLY
QUERY=

Filters rows from a specific table using a WHERE clause during export. Only that table gets filtered — other tables in the same job export fully. Cannot be combined with ESTIMATE_ONLY.

-- Export only active employees
expdp ... TABLES=EMPLOYEES \
  QUERY=EMPLOYEES:"WHERE status = 'ACTIVE'"

-- Multiple tables, different filters each
expdp ... TABLES=ORDERS,CUSTOMERS \
  QUERY=ORDERS:"WHERE order_date > DATE '2024-01-01'"
FLASHBACK_SCN=

Exports data as it existed at the specified System Change Number. Guarantees all tables in the export are consistent as of that SCN — crucial for large exports that span multiple tablespaces. Get current SCN with SELECT CURRENT_SCN FROM V$DATABASE.

-- Get SCN first
SELECT current_scn FROM v$database;
-- Output: 12345678

-- Export consistent as of that SCN
expdp ... FLASHBACK_SCN=12345678
FLASHBACK_TIME=

Exports data as it existed at the specified timestamp. Oracle resolves the timestamp to the nearest SCN. Mutually exclusive with FLASHBACK_SCN. Useful when you know a specific point-in-time but not the exact SCN.

-- Consistent export as of 2am today
expdp ... \
  FLASHBACK_TIME="TO_TIMESTAMP('2025-05-17 02:00:00',
    'YYYY-MM-DD HH24:MI:SS')"
VERSION=

Generates a dump file compatible with an older Oracle version. Use this when exporting from Oracle 19c to import into 12c. Oracle removes features not supported in the target version. Example: VERSION=12.1 on a 19c source.

-- Downgrade export: 19c → 12.1 compatible
expdp ... VERSION=12.1
CLUSTER= RAC only

For RAC environments. CLUSTER=Y (default) distributes Worker Processes across all RAC instances for maximum parallelism. CLUSTER=N forces all workers to run on the instance where the job was submitted — useful for debugging or I/O-constrained environments.

-- Force single-node in RAC (for debugging)
expdp ... CLUSTER=N
JOB_NAME=

Assigns a custom name to the Data Pump job. This name is used with ATTACH to reconnect, appears in DBA_DATAPUMP_JOBS, and is the Master Table name. If omitted, Oracle auto-generates a name like EXPORT_1. Choose meaningful names for easy monitoring.

expdp ... JOB_NAME=PROD_HR_EXPORT_20250517

-- Later: reattach to this job
expdp system/password@ORCL \
  ATTACH=PROD_HR_EXPORT_20250517
STATUS=N

Sets the frequency (in seconds) of status messages shown to the client. Default is 0 (only major milestones). Set to 60 to get a progress update every minute — useful for monitoring long-running jobs without entering interactive mode.

-- Report progress every 30 seconds
expdp ... STATUS=30
KEEP_MASTER=

By default KEEP_MASTER=NO — the Master Table is dropped after a successful job. Set to YES to retain it for debugging or if you need to re-run the job. The Master Table is always retained for failed or stopped jobs.

-- Retain master table after success
expdp ... KEEP_MASTER=YES

-- Drop orphaned master tables
DROP TABLE system.SYS_EXPORT_SCHEMA_01;
ATTACH= / Interactive Mode

Reconnect to a running or stopped job. After attaching, you enter interactive mode. Also triggered automatically by pressing Ctrl+C during a running job. In interactive mode you can monitor, control parallelism, add files, stop, or kill the job.

-- Attach to running job
expdp system/password@ORCL ATTACH=MYJOB

-- Interactive prompt appears:
Export> STATUS
Export> PARALLEL=8
Export> STOP_JOB
Export> START_JOB
Export> KILL_JOB
Section 7

Interactive Mode & DBMS_DATAPUMP API

Press Ctrl+C during any running expdp/impdp job to enter interactive mode. The job keeps running in the background — you get a prompt to monitor or control it.

Interactive Mode Commands

Command Description Recoverable?
STATUS [=seconds] Display current job status, tables processed, rows transferred, worker states, estimated completion —
CONTINUE_CLIENT Exit interactive mode; return to logging output. If the job was stopped, this also restarts it —
PARALLEL=N Dynamically change the number of Worker Processes. Increase to speed up, decrease to reduce load. Requires Enterprise Edition —
ADD_FILE=file.dmp Add a new dump file to the job's dump file set. Use when a file fills up and FILESIZE was not pre-set —
STOP_JOB [=IMMEDIATE] Gracefully stop the job (finish current object). STOP_JOB=IMMEDIATE stops all workers immediately. Master Table is preserved — job can be restarted Yes — restartable
START_JOB [=SKIP_CURRENT] Restart a stopped job from where it left off. SKIP_CURRENT skips the object that was in progress when the job stopped —
KILL_JOB DESTRUCTIVE — terminates the job immediately and drops the Master Table. The job CANNOT be restarted. Any partial dump files may be incomplete NOT restartable

DBMS_DATAPUMP — The PL/SQL API

The expdp/impdp utilities are thin wrappers. Everything they do is available through the DBMS_DATAPUMP PL/SQL package — enabling scheduled, conditional, or integrated export/import from within stored procedures or DBMS_SCHEDULER jobs.

DBMS_DATAPUMP — schema export via PL/SQL
DECLARE
  h1  NUMBER;
BEGIN
  -- Open export job
  h1 := DBMS_DATAPUMP.OPEN(
          operation => 'EXPORT',
          job_mode  => 'SCHEMA',
          job_name  => 'MY_API_EXPORT');

  -- Add dump file and log file
  DBMS_DATAPUMP.ADD_FILE(h1, 'api_exp.dmp', 'DPUMP_DIR');
  DBMS_DATAPUMP.ADD_FILE(h1, 'api_exp.log', 'DPUMP_DIR',
                          filetype => DBMS_DATAPUMP.KU$_FILE_TYPE_LOG_FILE);

  -- Filter: schema HR only
  DBMS_DATAPUMP.METADATA_FILTER(h1, 'SCHEMA_EXPR',
                                  'IN (''HR'')');

  -- Start and wait for completion
  DBMS_DATAPUMP.START_JOB(h1);
  DBMS_DATAPUMP.WAIT_FOR_JOB(h1, job_state => :job_state);
  DBMS_DATAPUMP.DETACH(h1);
END;

Real-World DBA Scenarios

These are the most common production tasks Oracle DBAs perform with Data Pump — know these cold for interviews and day-to-day work.

The most common Data Pump use case. Export PROD schema, import into DEV with different schema and tablespace names. Use TABLE_EXISTS_ACTION=REPLACE to fully refresh the DEV schema.

-- Step 1: Export from PROD (run on PROD server)
expdp system/password@PROD \
  SCHEMAS=HR \
  DIRECTORY=dpump_dir DUMPFILE=hr_prod_%U.dmp \
  LOGFILE=hr_prod_exp.log PARALLEL=4 \
  COMPRESSION=ALL

-- Step 2: Copy dump files to DEV server (OS level)
scp /u01/datapump/hr_prod_*.dmp oracle@devserver:/u01/datapump/

-- Step 3: Import into DEV (run on DEV server)
impdp system/password@DEV \
  DIRECTORY=dpump_dir DUMPFILE=hr_prod_%U.dmp \
  LOGFILE=hr_dev_imp.log \
  REMAP_SCHEMA=HR:HR_DEV \
  REMAP_TABLESPACE=PROD_DATA:DEV_DATA \
  REMAP_TABLESPACE=PROD_IDX:DEV_IDX \
  TABLE_EXISTS_ACTION=REPLACE \
  EXCLUDE=STATISTICS \
  PARALLEL=4

-- Step 4: Gather stats on DEV after import
EXEC DBMS_STATS.GATHER_SCHEMA_STATS('HR_DEV', cascade => TRUE);

For full database migration, use Full Transportable Export/Import (Oracle 12c+) for maximum speed, or fall back to FULL=Y if transportable isn't feasible. Full transportable moves most data as datafiles, drastically reducing export/import time.

-- OPTION A: Full database export (conventional)
expdp system/password@SOURCE \
  FULL=Y PARALLEL=8 \
  DIRECTORY=dpump_dir DUMPFILE=fulldb_%U.dmp \
  LOGFILE=fulldb_exp.log COMPRESSION=ALL \
  FLASHBACK_TIME="SYSDATE-1/24"  -- consistent as of 1 hour ago

-- OPTION B: Full Transportable (12c+) — much faster for large DBs
expdp system/password@SOURCE \
  FULL=Y TRANSPORTABLE=ALWAYS \
  VERSION=12.2 \
  DIRECTORY=dpump_dir DUMPFILE=fulltts.dmp \
  LOGFILE=fulltts_exp.log

-- Copy datafiles from source to target (OS)
-- Then import metadata on target:
impdp system/password@TARGET \
  FULL=Y TRANSPORT_DATAFILES='/path/to/datafiles' \
  DIRECTORY=dpump_dir DUMPFILE=fulltts.dmp \
  LOGFILE=fulltts_imp.log

Use the QUERY parameter to export a subset of rows from specific tables. Perfect for compliance (exclude sensitive data), testing (use only a sample), or extracting recent records. Different tables can have different QUERY filters in the same job.

-- Export only orders from last 30 days, all customers
expdp hr/password@ORCL \
  TABLES=ORDERS,CUSTOMERS,ORDER_ITEMS \
  QUERY=ORDERS:"WHERE order_date >= SYSDATE - 30" \
  QUERY=ORDER_ITEMS:"WHERE order_id IN (SELECT order_id FROM orders WHERE order_date >= SYSDATE-30)" \
  DIRECTORY=dpump_dir DUMPFILE=recent_orders.dmp \
  LOGFILE=recent_orders.log

-- Export schema EXCLUDING sensitive columns (use VIEWS instead)
-- Create a view that masks sensitive data, then export the view

When exporting databases containing PII, health records, or payment card data, encrypt the dump file. Without encryption, the dump file is readable by anyone with OS access to the server — a major security risk.

-- Export with AES-256 encryption (HIPAA/PCI compliant)
expdp system/password@ORCL \
  SCHEMAS=PATIENT_DATA \
  DIRECTORY=dpump_dir DUMPFILE=patient_%U.dmp \
  LOGFILE=patient_exp.log \
  ENCRYPTION=ALL \
  ENCRYPTION_ALGORITHM=AES256 \
  ENCRYPTION_PASSWORD='V3ryStr0ng#Pass!' \
  ENCRYPTION_MODE=PASSWORD \
  PARALLEL=4

-- Import (password required — anyone without it gets ORA-39215)
impdp system/password@TARGET \
  DIRECTORY=dpump_dir DUMPFILE=patient_%U.dmp \
  LOGFILE=patient_imp.log \
  ENCRYPTION_PASSWORD='V3ryStr0ng#Pass!' \
  REMAP_SCHEMA=PATIENT_DATA:PATIENT_DATA_UAT

When disk space is constrained, use NETWORK_LINK to import directly from the source database over a database link — no dump files. This is ideal for frequent schema refreshes between environments on the same network.

-- On TARGET: create DB link pointing to SOURCE
CREATE DATABASE LINK prod_link
  CONNECT TO system IDENTIFIED BY password
  USING '(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)(HOST=prodserver)(PORT=1521))(CONNECT_DATA=(SERVICE_NAME=ORCL)))';

-- Test the link
SELECT name FROM v$database@prod_link;

-- Import directly from SOURCE without any dump files
impdp system/password@TARGET \
  NETWORK_LINK=prod_link \
  SCHEMAS=HR \
  REMAP_SCHEMA=HR:HR_DEV \
  REMAP_TABLESPACE=PROD_DATA:DEV_DATA \
  DIRECTORY=dpump_dir LOGFILE=netlink_imp.log \
  TABLE_EXISTS_ACTION=REPLACE EXCLUDE=STATISTICS \
  PARALLEL=4

Use CONTENT=METADATA_ONLY to export just the schema structure — no data rows. The dump file is tiny and the import is fast. Perfect for: creating a DDL baseline before upgrades, documenting the schema, creating an empty dev environment, or comparing schema versions.

-- Export schema structure only (no data rows)
expdp hr/password@ORCL \
  SCHEMAS=HR \
  CONTENT=METADATA_ONLY \
  DIRECTORY=dpump_dir DUMPFILE=hr_ddl.dmp \
  LOGFILE=hr_ddl.log

-- Create empty copy of schema on same or different DB
impdp system/password@TESTDB \
  DUMPFILE=hr_ddl.dmp DIRECTORY=dpump_dir \
  CONTENT=METADATA_ONLY \
  REMAP_SCHEMA=HR:HR_EMPTY \
  TABLE_EXISTS_ACTION=REPLACE \
  LOGFILE=hr_empty.log

Real-Time Issues & ORA Errors

These are the most common Data Pump errors in production. Know the root cause and resolution for each — guaranteed interview and day-to-day relevance.

Root Cause

The directory object does not exist, the user does not have READ/WRITE privilege on it, or the physical OS directory doesn't exist or isn't writable by the oracle OS user.

-- Diagnose: check if directory exists in DB
SELECT directory_name, directory_path FROM dba_directories;

-- Check OS directory exists and permissions
ls -la /u01/datapump/

-- Fix: create directory object
CREATE OR REPLACE DIRECTORY dpump_dir AS '/u01/datapump';
GRANT READ, WRITE ON DIRECTORY dpump_dir TO myuser;

-- Fix: OS permissions (as root)
chown oracle:oinstall /u01/datapump
chmod 750 /u01/datapump

Root Cause

Invalid parameter combination: using mutually exclusive parameters (INCLUDE + EXCLUDE before 21c), invalid mode combination, missing required parameters, or an invalid parameter value that makes the operation impossible.

-- Common triggers:
-- Using INCLUDE= and EXCLUDE= together (before Oracle 21c)
-- Using QUERY= with ESTIMATE_ONLY=Y
-- Using TABLE_EXISTS_ACTION=SKIP with CONTENT=DATA_ONLY
-- TRANSPORT_TABLESPACES without tablespace in READ ONLY mode

-- Fix: check the log file for the specific cause
-- Review parameter combinations carefully
-- Separate INCLUDE and EXCLUDE into different jobs

Root Cause

An object (usually a table, index, constraint, sequence, or user) failed to create during import. Common causes: missing tablespace, missing user, privilege issues, character set mismatch, missing dependency, or constraint violation during data load.

-- Always check the LOGFILE — ORA-39083 is followed by the actual error
-- Example log:
-- ORA-39083: Object type TABLE:"HR"."EMPLOYEES" failed to create
-- ORA-00959: tablespace 'PROD_DATA' does not exist

-- Fix: create the missing tablespace OR add REMAP_TABLESPACE
CREATE TABLESPACE prod_data DATAFILE '/u01/data/prod_data01.dbf'
  SIZE 100M AUTOEXTEND ON;

-- Or remap to an existing tablespace on import
impdp ... REMAP_TABLESPACE=PROD_DATA:USERS

-- Skip problematic objects and continue (accept errors)
impdp ... TABLE_EXISTS_ACTION=SKIP

Root Cause

A Data Pump job with that name already exists in DBA_DATAPUMP_JOBS — it's either running, stopped, or its Master Table was retained after a previous run (KEEP_MASTER=YES or the job failed). Oracle re-uses job names if a Master Table from a previous run exists.

-- Find existing jobs (including stopped/failed ones)
SELECT job_name, state, operation, owner_name
FROM   dba_datapump_jobs
WHERE  state != 'COMPLETING'
ORDER BY job_name;

-- Attach and kill a stopped job
expdp system/password@ORCL ATTACH=MYJOB
Export> KILL_JOB

-- Or drop the orphaned master table directly
DROP TABLE system.SYS_EXPORT_SCHEMA_01 PURGE;

-- Use unique JOB_NAME to avoid collisions
expdp ... JOB_NAME=HR_EXP_20250517_001

Root Cause

Attempting to ATTACH to a job that doesn't exist in DBA_DATAPUMP_JOBS. Can happen if: the job name is misspelled, the job completed and the master table was dropped, or the SYSTEM tablespace has issues preventing the job table from being read.

-- Check what jobs actually exist
SELECT owner_name, job_name, operation, state
FROM   dba_datapump_jobs;

-- Also check USER_DATAPUMP_JOBS (your own jobs)
SELECT * FROM user_datapump_jobs;

-- If job completed: the master table was dropped — job is done
-- Check the log file for results

Root Cause

A Worker Process crashed unexpectedly. Common causes: corrupted internal views (e.g., SYS.KU$_CLUSTER_VIEW), invalid objects in the schema being exported, insufficient temporary tablespace for worker operations, or Oracle bug requiring a patch.

-- Check for invalid objects before export
SELECT owner, object_name, object_type, status
FROM   dba_objects
WHERE  status = 'INVALID'
  AND  owner = 'HR';

-- Recompile invalid objects
EXEC UTL_RECOMP.RECOMP_SCHEMA('HR');

-- Check and add temporary tablespace if insufficient
SELECT tablespace_name, bytes_used, bytes_free
FROM   v$temp_space_header;

-- Workaround: exclude statistics (common trigger)
expdp ... EXCLUDE=STATISTICS

-- Reduce PARALLEL if workers keep crashing
expdp ... PARALLEL=1

Root Cause

An invalid value was passed to a Data Pump parameter. Common causes: negative PARALLEL value, invalid COMPRESSION value, invalid CONTENT value, or an invalid object type in INCLUDE/EXCLUDE.

-- Check the error message in the log for the specific invalid argument
-- Valid COMPRESSION values: NONE, METADATA_ONLY, DATA_ONLY, ALL
-- Valid CONTENT values: ALL, DATA_ONLY, METADATA_ONLY
-- Valid PARALLEL: positive integer (1 or more)
-- Valid ENCRYPTION: NONE, METADATA_ONLY, DATA_ONLY, ENCRYPTED_COLUMNS_ONLY, ALL

Root Cause

Internal Data Pump API error. Often caused by: missing or corrupted XSL stylesheets used by the Metadata API, missing SYS.METASTYLESHEET table, or a known bug requiring an Oracle patch.

-- Fix: reload the metadata stylesheets as SYSDBA
EXEC DBMS_METADATA_UTIL.LOAD_STYLESHEETS();

-- Verify SYS.METASTYLESHEET exists
SELECT COUNT(*) FROM sys.metastylesheet;

Interview Q&A

Data Pump — Interview Questions

Top Data Pump interview questions covering expdp/impdp options, performance, and migration scenarios.

The legacy exp/imp tools run entirely on the client side, processing data through SQL*Net to/from the client machine. They are single-threaded and limited in performance and restart capability.

expdp/impdp (Data Pump) runs entirely on the server side using a master table and worker processes in the database. Key advantages: (1) PARALLEL — multiple worker processes write simultaneously to multiple dump files; (2) Restart — can be paused/detached and reattached; (3) Faster — direct path reads bypass SQL layer; (4) Network link imports — can import directly from remote database without a dump file; (5) Richer filtering — INCLUDE/EXCLUDE, CONTENT=DATA_ONLY, query filters per table. Legacy exp/imp is deprecated since Oracle 10g.

Data Pump provides two key remapping parameters:

  • REMAP_SCHEMA=source_schema:target_schema — imports all objects from the source schema into a different target schema. Useful when migrating from PROD to DEV with different schema names.
  • REMAP_TABLESPACE=source_ts:target_ts — relocates all objects from one tablespace to another during import. Use when the target database has different tablespace names.
impdp system/pwd DIRECTORY=dpump_dir DUMPFILE=prod_exp.dmp
  REMAP_SCHEMA=PRODUSER:DEVUSER
  REMAP_TABLESPACE=PROD_DATA:DEV_DATA
  LOGFILE=import.log

The PARALLEL parameter specifies how many worker processes simultaneously export or import data. For PARALLEL to be effective, you must specify multiple dump files with a %U substitution variable: DUMPFILE=exp_%U.dmp PARALLEL=4 creates up to 4 dump files written simultaneously.

When to use: Large databases (>50GB) where export/import time is critical. Parallel degree should match the number of large tables, CPUs available, and I/O throughput. Setting PARALLEL higher than CPU cores or I/O bandwidth can cause contention. For small exports or a single-table export, PARALLEL=1 is sufficient.

Data Pump supports importing directly from a source database over a database link — no intermediate dump file is needed. This is efficient for migrations between databases on the same network.

-- Step 1: Create db link to source (on target db)
CREATE DATABASE LINK prod_link
  CONNECT TO SYSTEM IDENTIFIED BY <pwd>
  USING '<tns_alias_to_source>';

-- Step 2: Import via network link
impdp system/pwd NETWORK_LINK=prod_link
  SCHEMAS=HRSCHEMA REMAP_SCHEMA=HRSCHEMA:HRDEV
  LOGFILE=net_import.log

The source user referenced in the DB link must have the EXP_FULL_DATABASE role or DATAPUMP_EXP_FULL_DATABASE privilege. Network link imports are slower than file-based imports but eliminate the intermediate storage requirement.

ESTIMATE_ONLY=YES performs a dry run — Data Pump estimates the dump file size based on segment sizes without actually exporting any data. Useful before a migration to plan storage requirements: expdp system/pwd FULL=YES ESTIMATE_ONLY=YES ESTIMATE=BLOCKS.

To monitor an active Data Pump job: (1) Attach to the running job: expdp ATTACH=<job_name>, then type STATUS; (2) Query the database: SELECT job_name, operation, state, degree FROM dba_datapump_jobs;; (3) Check the master table: SELECT owner_name, job_name, percent_done FROM v$datapump_job;. To pause and resume: use the STOP_JOB and START_JOB commands from the attach prompt.
