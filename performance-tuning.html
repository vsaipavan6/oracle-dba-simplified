Performance Tuning Methodology

A structured, repeatable approach is the difference between a lucky fix and a permanent solution. Always follow the data — not gut instinct.

1

Baseline

Capture current AWR snapshot and performance metrics

2

Identify

AWR Top 5 Wait Events, ADDM findings, top SQL

3

Analyse

Root cause — SQL plan, memory, I/O, locking

4

Tune

One change at a time — SQL, indexes, memory, parameters

5

Measure

Generate new AWR, compare before/after metrics

6

Monitor

Watch for regressions, automate alerts

Oracle Diagnostic Toolkit

AWR

Automatic Workload Repository

Historical snapshots every 60 min (default). Source of truth for all tuning. Requires Diagnostics Pack.

ASH

Active Session History

Samples active sessions every 1 second. Real-time visibility. Stored in SGA, some written to AWR.

ADDM

Automatic DB Diagnostic Monitor

Automatically analyses AWR snapshots, identifies root causes, and gives actionable recommendations.

STA

SQL Tuning Advisor

Analyses specific SQL and suggests indexes, SQL profiles, and plan changes to improve performance.

SPM

SQL Plan Management

Pins SQL execution plans so they cannot regress after upgrades, stats changes, or parameter changes.

The DBA's Golden Rules of Tuning

Tune the application first, then the database

A bad SQL query cannot be fixed by any amount of memory or hardware. Fix the SQL before adding RAM.

One change at a time

Making multiple changes simultaneously makes it impossible to know what helped or hurt.

Measure before you tune

Take an AWR snapshot before any change. You cannot prove improvement without a baseline.

DB Time is the only metric that matters

DB Time = CPU time + Wait time. Everything else is a component. Tune what consumes the most DB Time.

Always check statistics currency

90% of "sudden" slow SQL is caused by stale statistics producing a bad execution plan.

Historical Diagnostics

AWR — Automatic Workload Repository

AWR is Oracle's built-in performance warehouse — snapshots of every key metric every 60 minutes, retained for 8 days (default). The foundation of all performance tuning.

AWR Snapshot Management
-- List recent AWR snapshots
SELECT snap_id,
       begin_interval_time,
       end_interval_time,
       snap_level
FROM   dba_hist_snapshot
ORDER BY snap_id DESC
FETCH FIRST 10 ROWS ONLY;

-- Create manual AWR snapshot NOW
EXEC DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT;

-- Change snapshot interval and retention
BEGIN
  DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS(
    retention  => 43200,   -- 30 days in minutes
    interval   => 30,      -- every 30 minutes
    topnsql    => 100     -- top 100 SQL captured
  );
END;
/

-- Purge snapshots older than range
BEGIN
  DBMS_WORKLOAD_REPOSITORY.DROP_SNAPSHOT_RANGE(
    low_snap_id  => 1,
    high_snap_id => 50
  );
END;

Key AWR Report Sections — Reading Order

1st

Top 5 Timed Events

Lists the five events consuming most DB Time. This tells you WHERE the bottleneck is. Start here every time.

2nd

Load Profile

DB Time, Logical Reads/sec, Physical Reads/sec, Hard Parses/sec, Redo Size/sec. Compare to baseline to spot anomalies.

3rd

SQL Statistics

Top SQL by CPU, Elapsed Time, Disk Reads, Buffer Gets, Parse Calls. Identifies which SQL drives the most load.

4th

Instance Efficiency

Buffer Cache Hit %, Library Cache Hit %, Soft Parse %. Green metrics here = healthy memory configuration.

5th

Memory Statistics

SGA/PGA usage, buffer cache advice, shared pool advice. Used to validate memory sizing decisions.

AWR Historical Top SQL (dba_hist_sqlstat)
-- AWR top SQL — all snapshots in last 24h
SELECT
  s.sql_id,
  s.plan_hash_value,
  SUM(s.executions_delta)             executions,
  ROUND(SUM(s.elapsed_time_delta)/1e6,1) elapsed_sec,
  ROUND(SUM(s.cpu_time_delta)/1e6,1)     cpu_sec,
  SUM(s.disk_reads_delta)             disk_reads,
  SUM(s.buffer_gets_delta)            buffer_gets,
  SUBSTR(t.sql_text,1,60)             sql_preview
FROM   dba_hist_sqlstat s
JOIN   dba_hist_sqltext t
       ON s.sql_id = t.sql_id
JOIN   dba_hist_snapshot sn
       ON s.snap_id = sn.snap_id
WHERE  sn.begin_interval_time >= SYSDATE - 1
  AND  s.executions_delta > 0
GROUP BY s.sql_id, s.plan_hash_value,
         SUBSTR(t.sql_text,1,60)
ORDER BY SUM(s.elapsed_time_delta) DESC
FETCH FIRST 15 ROWS ONLY;

-- Detect SQL plan changes (regression detection)
SELECT
  sql_id,
  plan_hash_value,
  COUNT(DISTINCT snap_id)             snaps,
  ROUND(AVG(elapsed_time_delta
    /NULLIF(executions_delta,0))/1e6,3) avg_elapsed_sec,
  MIN(sn.begin_interval_time)          first_seen,
  MAX(sn.begin_interval_time)          last_seen
FROM   dba_hist_sqlstat s
JOIN   dba_hist_snapshot sn
       ON s.snap_id = sn.snap_id
WHERE  s.sql_id = '&sql_id'
  AND  s.executions_delta > 0
GROUP BY sql_id, plan_hash_value
ORDER BY first_seen;
AWR Instance Efficiency Metrics
-- Buffer Cache Hit Ratio
SELECT
  ROUND(100 * (1 - (phys / (dblk + cons))), 2) bchr_pct
FROM (
  SELECT
    SUM(CASE WHEN name='physical reads'
             THEN value ELSE 0 END) phys,
    SUM(CASE WHEN name='db block gets'
             THEN value ELSE 0 END) dblk,
    SUM(CASE WHEN name='consistent gets'
             THEN value ELSE 0 END) cons
  FROM v$sysstat
);
-- Target: > 95% (ideally > 99% for OLTP)

-- Library Cache Hit Ratio
SELECT
  namespace,
  ROUND(100*(pins-reloads)/NULLIF(pins,0),2) hit_pct,
  reloads, invalidations
FROM   v$librarycache
WHERE  namespace IN ('SQL AREA','TABLE/PROCEDURE','BODY')
ORDER BY hit_pct;
-- Target: > 99%

-- Hard vs. Soft parse ratio
SELECT
  hard_parses,
  total_parses,
  ROUND(100*hard_parses/NULLIF(total_parses,0),2) hard_pct
FROM (
  SELECT
    SUM(CASE WHEN name='parse count (hard)'
             THEN value ELSE 0 END) hard_parses,
    SUM(CASE WHEN name='parse count (total)'
             THEN value ELSE 0 END) total_parses
  FROM v$sysstat
);
-- Target: hard parse% < 5%

-- Redo log switches per hour (should be < 4)
SELECT
  TRUNC(completion_time,'HH') hr,
  COUNT(*)                      switches
FROM   v$archived_log
WHERE  completion_time >= SYSDATE - 1
GROUP BY TRUNC(completion_time,'HH')
ORDER BY hr DESC;

How ADDM Works

ADDM automatically runs after every AWR snapshot and analyses the data between the two most recent snapshots. It identifies root causes — not just symptoms — and quantifies their impact as a percentage of DB Time.

What it finds

SQL hogging resources, memory pressure, I/O saturation, locking, high parse rates, undo usage

What it recommends

Run SQL Tuning Advisor, increase SGA, use bind variables, create indexes, resize redo logs

-- Run ADDM manually for a custom snapshot range
DECLARE
  task_name VARCHAR2(30) := 'my_addm_task';
BEGIN
  DBMS_ADVISOR.CREATE_TASK('ADDM', task_name);
  DBMS_ADVISOR.SET_TASK_PARAMETER(
    task_name, 'START_SNAPSHOT', 1120);
  DBMS_ADVISOR.SET_TASK_PARAMETER(
    task_name, 'END_SNAPSHOT',   1125);
  DBMS_ADVISOR.EXECUTE_TASK(task_name);
END;

Real-Time Diagnostics

Active Session History (ASH)

ASH samples every active session every second, storing a rolling 1-hour in-memory history. The richest tool for diagnosing transient performance spikes that have already ended.

1-Second Sampling

MMNL background process samples v$session every second, recording active sessions (status=ACTIVE and not idle). This gives sub-minute granularity AWR lacks.

In-Memory → AWR

Up to ~1 hour in v$active_session_history (memory). Every 10th row flushed to dba_hist_active_sess_history (disk) for long-term analysis.

What ASH Tells You

Top wait events per SQL, per user, per time window. Identify blocking sessions, top offenders, spikes that lasted only 2 minutes — invisible in AWR snapshots.

Run these queries while a problem is happening for instant insight.

v$active_session_history — live
-- What are sessions waiting on RIGHT NOW?
SELECT event, COUNT(*) sessions,
       ROUND(COUNT(*) * 100 / SUM(COUNT(*)) OVER(), 1) pct
FROM   v$active_session_history
WHERE  sample_time >= SYSDATE - INTERVAL '5' MINUTE
  AND  session_state = 'WAITING'
GROUP BY event
ORDER BY 2 DESC
FETCH FIRST 10 ROWS ONLY;

-- Top sessions by activity in last 5 minutes
SELECT s.sid, s.serial#, s.username,
       ash.event, COUNT(*) samples,
       s.sql_id, s.blocking_session
FROM   v$active_session_history ash
JOIN   v$session s ON ash.session_id = s.sid
WHERE  ash.sample_time >= SYSDATE - INTERVAL '5' MINUTE
GROUP BY s.sid, s.serial#, s.username, ash.event, s.sql_id, s.blocking_session
ORDER BY samples DESC
FETCH FIRST 15 ROWS ONLY;

-- CPU consumers RIGHT NOW (no wait event = on CPU)
SELECT session_id, session_serial#, user_id,
       sql_id, sql_plan_hash_value, COUNT(*) cpu_samples
FROM   v$active_session_history
WHERE  sample_time >= SYSDATE - INTERVAL '2' MINUTE
  AND  session_state = 'ON CPU'
GROUP BY session_id, session_serial#, user_id, sql_id, sql_plan_hash_value
ORDER BY cpu_samples DESC;

Find the SQL statements causing the most waits — and what they're waiting for.

ASH — top SQL by wait event
-- Top SQL by total wait time in last hour
SELECT sql_id,
       event,
       COUNT(*) * 1 AS est_wait_secs,
       SUBSTR(sql_text, 1, 80) sql_preview
FROM   v$active_session_history ash
LEFT JOIN v$sql sq USING (sql_id)
WHERE  ash.sample_time >= SYSDATE - 1/24
  AND  session_state = 'WAITING'
  AND  sql_id IS NOT NULL
GROUP BY sql_id, event, SUBSTR(sql_text, 1, 80)
ORDER BY 3 DESC
FETCH FIRST 20 ROWS ONLY;

-- Wait event breakdown per SQL (drill-down)
SELECT event,
       wait_class,
       COUNT(*) samples,
       ROUND(COUNT(*) * 100 / SUM(COUNT(*)) OVER(), 1) pct
FROM   v$active_session_history
WHERE  sql_id = '&your_sql_id'
  AND  sample_time >= SYSDATE - 1/24
GROUP BY event, wait_class
ORDER BY samples DESC;

-- Time-series activity for a specific SQL (every 5 min bucket)
SELECT TRUNC(sample_time, 'MI') - MOD(TO_NUMBER(TO_CHAR(sample_time,'MI')),5)/(24*60) tm,
       session_state,
       COUNT(*) samples
FROM   v$active_session_history
WHERE  sql_id = '&your_sql_id'
  AND  sample_time >= SYSDATE - 2/24
GROUP BY TRUNC(sample_time,'MI') - MOD(TO_NUMBER(TO_CHAR(sample_time,'MI')),5)/(24*60), session_state
ORDER BY 1;

Use dba_hist_active_sess_history for incidents that happened hours or days ago.

dba_hist_active_sess_history — historical
-- Top wait events during a past incident window
SELECT event,
       wait_class,
       COUNT(*) * 10 est_secs,  -- ×10 because 1-in-10 sampling
       ROUND(COUNT(*) * 1000 / SUM(COUNT(*)) OVER(), 1) pct_x10
FROM   dba_hist_active_sess_history
WHERE  sample_time BETWEEN
         TO_TIMESTAMP('2025-01-15 09:00', 'YYYY-MM-DD HH24:MI')
     AND TO_TIMESTAMP('2025-01-15 09:30', 'YYYY-MM-DD HH24:MI')
  AND  dbid = (SELECT dbid FROM v$database)
GROUP BY event, wait_class
ORDER BY 3 DESC;

-- Top SQL during incident (historical, ranked by samples)
SELECT ash.sql_id,
       COUNT(*) * 10 est_secs,
       SUBSTR(txt.sql_text, 1, 100) sql_preview,
       ash.event
FROM   dba_hist_active_sess_history ash
LEFT JOIN dba_hist_sqltext txt ON ash.sql_id = txt.sql_id AND ash.dbid = txt.dbid
WHERE  ash.sample_time BETWEEN
         TO_TIMESTAMP('2025-01-15 09:00', 'YYYY-MM-DD HH24:MI')
     AND TO_TIMESTAMP('2025-01-15 09:30', 'YYYY-MM-DD HH24:MI')
  AND  ash.dbid = (SELECT dbid FROM v$database)
  AND  ash.sql_id IS NOT NULL
GROUP BY ash.sql_id, SUBSTR(txt.sql_text,1,100), ash.event
ORDER BY 2 DESC
FETCH FIRST 15 ROWS ONLY;

-- Blocking chain history
SELECT sample_time, session_id, blocking_session,
       event, wait_class, sql_id
FROM   dba_hist_active_sess_history
WHERE  blocking_session IS NOT NULL
  AND  sample_time >= SYSDATE - 1
  AND  dbid = (SELECT dbid FROM v$database)
ORDER BY sample_time, session_id;

ASH vs AWR

AWR: 1-hour snapshot intervals, ideal for trends and baselines. ASH: 1-second samples, ideal for "what happened at 9:15 AM for 3 minutes." Use both together — AWR for context, ASH for precision.

Sampling Caveat

ASH is sampled, not exact. A query that runs 0.5s and completes between samples may not appear at all. It's statistically representative, not forensically precise. For very short queries, use SQL trace or extended statistics.

Bottleneck Identification

Wait Events Deep Dive

Every second a session is active it's either on CPU or waiting. Wait events name exactly what Oracle is waiting for. Click any event below to see diagnostic SQL and resolution steps.

User I/O

Reading/writing user data — db file sequential/scattered reads

Concurrency

Waiting for another session — locks, latches, enqueues

Commit

Waiting for redo to disk — log file sync

Network

SQL*Net message waits, client fetch delays

db file sequential read
User I/O High Impact

Single-block reads — index lookups, FTS on small tables. Most common wait in OLTP databases.

db file scattered read
User I/O FTS Signal

Multi-block reads — full table/index scans. High value = missing indexes or poor selectivity.

log file sync
Commit LGWR Wait

Session waiting for LGWR to write redo to disk on COMMIT. Slow disk or too-frequent commits.

enq: TX - row lock
Concurrency Blocking

Session waiting for a row locked by another transaction. Classic blocking scenario.

library cache lock
Concurrency Shared Pool

DDL or hard parse competing with active SQL. Invalidation storms, missing bind variables.

buffer busy waits
Concurrency Hot Block

Multiple sessions competing for the same buffer. Hot index root blocks, unordered inserts.

db file sequential read

P1=file# · P2=first block# · P3=block count (usually 1)

Root Causes

  • Inefficient index range scans (low selectivity)
  • Missing indexes on joined columns
  • Nested loops with large outer result set
  • Slow I/O subsystem (check await in iostat)
  • Buffer cache too small

Resolution Steps

  • Review execution plan — is index appropriate?
  • Check index selectivity (NDV / NUM_ROWS)
  • Consider composite index for covered queries
  • Increase DB_CACHE_SIZE
  • Verify storage latency (< 5ms target)
Diagnose db file sequential read
-- Top SQL generating this wait (last 1 hour)
SELECT ash.sql_id, COUNT(*) waits,
       SUBSTR(sq.sql_text, 1, 80) sql_preview
FROM   v$active_session_history ash
JOIN   v$sql sq ON ash.sql_id = sq.sql_id
WHERE  ash.event = 'db file sequential read'
  AND  ash.sample_time >= SYSDATE - 1/24
GROUP BY ash.sql_id, SUBSTR(sq.sql_text, 1, 80)
ORDER BY 2 DESC;

-- Check average wait time system-wide
SELECT event, total_waits, time_waited_micro/1000 ms,
       ROUND(time_waited_micro/total_waits/1000,2) avg_ms
FROM   v$system_event
WHERE  event = 'db file sequential read';
-- avg_ms > 10ms → storage is the problem, not Oracle

db file scattered read

P1=file# · P2=first block# · P3=block count (multi-block read count)

Root Causes

  • Full table or index scans on large objects
  • Stale or missing optimizer statistics
  • Wrong join method chosen by optimizer
  • Parallel query spawning excessive I/O

Resolution Steps

  • Create or rebuild missing indexes
  • Gather fresh statistics (DBMS_STATS)
  • Use hints to test alternate plans
  • Tune DB_FILE_MULTIBLOCK_READ_COUNT
Find full scans
-- Find FTS operations in current SQL plans
SELECT s.sql_id, p.object_name, p.object_type,
       s.executions, s.disk_reads, s.rows_processed
FROM   v$sql s
JOIN   v$sql_plan p ON s.sql_id = p.sql_id AND s.child_number = p.child_number
WHERE  p.operation = 'TABLE ACCESS'
  AND  p.options  = 'FULL'
  AND  s.disk_reads > 10000
ORDER BY s.disk_reads DESC;

log file sync

P1=buffer# synced — occurs on every COMMIT/ROLLBACK

Root Causes

  • Slow redo log storage (non-SSD redo logs)
  • Committing inside a loop (row-by-row commits)
  • Redo logs too small → frequent log switches
  • I/O contention on shared storage

Resolution Steps

  • Move redo logs to fastest storage (NVMe/SSD)
  • Batch commits — commit every N rows, not every row
  • Increase redo log size (target 1 switch per 15-30 min)
  • Use COMMIT_WRITE=BATCH,NOWAIT for non-critical apps
Diagnose log file sync
-- Average log file sync time (target < 2ms)
SELECT event, total_waits,
       ROUND(time_waited_micro/total_waits/1000,2) avg_ms,
       ROUND(time_waited_micro/1000000,1) total_secs
FROM   v$system_event
WHERE  event IN ('log file sync', 'log file parallel write');

-- Log switch frequency (should be ~20-30 min)
SELECT TO_CHAR(first_time,'YYYY-MM-DD HH24') hr,
       COUNT(*) switches
FROM   v$log_history
WHERE  first_time >= SYSDATE - 2
GROUP BY TO_CHAR(first_time,'YYYY-MM-DD HH24')
ORDER BY 1;

enq: TX - row lock contention

P1=lock type (TX=1415053318) · P2=TX slot · P3=sequence

Root Causes

  • Long-running uncommitted transactions
  • Application-level commit missing
  • Batch job holding locks during peak hours
  • Deadlock chains (ORA-00060)

Resolution Steps

  • Identify blocker via v$session.blocking_session
  • Kill blocking session if safe: ALTER SYSTEM KILL
  • Fix application to commit/rollback promptly
  • For deadlocks: check alert log for ORA-00060
Find & resolve row lock contention
-- Show complete blocking chain
SELECT
  LPAD(' ', LEVEL*2) || s.sid                  AS session_tree,
  s.username, s.status, s.sql_id,
  s.blocking_session                           AS blocked_by,
  s.wait_class, s.event,
  FLOOR(s.seconds_in_wait/60) wait_min
FROM   v$session s
WHERE  s.blocking_session IS NOT NULL
   OR  s.sid IN (SELECT blocking_session FROM v$session WHERE blocking_session IS NOT NULL)
CONNECT BY PRIOR s.sid = s.blocking_session
START WITH s.blocking_session IS NULL AND s.sid IN
  (SELECT blocking_session FROM v$session WHERE blocking_session IS NOT NULL)
ORDER SIBLINGS BY s.sid;

-- Kill the root blocker (DBA only, confirm first!)
ALTER SYSTEM KILL SESSION '&sid,&serial#' IMMEDIATE;

library cache lock / pin

Hard parse contention in the shared pool library cache

Diagnose library cache issues
-- Hard parse ratio (target < 1%)
SELECT
  ROUND(
    (SELECT value FROM v$sysstat WHERE name='parse count (hard)') * 100 /
    NULLIF((SELECT value FROM v$sysstat WHERE name='parse count (total)'), 0), 2
  ) hard_parse_pct
FROM dual;

-- Top hard-parsing SQL (missing bind variables)
SELECT SUBSTR(sql_text, 1, 60) sql_preview,
       COUNT(*) versions, SUM(parse_calls) parses
FROM   v$sql
WHERE  parse_calls > 100
GROUP BY SUBSTR(sql_text, 1, 60)
HAVING COUNT(*) > 5
ORDER BY 3 DESC;

-- Enable CURSOR_SHARING (emergency fix only)
ALTER SYSTEM SET cursor_sharing = FORCE;
-- Better fix: rewrite application SQL to use bind variables

buffer busy waits

P1=file# · P2=block# · P3=class# — hot block contention

Diagnose buffer busy waits

TABLE ACCESS FULL

Full table scan. Bad for OLTP on large tables. Good for DSS bulk reads. Missing index or stale stats?

INDEX RANGE SCAN

Good for OLTP with high selectivity. Check if columns in WHERE match leading index columns.

NESTED LOOPS

Efficient join when outer set is small. Scales linearly. Can be slow if driving row count is large.

HASH JOIN

Efficient for large unsorted sets. Uses PGA workarea. Spills to temp if PGA_AGGREGATE_TARGET too small.

SGA · PGA · AMM

Memory Tuning

Oracle memory management — from manually sizing each SGA component to letting AMM self-tune. Right-sized memory eliminates the majority of I/O-related wait events.

Oracle Memory Architecture

System Global Area (SGA) Shared
Buffer Cache— Cached data blocks. Largest component.
Shared Pool— Library cache + data dictionary cache.
Large Pool— RMAN, parallel query, shared server.
Redo Log Buffer— Pre-write redo buffer for LGWR.
Java Pool / Streams— Java VM and Streams/GoldenGate memory.
Program Global Area (PGA) Per Session
Sort Area— ORDER BY, GROUP BY, DISTINCT in memory.
Hash Area— Hash join build side. Spills to temp if too small.
Bitmap Merge Area— Bitmap index operations.
Session Stack / Variables— Cursor state, bind variable storage.

PGA spill → temp tablespace I/O

When PGA workarea overflows, Oracle writes to TEMP. Monitor v$sql_workarea_histogram for MULTIPASS operations — each is a performance penalty.

SGA component sizing
-- Current SGA layout
SELECT name, ROUND(bytes/1024/1024,0) MB
FROM   v$sgastat
WHERE  pool IS NULL OR pool = 'shared pool'
ORDER BY bytes DESC;

-- Buffer cache hit ratio (target > 95%)
SELECT
  ROUND(
    (1 - (phyrds.value / (db_blk_gets.value + consist_gets.value))) * 100
  , 2) buffer_cache_hit_pct
FROM
  (SELECT value FROM v$sysstat WHERE name = 'physical reads')          phyrds,
  (SELECT value FROM v$sysstat WHERE name = 'db block gets')           db_blk_gets,
  (SELECT value FROM v$sysstat WHERE name = 'consistent gets')         consist_gets;

-- Shared pool: library cache hit ratio (target > 99%)
SELECT
  namespace, gethits, gets,
  ROUND(gethitratio * 100, 2) hit_pct,
  reloads, invalidations
FROM   v$librarycache
ORDER BY gets DESC;

-- Shared pool free memory (fragmentation check)
SELECT pool, name,
       ROUND(bytes/1024/1024,1) MB
FROM   v$sgastat
WHERE  name IN ('free memory')
ORDER BY pool;

AMM
Automatic Memory Management

Set only MEMORY_TARGET. Oracle self-adjusts both SGA and PGA. Simple but can cause issues with HugePages on Linux (AMM uses tmpfs, HugePages requires fixed SGA).

-- AMM parameters
MEMORY_TARGET       = 12G  -- total Oracle memory
MEMORY_MAX_TARGET   = 14G  -- upper ceiling
SGA_TARGET          = 0    -- 0 = let AMM control
PGA_AGGREGATE_TARGET = 0   -- 0 = let AMM control
ASMM
Auto Shared Memory Mgmt

Set SGA_TARGET (Oracle auto-sizes SGA components) and PGA_AGGREGATE_TARGET separately. Recommended for Linux with HugePages — much more predictable performance.

-- ASMM parameters
MEMORY_TARGET       = 0    -- 0 = disable AMM
SGA_TARGET          = 8G   -- SGA auto-managed
SGA_MAX_SIZE        = 10G  -- upper ceiling
PGA_AGGREGATE_TARGET = 4G  -- PGA managed separately

Production Recommendation

Use ASMM on Linux with HugePages (set vm.nr_hugepages to cover SGA_MAX_SIZE). Disable AMM (MEMORY_TARGET=0). AMM on Linux uses /dev/shm which doesn't support HugePages — you lose a significant performance benefit. For Windows and Exadata, AMM is fine.

Statistics & Index Management

The CBO is only as good as its statistics. Stale stats = wrong cardinality estimates = bad plans. And an unused index is a drag on every DML operation.

DBMS_STATS — the complete toolkit

Stale statistics detection
-- Find stale or missing stats (> 10% row change)
SELECT owner, table_name, num_rows,
       last_analyzed,
       stale_stats,
       ROUND((SELECT mon.inserts + mon.updates + mon.deletes
              FROM   dba_tab_modifications mon
              WHERE  mon.table_owner = t.owner
                AND  mon.table_name  = t.table_name) * 100
             / NULLIF(t.num_rows, 0), 1) pct_changed
FROM   dba_tab_statistics t
WHERE  owner NOT IN ('SYS','SYSTEM','SYSMAN')
  AND  (stale_stats = 'YES' OR last_analyzed IS NULL)
ORDER BY pct_changed DESC NULLS LAST;

-- Column stats: check NDV and histogram presence
SELECT column_name, num_distinct ndv,
       num_nulls, density,
       histogram, num_buckets,
       last_analyzed
FROM   dba_col_statistics
WHERE  owner      = 'SCOTT'
  AND  table_name = 'ORDERS'
ORDER BY column_name;
-- High num_buckets = frequency/height-balanced histogram present
-- density = 1/NDV (without histogram), low NDV + skew = needs histogram

-- Objects with no stats at all
SELECT owner, table_name, num_rows, last_analyzed
FROM   dba_tables
WHERE  last_analyzed IS NULL
  AND  owner NOT IN ('SYS','SYSTEM')
ORDER BY owner, table_name;

       ROUND(distinct_keys * 100 / NULLIF(num_rows,0),2) selectivity_pct
FROM   dba_indexes di
JOIN   dba_tables  dt ON di.owner=dt.owner AND di.table_name=dt.table_name
WHERE  di.owner = 'SCOTT'

Bitmap, function-based, composite, and reverse key indexes
-- Function-based index (index on expression)
CREATE INDEX emp_upper_name_idx ON emp (UPPER(ename));
-- Now this uses the index (case-insensitive search):
SELECT * FROM emp WHERE UPPER(ename) = 'SCOTT';

-- Bitmap index (low cardinality, DSS workloads only)
CREATE BITMAP INDEX orders_status_bidx ON orders(status);
-- Warning: catastrophic for OLTP (row-level bitmap locking)
-- Use ONLY on read-mostly DSS tables with < 100 distinct values

-- Composite index — column order matters!
CREATE INDEX emp_dept_sal_idx ON emp(deptno, sal);
-- Can drive: WHERE deptno=10               → range scan ✓
-- Can drive: WHERE deptno=10 AND sal>2000  → range scan ✓
-- Cannot:   WHERE sal>2000 (only)          → skip scan or FTS

-- Reverse key index (eliminate hot index root block)
CREATE INDEX orders_id_rev_idx ON orders(order_id) REVERSE;
-- Spreads monotonically increasing inserts across leaf blocks
-- Trade-off: cannot do range scans on the indexed column

-- Partial index (11g+ invisible + 12c+ partial)
CREATE INDEX orders_active_idx ON orders(order_date)
  INDEXING PARTIAL;   -- only on INDEXING ON partitions

-- Index on partitioned table
CREATE INDEX orders_date_loc_idx ON orders(order_date) LOCAL;
-- LOCAL = one index segment per partition (partition-pruning aware)
-- GLOBAL = single index across all partitions (harder to maintain)
Concurrency Control

Locking & Blocking

Blocking is one of the most common production emergencies. Know how to identify the chain, confirm the blocker, and resolve it — in under 2 minutes.

Complete blocking resolution workflow
-- Step 1: Quick check — any blocking right now?
SELECT COUNT(*) blocking_pairs
FROM   v$session
WHERE  blocking_session IS NOT NULL;

-- Step 2: Full blocking chain with wait time
SELECT
  s.sid, s.serial#,
  s.username,
  s.blocking_session                        blocker_sid,
  s.event,
  s.wait_class,
  FLOOR(s.seconds_in_wait/60)             wait_min,
  s.sql_id,
  s.module,
  s.machine,
  s.status
FROM   v$session s
WHERE  s.blocking_session IS NOT NULL
ORDER BY s.blocking_session, s.seconds_in_wait DESC;

-- Step 3: What is the blocker doing?
SELECT s.sid, s.username, s.sql_id,
       SUBSTR(sq.sql_text,1,120) sql_text,
       s.status, s.last_call_et secs_idle,
       s.module, s.machine, s.osuser
FROM   v$session s
LEFT JOIN v$sql sq ON s.sql_id = sq.sql_id
WHERE  s.sid = &blocker_sid;

-- Step 4: What object is locked?
SELECT l.sid, l.type, l.lmode, l.request,
       o.object_name, o.object_type,
       l.block
FROM   v$lock l
LEFT JOIN dba_objects o ON l.id1 = o.object_id
WHERE  l.block = 1           -- 1 = this session IS blocking others
   OR  l.request > 0;       -- > 0 = this session IS being blocked

-- Step 5: Get the actual locked rows (DBA_DML_LOCKS)
SELECT * FROM dba_dml_locks
WHERE  mode_held != 'None'
ORDER BY name;

-- Step 6: Kill the blocker (confirm with app team first!)
ALTER SYSTEM KILL SESSION '&sid,&serial#' IMMEDIATE;
-- If it doesn't die (background process, DDL):
ALTER SYSTEM DISCONNECT SESSION '&sid,&serial#' IMMEDIATE;

-- Step 7: OS-level kill if Oracle kill fails
SELECT p.spid os_pid, s.sid, s.serial#, s.username
FROM   v$session s
JOIN   v$process p ON s.paddr = p.addr
WHERE  s.sid = &blocker_sid;
-- Then on OS: kill -9 <spid>

Prevention Best Practices

  • Always access tables in the same order across all transactions
  • Keep transactions short — commit/rollback quickly
  • Use SELECT FOR UPDATE NOWAIT or SKIP LOCKED
  • Move batch jobs to off-peak hours
  • Set DDL_LOCK_TIMEOUT for schema changes
  • Monitor blocking via EM Cloud Control alerts or custom script

Root Causes

Runaway SQL, blocking chain, auto-stats changed a plan, disk degradation, log file sync spike.

5-step triage script
-- STEP 1: Check top wait events right now
SELECT event, COUNT(*) cnt
FROM   v$active_session_history
WHERE  sample_time >= SYSDATE - INTERVAL '5' MINUTE
GROUP BY event ORDER BY 2 DESC FETCH FIRST 5 ROWS ONLY;

-- STEP 2: Blocking sessions?
SELECT blocking_session, COUNT(*) waiters, MIN(seconds_in_wait) wait_s
FROM   v$session WHERE blocking_session IS NOT NULL
GROUP BY blocking_session ORDER BY 2 DESC;

-- STEP 3: Runaway SQL (consuming all resources)?
SELECT sql_id, COUNT(*) samples, event
FROM   v$active_session_history
WHERE  sample_time >= SYSDATE - INTERVAL '10' MINUTE
  AND  sql_id IS NOT NULL
GROUP BY sql_id, event ORDER BY 2 DESC FETCH FIRST 5 ROWS ONLY;

-- STEP 4: Did a plan change? (compare with yesterday)
SELECT sql_id, plan_hash_value,
       MAX(snap_id) last_snap,
       ROUND(AVG(elapsed_time_total/1e6/NULLIF(executions_total,0)),2) avg_s
FROM   dba_hist_sqlstat
WHERE  snap_id > (SELECT MAX(snap_id)-24 FROM dba_hist_snapshot)
  AND  executions_total > 0
GROUP BY sql_id, plan_hash_value
ORDER BY avg_s DESC FETCH FIRST 10 ROWS ONLY;

-- STEP 5: Log file sync spike? (check redo log size)
SELECT TO_CHAR(first_time,'HH24:MI') t, COUNT(*) switches
FROM   v$log_history WHERE first_time >= SYSDATE - 2/24
GROUP BY TO_CHAR(first_time,'HH24:MI') ORDER BY 1;

ORA-04031 diagnosis & resolution
-- Confirm shared pool pressure
SELECT pool, name, ROUND(bytes/1024/1024,1) MB
FROM   v$sgastat
WHERE  name IN ('free memory','library cache')
ORDER BY pool, name;
-- Free memory < 5% of SHARED_POOL_SIZE = fragmented

-- Hard parse rate (the root cause)
SELECT name, value
FROM   v$sysstat
WHERE  name IN ('parse count (hard)','parse count (total)',
                'parse count (failures)');

-- Find non-shared cursors (literal SQL = hard parses)
SELECT SUBSTR(sql_text,1,50) sql_prefix,
       COUNT(*) versions
FROM   v$sql
GROUP BY SUBSTR(sql_text,1,50)
HAVING COUNT(*) > 20
ORDER BY 2 DESC FETCH FIRST 10 ROWS ONLY;
-- Many versions of same prefix = literal values instead of binds

-- Immediate fix: flush shared pool (use in emergency only)
ALTER SYSTEM FLUSH SHARED_POOL;
-- Warning: causes brief spike of hard parses, use off-peak

-- Permanent fix: enable cursor sharing (last resort)
ALTER SYSTEM SET cursor_sharing = FORCE;
-- Better: rewrite app to use bind variables
-- Also: increase SHARED_POOL_SIZE or SHARED_POOL_RESERVED_SIZE
ALTER SYSTEM SET shared_pool_size        = 2G;
ALTER SYSTEM SET shared_pool_reserved_size = 200M; -- 10% of shared_pool
log file sync investigation
-- Measure commit rate and wait time
SELECT event,
       total_waits,
       ROUND(time_waited_micro/1000000,1)        total_secs,
       ROUND(time_waited_micro/total_waits/1000,2) avg_ms
FROM   v$system_event
WHERE  event IN ('log file sync','log file parallel write');
-- avg_ms > 10 → storage is the bottleneck
-- log file sync >> log file parallel write → commit rate too high

-- Identify commit-happy sessions (commit per row)
SELECT s.sid, s.username, s.module,
       st.value commits, s.sql_id
FROM   v$sesstat st
JOIN   v$statname sn ON st.statistic# = sn.statistic#
JOIN   v$session  s  ON st.sid = s.sid
WHERE  sn.name = 'user commits'
  AND  st.value > 1000
  AND  s.status = 'ACTIVE'
ORDER BY st.value DESC;

-- Check log switch frequency (should be 1 per 15-30 min)
SELECT TO_CHAR(first_time,'YYYY-MM-DD HH24') hr,
       COUNT(*) switches
FROM   v$log_history
WHERE  first_time >= SYSDATE - 1
GROUP BY TO_CHAR(first_time,'YYYY-MM-DD HH24') ORDER BY 1;

ALTER DATABASE ADD LOGFILE GROUP 4
  '/oradata/redo04a.log' SIZE 1G;

WHERE  owner = 'SCOTT' AND table_name = 'ORDERS'

Emergency blocking resolution
-- Find the root blocker (session blocking the most sessions)
SELECT blocking_session root_blocker,
       COUNT(*)          sessions_blocked,
       MIN(seconds_in_wait) secs
FROM   v$session
WHERE  blocking_session IS NOT NULL
GROUP BY blocking_session
ORDER BY sessions_blocked DESC;

-- Who is this blocker? What were they doing?
SELECT sid, serial#, username, status, last_call_et idle_secs,
       sql_id, prev_sql_id, module, machine, osuser
FROM   v$session
WHERE  sid = &root_blocker;
-- last_call_et = seconds since last Oracle call
-- status=INACTIVE + sql_id=NULL = idle, holding a lock

-- What did they last run? (prev_sql_id)
SELECT sql_fulltext FROM v$sql
WHERE  sql_id = '&prev_sql_id' FETCH FIRST 1 ROW ONLY;
-- Tells you what transaction started the lock

-- Escalation decision matrix:
-- idle_secs < 60   → contact app team, may still be active
-- idle_secs 60-300 → kill with app team approval
-- idle_secs > 300  → kill immediately (session abandoned)

-- Kill the root blocker
ALTER SYSTEM KILL SESSION '&sid,&serial#' IMMEDIATE;
-- Verify all waiters are now unblocked
SELECT COUNT(*) FROM v$session WHERE blocking_session IS NOT NULL;
Parse rate optimization
-- Measure hard parse rate right now
SELECT name, value
FROM   v$sysstat
WHERE  name IN ('parse count (hard)','parse count (total)',
                'execute count','parse count (failures)');

-- Identify the worst literal SQL patterns
SELECT REGEXP_REPLACE(UPPER(SUBSTR(sql_text,1,60)),
         '[0-9]+','N') sql_pattern,
       COUNT(*)         child_cursors,
       SUM(parse_calls) total_parses
FROM   v$sql
WHERE  parse_calls > 50
GROUP BY REGEXP_REPLACE(UPPER(SUBSTR(sql_text,1,60)),'[0-9]+','N')
HAVING COUNT(*) > 10
ORDER BY child_cursors DESC FETCH FIRST 10 ROWS ONLY;

-- Check SESSION_CACHED_CURSORS (should be >= 50)
SELECT name, value FROM v$parameter
WHERE  name IN ('session_cached_cursors','open_cursors',
                'cursor_sharing','cursor_space_for_time');

ALTER SYSTEM SET session_cached_cursors = 100;

ALTER SYSTEM SET cursor_sharing = FORCE;

-- may prevent optimal histogram-driven plans

Interview Q&A

Performance Tuning — Interview Questions

High-frequency Oracle performance tuning questions covering AWR, wait events, parsing, and SQL tuning methodology.

A hard parse occurs when Oracle cannot find a matching execution plan in the Shared Pool for the incoming SQL. It must perform: (1) syntax check, (2) semantic check (validate objects/privileges), (3) optimization (CBO generates execution plan). Hard parses are CPU-intensive and involve a library cache latch — at high rates they cause severe library cache contention.

A soft parse occurs when Oracle finds a matching SQL hash in the library cache. It validates the SQL is still valid (objects unchanged) and reuses the existing execution plan. Much cheaper — avoids optimization overhead.

Ideal state: Hard parses should approach zero in a well-tuned OLTP system. Achieve this through bind variables, application connection pooling, and setting CURSOR_SHARING=FORCE as a stopgap for applications that don't use bind variables.

An AWR (Automatic Workload Repository) report is a snapshot-based performance report comparing two time intervals. It's generated via @$ORACLE_HOME/rdbms/admin/awrrpt.sql.

Key sections to review in order:

  1. DB Time and Load Profile: How busy was the database? DB Time >> Elapsed Time means CPU/IO bottleneck.
  2. Top 5 Wait Events: What were sessions waiting for most? CPU, I/O, lock waits, etc.
  3. SQL Statistics: Top SQL by Elapsed Time, CPU, Disk Reads. These are your tuning targets.
  4. Instance Efficiency Percentages: Buffer cache hit ratio, library cache hit ratio, parse ratios.
  5. Memory Statistics: SGA/PGA sizing, memory advisor recommendations.

A logical read is any access to a data block — whether it comes from the buffer cache (fast) or from disk (slow). Every physical read first becomes a logical read once in cache.

A physical read means the block was not in the buffer cache and had to be fetched from disk (or the OS file cache). Physical reads are typically 10–1000x slower than logical reads from RAM.

The buffer cache hit ratio = (logical reads - physical reads) / logical reads. A 99% hit ratio sounds good but is misleading — a poorly indexed query doing 1M logical reads per second is a problem even if 99% come from cache. Focus on reducing total logical reads (fix the SQL/index), not just improving hit ratio.

First identify blocking sessions using V$SESSION:

SELECT blocking_session, sid, wait_class, seconds_in_wait, sql_id
FROM v$session WHERE blocking_session IS NOT NULL;

Look at what SQL the blocking session is running. Common causes: (1) Long uncommitted transaction with row-level locks; (2) Missing commit after DML; (3) Application bug holding locks; (4) Deadlock (ORA-00060).

Resolution: (1) Ask the blocking user to commit/rollback; (2) Kill the blocking session: ALTER SYSTEM KILL SESSION 'sid,serial#' IMMEDIATE; (3) Long-term: reduce lock hold time, use SELECT FOR UPDATE NOWAIT or SKIP LOCKED to avoid blocking.

V$SESSION_WAIT shows what each currently active session is waiting on right now — one row per session. It's a point-in-time snapshot and is useful for diagnosing immediate, ongoing problems.

V$SYSTEM_EVENT shows cumulative wait statistics since instance startup for all wait events across all sessions. It shows total waits, total timeouts, time waited, and average wait time. This is ideal for trend analysis and understanding the overall wait profile of the database over time.

For performance tuning, use V$SYSTEM_EVENT to identify the worst cumulative waits, then drill into V$SESSION_WAIT for active sessions, and finally V$SQL_MONITOR or ASH (Active Session History) for SQL-level analysis.
