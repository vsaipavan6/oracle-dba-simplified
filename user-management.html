How It Works

Oracle’s Three-Layer Security Model

Oracle security is not just a CREATE USER command. It’s a layered system: a User gets Privileges either directly or through Roles, and a Profile enforces password and resource policies.

Oracle Security Architecture

How users, roles, privileges, and profiles connect in Oracle Database 19c

Password Authentication

IDENTIFIED BY

The default. Oracle stores a hashed version of the password. The user provides the password when connecting. Use this for most application and DBA accounts.

CREATE USER scott
  IDENTIFIED BY "Tiger#2024";

External Authentication

IDENTIFIED EXTERNALLY

Oracle delegates authentication to the OS. The OS username must match the Oracle username (or use OPS$ prefix). Used with Kerberos or OS-based auth in trusted environments.

CREATE USER ops$oracle
  IDENTIFIED EXTERNALLY;

Global Authentication

IDENTIFIED GLOBALLY

Oracle delegates authentication to a centralized directory service (Oracle Internet Directory / LDAP / Active Directory). Used in enterprise SSO setups with Oracle Advanced Security.

CREATE USER ldap_user
  IDENTIFIED GLOBALLY AS
  'CN=scott,OU=users,DC=corp';
Step 1

CREATE USER — Full Syntax

A user account is the entry point into the database. Every connection comes through a user. Getting the user definition right from the start saves a lot of rework.

Complete CREATE USER Syntax (Oracle 19c)

Purple = required keyword  |  Gray = optional clause  |  Green = your value  |  Blue = keyword option

CREATE USER username IDENTIFIED BY password | IDENTIFIED EXTERNALLY [AS 'certificate_distinguished_name'] | IDENTIFIED GLOBALLY [AS 'directory_distinguished_name'] [DEFAULT TABLESPACE tablespace_name] -- where user's objects are stored [TEMPORARY TABLESPACE temp_tablespace_name] -- for sort operations [LOCAL TEMPORARY TABLESPACE local_temp_name] -- RAC-specific (19c) [QUOTA { size_clause | UNLIMITED } ON tablespace_name] -- repeatable for multiple tablespaces [PROFILE profile_name] -- assign a password/resource profile [PASSWORD EXPIRE] -- force password change on first login [ACCOUNT { LOCK | UNLOCK }] -- default is UNLOCK [ENABLE EDITIONS] -- for Edition-Based Redefinition [CONTAINER = { CURRENT | ALL }]; -- CDB only: ALL = common user (C## required)

Clause-by-Clause Explained

DEFAULT TABLESPACE

Where the user’s objects (tables, indexes) are created if no tablespace is specified in CREATE TABLE. If omitted, Oracle uses the database default (usually USERS or SYSTEM — always set this explicitly).

TEMPORARY TABLESPACE

Used for sort operations, hash joins, and temporary segments. Always set to TEMP (or a named temp tablespace). If omitted, uses the database-wide default temporary tablespace.

QUOTA size ON tbs

Limits how much space the user can use in a tablespace. Use UNLIMITED for schema-owning users. Application users that don’t create objects need no quota. Specify multiple QUOTA clauses for multiple tablespaces.

PROFILE

Assigns a profile that governs password policy (max failed logins, expiry, reuse) and resource limits (max sessions, CPU time, idle time). If omitted, the DEFAULT profile is used.

PASSWORD EXPIRE

Forces the user to change their password on the very first connection. Use this for new accounts so the DBA-set initial password is changed immediately by the user. The user cannot do anything until they set a new password.

ACCOUNT LOCK

Prevents all logins immediately. Use this to create an account that will be set up later, or to immediately block a compromised or terminated-employee account. ALTER USER name ACCOUNT LOCK also works on existing users.

Real-World Examples

CREATE USER scenarios
-- Schema-owning application account
-- (holds the actual tables/objects)
CREATE USER hr_schema
  IDENTIFIED BY "HrSchema#2024"
  DEFAULT TABLESPACE   hr_data
  TEMPORARY TABLESPACE temp
  QUOTA UNLIMITED ON   hr_data
  QUOTA 200M ON         temp
  PROFILE              app_schema_profile
  ACCOUNT UNLOCK;

-- Read-only analyst (no object creation)
CREATE USER analyst_john
  IDENTIFIED BY "Analyst#Pwd1"
  DEFAULT TABLESPACE   users
  TEMPORARY TABLESPACE temp
  -- No QUOTA needed: john won't create objects
  PROFILE  standard_profile
  PASSWORD EXPIRE
  ACCOUNT UNLOCK;

-- Service account (app connects with this)
CREATE USER app_svc
  IDENTIFIED BY "SvcAcc#2024Sec"
  DEFAULT TABLESPACE   users
  TEMPORARY TABLESPACE temp
  PROFILE              svc_profile
  ACCOUNT UNLOCK;

-- Admin account to be activated later
CREATE USER backup_admin
  IDENTIFIED BY "Tmp#Pass2024"
  DEFAULT TABLESPACE   users
  TEMPORARY TABLESPACE temp
  PROFILE  dba_profile
  PASSWORD EXPIRE
  ACCOUNT LOCK;  -- Locked until needed

ALTER USER — Common Operations

-- Change password
ALTER USER scott IDENTIFIED BY "NewPass#1";

-- Force password change at next login
ALTER USER scott PASSWORD EXPIRE;

-- Lock / unlock account
ALTER USER scott ACCOUNT LOCK;
ALTER USER scott ACCOUNT UNLOCK;

-- Change default tablespace
ALTER USER scott DEFAULT TABLESPACE users;

-- Add/change quota
ALTER USER scott QUOTA 1G ON users;
ALTER USER scott QUOTA 0 ON users; -- remove quota

-- Change profile
ALTER USER scott PROFILE prod_profile;

-- Drop a user (CASCADE removes all objects)
DROP USER scott CASCADE;

       created, expiry_date
FROM   dba_users

       lock_date, profile
FROM   dba_users
WHERE  account_status LIKE '%LOCKED%';

-- Expired passwords (users can't login)

       expiry_date
FROM   dba_users
WHERE  account_status LIKE '%EXPIRED%';

-- Users NOT using DEFAULT profile
SELECT username, profile
FROM   dba_users
WHERE  profile != 'DEFAULT'
AND    account_status = 'OPEN';

-- Users with SYSTEM as default tablespace
-- (bad practice - find them)
SELECT username, default_tablespace
FROM   dba_users
WHERE  default_tablespace = 'SYSTEM'
AND    username NOT IN
       ('SYS','SYSTEM','DBSNMP','SYSMAN');
Section 3

System Privileges

System privileges grant the right to perform a particular action anywhere in the database — not tied to a specific object. Oracle 19c has over 200 system privileges. Understanding which ones are safe to grant and which are dangerous is a critical DBA skill.

System Privilege vs Object Privilege

A system privilege says "you can create tables anywhere". An object privilege says "you can SELECT from this specific table". Always grant object privileges when possible — system privileges are much broader and riskier.

GRANT / REVOKE Syntax

GRANT privilege_name [, privilege_name ...] TO { user | role | PUBLIC } [, ...] [WITH ADMIN OPTION] -- grantee can re-grant to others ; REVOKE privilege_name [, privilege_name ...] FROM { user | role | PUBLIC } [, ...] ;

ADMIN OPTION revoke does NOT cascade

If Alice was granted CREATE TABLE WITH ADMIN OPTION and re-granted it to Bob, revoking from Alice does not revoke from Bob. This is different from GRANT OPTION on object privileges (which does cascade). — Oracle Concepts Guide, Security chapter

These privileges control the ability to connect to and manage sessions in the database.

CREATE SESSION Required

The minimum privilege to connect to the database. Without this, a user account exists but login is impossible. Always the first privilege granted.

ALTER SESSION Session

Allows the user to change their own session parameters using ALTER SESSION SET parameter=value. Common for NLS settings, optimizer hints.

ALTER USER Admin

Allows modifying another user's account — password, profile, tablespace quota. Users can always alter their own password without this privilege.

RESTRICTED SESSION Admin

Allows connecting when the database is started in restricted mode (STARTUP RESTRICT). Used for maintenance windows where only DBAs should connect.

DDL privileges control schema object creation. Privileges prefixed with ANY operate across all schemas — use sparingly.

CREATE TABLE

Create tables in the user's own schema. Requires sufficient tablespace quota. Does NOT allow creating tables in other schemas.

CREATE ANY TABLE
ANY = any schema

Create a table in any schema. Dangerous — can be used to overwrite important objects in SYS or other privileged schemas.

CREATE VIEW / CREATE SEQUENCE

Create views and sequences in own schema. Views are commonly granted to application developers who need to encapsulate business logic.

CREATE PROCEDURE

Create stored procedures, functions, packages. Combined with EXECUTE ANY PROCEDURE this is extremely powerful — review carefully before granting.

CREATE INDEX / CREATE TRIGGER

Create indexes (affects query performance) and triggers (auto-executed PL/SQL). Triggers that call external procedures need additional network privileges.

CREATE SYNONYM / CREATE PUBLIC SYNONYM

Private synonyms alias objects in own schema. PUBLIC synonyms are visible to all users — granting CREATE PUBLIC SYNONYM should be tightly controlled.

Data privileges allow DML operations. The ANY variants cross schema boundaries — only grant to trusted application accounts or DBAs.

Privilege Scope Notes
SELECT ANY TABLE Very Broad Read any table in any schema including sensitive data. Commonly abused for data exfiltration. Avoid granting.
INSERT ANY TABLE Dangerous Insert into any table. Combined with SELECT ANY TABLE, allows full read-write access to all data.
UPDATE ANY TABLE Dangerous Modify any row in any table. Can alter audit logs, financial records, user accounts.
DELETE ANY TABLE Dangerous Delete rows from any table — destructive. TRUNCATE requires DROP ANY TABLE privilege.
EXECUTE ANY PROCEDURE Broad Run any stored procedure in any schema. Can invoke privileged SYS packages.
SELECT ANY DICTIONARY Sensitive Read data dictionary views (DBA_*). Exposes schema structures, passwords (hashed), audit config. Even excluded from GRANT ALL PRIVILEGES.
SELECT ANY SEQUENCE Low Risk Read sequence values from any schema. Generally low risk — sequence numbers are not secret.

Administrative privileges control the database itself. These are reserved for the DBA team only — never granted to application accounts.

ALTER DATABASE DBA only

Modify database configuration — add/rename datafiles, enable/disable archivelog, change character set. Extremely powerful.

ALTER SYSTEM DBA only

Change system parameters (ALTER SYSTEM SET ...), kill sessions, flush the shared pool. Key for performance tuning and emergency response.

CREATE TABLESPACE DBA

Create new tablespace storage containers. Granted to DBAs who manage storage. Misuse can create tablespaces that consume all disk space.

AUDIT SYSTEM Audit DBA

Enable/disable auditing for SQL statements and system events. Required for compliance setup. Should be separate from general DBA to enforce separation of duties.

CREATE ROLE Role Admin

Create new roles in the database. Used by security administrators to define new job-function roles. Combined with GRANT ANY ROLE, this is very powerful.

GRANT ANY PRIVILEGE High Risk

Grant any system privilege to any user or role. Effectively equivalent to DBA access. Only grant to the most trusted security administrators.

Special Admin Privileges: SYSDBA & SYSOPER

These are not regular system privileges — they are special authentication modes that bypass normal database security. Granted via GRANT SYSDBA TO username and stored in the external password file, not the data dictionary.

SYSDBA
  • • Connect when database is down (MOUNT/NOMOUNT)
  • • STARTUP / SHUTDOWN
  • • CREATE SPFILE / PFILE
  • • FLASHBACK DATABASE
  • • ALTER DATABASE ARCHIVELOG
  • • Full DBA system privileges
  • • Logs in as SYS
SYSOPER
  • • STARTUP / SHUTDOWN
  • • ALTER DATABASE OPEN/MOUNT/BACKUP
  • • CREATE SPFILE
  • • RECOVER DATABASE (no data access)
  • • Cannot view user data
  • • Logs in as PUBLIC (not SYS)
SQL*Plus — check password file users
-- Who has SYSDBA / SYSOPER access? (password file)
SELECT username, sysdba, sysoper, sysbackup, sysdg, syskm, sysrac
FROM   V$PWFILE_USERS
ORDER BY username;

-- Grant SYSDBA to a new DBA (adds to password file)
GRANT SYSDBA TO dba_jones;

-- Revoke SYSDBA
REVOKE SYSDBA FROM dba_jones;

-- Connect as SYSDBA (from OS or SQL*Plus)
-- sqlplus / AS SYSDBA   (OS authentication, no password needed if in dba group)
-- sqlplus sys/password@ORCL AS SYSDBA

Privileges That Should Never Be Granted to Application Accounts

The following privileges can cause serious security breaches or data loss if granted to non-DBA accounts. These are commonly flagged by Oracle security audits and STIG (Security Technical Implementation Guide) checks.

DROP ANY TABLE

Drop tables in any schema — permanently destroying data. Even with Flashback, recovery may be impossible if recyclebin is off.

TRUNCATE ANY TABLE
Requires DROP ANY TABLE

TRUNCATE bypasses the recycle bin and undo segments. Data is immediately unrecoverable. Often overlooked in privilege reviews.

ALTER ANY TABLE

Modify any table's structure — add/drop columns, disable constraints. Can break application logic across the entire database.

BECOME USER

Impersonate any user — used by Data Pump during import. Should only exist on the DATA_PUMP_OPERATOR_ROLE or dedicated import accounts.

ALTER ANY PROCEDURE

Recompile or replace stored code in any schema. Can inject malicious PL/SQL into existing trusted procedures.

CREATE ANY DIRECTORY

Create OS-level directory aliases. Combined with UTL_FILE, can read/write any file the Oracle OS user can access — a common data exfiltration path.

EXEMPT ACCESS POLICY

Bypass Oracle Virtual Private Database (VPD) row-level security policies. Users with this privilege see ALL rows even when VPD policies restrict them.

GRANT ANY OBJECT PRIVILEGE

Grant object privileges on objects owned by other users. Effectively allows the holder to grant themselves access to any data.

Security Audit Query — find dangerous privilege holders
-- Find all users/roles with dangerous system privileges
SELECT grantee, privilege, admin_option
FROM   DBA_SYS_PRIVS
WHERE  privilege IN (
         'DROP ANY TABLE',     'TRUNCATE ANY TABLE',
         'ALTER ANY TABLE',    'DELETE ANY TABLE',
         'CREATE ANY DIRECTORY','BECOME USER',
         'EXEMPT ACCESS POLICY','GRANT ANY PRIVILEGE',
         'GRANT ANY OBJECT PRIVILEGE', 'ALTER ANY PROCEDURE'
       )
ORDER BY grantee, privilege;

-- Find non-DBA users who have DBA role
SELECT grantee, granted_role, admin_option, default_role
FROM   DBA_ROLE_PRIVS
WHERE  granted_role = 'DBA'
AND    grantee NOT IN ('SYS','SYSTEM')
ORDER BY grantee;
Section 4

Object Privileges

Object privileges grant access to a specific object owned by a specific schema — a table, view, sequence, procedure, etc. This is the preferred way to grant access: precise and least-privilege by design.

Object Type Available Privileges Notes
TABLE SELECT, INSERT, UPDATE, DELETE, ALTER, INDEX, REFERENCES, FLASHBACK, DEBUG Most common. UPDATE/DELETE can be column-specific. REFERENCES allows creating FK constraints pointing to this table.
VIEW SELECT, INSERT, UPDATE, DELETE, FLASHBACK, DEBUG DML on a view requires the view to be updatable. Views are the primary way to restrict column/row access.
SEQUENCE SELECT, ALTER SELECT allows using NEXTVAL/CURRVAL. Common for application accounts that insert rows using sequence-generated PKs.
PROCEDURE / FUNCTION / PACKAGE EXECUTE, DEBUG EXECUTE on a package grants access to all public subprograms. Use AUTHID CURRENT_USER in the package to run as caller, not definer.
DIRECTORY READ, WRITE, EXECUTE Controls access to OS directory aliases for external files (Data Pump, UTL_FILE). WRITE is very sensitive — file overwrite possible.
TYPE / JAVA CLASS EXECUTE, UNDER, DEBUG UNDER allows creating subtypes. Java class EXECUTE needed to call Java stored procedures from SQL/PL/SQL.

Object Privilege Syntax

GRANT object_privilege [(column_list)] [, ...] ON [schema.]object_name TO { user | role | PUBLIC } [WITH GRANT OPTION] -- grantee can re-grant; revoke CASCADES ; REVOKE object_privilege [, ...] ON [schema.]object_name FROM { user | role | PUBLIC } [CASCADE CONSTRAINTS] -- remove FK constraints that depended on REFERENCES priv ;
SQL*Plus — object privilege examples
-- Grant SELECT on a table to a reporting user
GRANT SELECT ON hr.employees TO reporting_user;

-- Grant SELECT and INSERT on a specific table (app account)
GRANT SELECT, INSERT ON sales.orders TO app_salesdb;

-- Grant UPDATE on specific columns only (column-level privilege)
GRANT UPDATE (salary, commission_pct) ON hr.employees TO hr_manager;

-- Grant EXECUTE on a package
GRANT EXECUTE ON hr.emp_pkg TO app_salesdb;

-- Grant SELECT on a sequence (for INSERT with PK generation)
GRANT SELECT ON hr.employees_seq TO app_salesdb;

-- Grant with GRANT OPTION (receiver can re-grant to others)
GRANT SELECT ON hr.employees TO lead_dev WITH GRANT OPTION;

-- Revoke — GRANT OPTION revoke CASCADES to re-grantees
REVOKE SELECT ON hr.employees FROM lead_dev;  -- also revokes from anyone lead_dev granted to

-- Grant SELECT to all users (PUBLIC) — use with caution
GRANT SELECT ON app.reference_data TO PUBLIC;

-- Query: what object privileges has a specific user received?
SELECT owner, table_name, privilege, grantable
FROM   DBA_TAB_PRIVS
WHERE  grantee = 'REPORTING_USER'
ORDER BY owner, table_name;

-- Column-level object privileges
SELECT owner, table_name, column_name, privilege
FROM   DBA_COL_PRIVS
WHERE  grantee = 'HR_MANAGER';

WITH GRANT OPTION (Object Privs)

  • Allows re-granting the object privilege to others
  • Cannot be granted to a role (only users or PUBLIC)
  • Revoke CASCADES — all downstream grantees lose the privilege automatically
  • Visible in DBA_TAB_PRIVS as GRANTABLE='YES'

WITH ADMIN OPTION (System Privs)

  • Allows re-granting the system privilege to others
  • Can be granted to roles
  • Revoke does NOT cascade — downstream grantees keep the privilege
  • Visible in DBA_SYS_PRIVS as ADMIN_OPTION='YES'
Section 5

Roles

A role is a named collection of privileges and other roles. Instead of granting dozens of privileges individually to each user, you grant one role. When the role changes, all users with that role are automatically updated. Oracle 19c supports a maximum of 148 user-defined roles per user session simultaneously.

Simplify Management

Grant one role instead of 20 individual privileges. Revoke the role to immediately remove all access — one command.

Match Job Functions

Create roles named after real job roles (APP_READ_ROLE, HR_MANAGER_ROLE). Maps security configuration to the org chart.

Enable / Disable

Roles can be enabled/disabled per session with SET ROLE. A user can have a role but disable it temporarily.

Oracle Predefined Roles (19c)

Oracle ships with several built-in roles. You should know what each one actually contains — granting the wrong predefined role is a common mistake in production environments.

In Oracle 19c, CONNECT only contains 2 privileges. This is very different from older versions (8i/9i) where CONNECT had many more privileges. Always verify what CONNECT means in your specific version.

CREATE SESSION

Allows connecting to the database

SET CONTAINER

Switch between PDBs in multitenant (CDB) environments

SELECT privilege FROM DBA_SYS_PRIVS WHERE grantee = 'CONNECT';

RESOURCE allows creating schema objects. It also grants UNLIMITED TABLESPACE — which overrides tablespace quotas and allows the user to use any amount of space in any tablespace. Often granted more than necessary.

CREATE TABLE
CREATE CLUSTER
CREATE SEQUENCE
CREATE PROCEDURE

UNLIMITED TABLESPACE⚠ Often overlooked — grants unlimited space in all tablespaces

The DBA role contains most system privileges (200+) with ADMIN OPTION. It is the most powerful role in the database short of SYSDBA. Never grant DBA to application accounts or general users.

Includes all CREATE ANY, DROP ANY, ALTER ANY, SELECT ANY, INSERT ANY, UPDATE ANY, DELETE ANY, EXECUTE ANY, GRANT ANY and hundreds more. The DBA role also includes the RESOURCE, CONNECT, and EXP_FULL_DATABASE roles.

-- How many privileges does DBA contain?
SELECT COUNT(*) FROM DBA_SYS_PRIVS WHERE grantee = 'DBA';

Required for full database exports and imports using Oracle Data Pump (expdp/impdp). These are sensitive roles that grant access to all data.

EXP_FULL_DATABASE
  • • SELECT ANY TABLE (read all data)
  • • BACKUP ANY TABLE
  • • EXECUTE ANY PROCEDURE
  • • EXECUTE ANY TYPE
IMP_FULL_DATABASE
  • • BECOME USER
  • • CREATE ANY TABLE / INDEX
  • • INSERT ANY TABLE / UPDATE ANY TABLE
  • • DROP ANY TABLE

Grants SELECT access to most DBA_* and V$ views. Common for monitoring tools, DBAs who need read-only access to dictionary, and middleware accounts that query metadata. Safer alternative to SELECT ANY DICTIONARY privilege.

GRANT SELECT_CATALOG_ROLE TO monitoring_user;

Creating Custom Roles

CREATE ROLE role_name [NOT IDENTIFIED -- default: no password needed to activate | IDENTIFIED BY password -- password required to SET ROLE | IDENTIFIED USING pkg -- application-level role (PL/SQL package gate) | IDENTIFIED EXTERNALLY -- OS/directory group membership controls activation | IDENTIFIED GLOBALLY -- Oracle Internet Directory (OID/LDAP) group] ;
Real-world custom role examples
-- 1. Read-only reporting role
CREATE ROLE app_reporting_role;
GRANT SELECT ON sales.orders          TO app_reporting_role;
GRANT SELECT ON sales.order_items     TO app_reporting_role;
GRANT SELECT ON hr.employees          TO app_reporting_role;
-- Grant the role to all reporting users
GRANT app_reporting_role TO alice, bob, carol;

-- 2. Application DML role (read + write to specific tables)
CREATE ROLE crm_app_role;
GRANT SELECT, INSERT, UPDATE ON crm.customers  TO crm_app_role;
GRANT SELECT, INSERT          ON crm.contacts   TO crm_app_role;
GRANT EXECUTE                 ON crm.crm_pkg    TO crm_app_role;
GRANT crm_app_role TO app_crm_user;

-- 3. Password-protected role (application must call SET ROLE to activate)
CREATE ROLE admin_ops_role IDENTIFIED BY "Str0ngRoleP@ss";
GRANT DELETE ON audit.log_archive TO admin_ops_role;
GRANT admin_ops_role TO dba_ops;
-- dba_ops must activate the role in their session:
SET ROLE admin_ops_role IDENTIFIED BY "Str0ngRoleP@ss";

-- 4. Role nesting (role within a role)
CREATE ROLE senior_dev_role;
GRANT app_reporting_role TO senior_dev_role;  -- inherit all reporting privs
GRANT CREATE TABLE, CREATE VIEW       TO senior_dev_role;
GRANT senior_dev_role TO dev_smith;

-- 5. Drop a role (revoked from all grantees automatically)
DROP ROLE old_legacy_role;

-- Query: what roles and privileges does a user have?
SELECT granted_role, admin_option, default_role
FROM   DBA_ROLE_PRIVS
WHERE  grantee = 'DEV_SMITH'
ORDER BY granted_role;

-- Query: what privileges are inside a role?
SELECT privilege, admin_option
FROM   DBA_SYS_PRIVS
WHERE  grantee = 'CRM_APP_ROLE'
UNION ALL
SELECT owner || '.' || table_name || ' (' || privilege || ')', 'NO'
FROM   DBA_TAB_PRIVS
WHERE  grantee = 'CRM_APP_ROLE';

Roles vs Direct Privileges — When to Use Which

Scenario Use Role Use Direct Privilege
Many users need same access ✓ Grant one role to all Tedious — N×M grants
Access needed inside a stored procedure/definer-rights view ✗ Role privs inactive in definer-rights objects ✓ Direct grant required
Application service account ✓ Grant app role — easy to audit Acceptable but harder to maintain
WITH GRANT OPTION needed (re-grant) ✗ Roles cannot use GRANT OPTION ✓ Only direct grants support GRANT OPTION
Revoking all access instantly ✓ Drop role or revoke role — one step Must revoke each privilege individually

Key Rule: Definer-Rights Objects

If a stored procedure runs with AUTHID DEFINER (the default), it executes with the owner's privileges — but role privileges are NOT active inside definer-rights PL/SQL. This means if the owner has a role granting SELECT on a table, the procedure still cannot query it. You must GRANT the privilege directly to the schema owner for the procedure to work. — Oracle PL/SQL Language Reference, Security Model

Section 6

Profiles

A profile is a set of limits assigned to a user account. It controls two things: password policy (complexity, expiry, lockout) and resource limits (CPU time, idle time, connections). Every user has exactly one profile — the default is the DEFAULT profile.

Resource limits only enforce when RESOURCE_LIMIT = TRUE (ALTER SYSTEM SET RESOURCE_LIMIT=TRUE). Password limits always enforce regardless of this parameter.

Password Parameters

Always active — enforce independently of RESOURCE_LIMIT. These are the parameters you configure for Oracle security compliance.

  • FAILED_LOGIN_ATTEMPTS Account locked after N failed attempts
  • PASSWORD_LIFE_TIME Days before password expires
  • PASSWORD_REUSE_TIME Days before reusing a password
  • PASSWORD_REUSE_MAX Min changes before reuse
  • PASSWORD_LOCK_TIME Days account stays locked
  • PASSWORD_GRACE_TIME Grace days after expiry
  • PASSWORD_VERIFY_FUNCTION PL/SQL complexity checker
  • INACTIVE_ACCOUNT_TIME Lock after N days no login (19c)
  • PASSWORD_ROLLOVER_TIME Old password still works during rollover

Resource Parameters

Only active when RESOURCE_LIMIT=TRUE. Used to prevent runaway sessions from consuming excessive database resources.

  • SESSIONS_PER_USER Concurrent sessions per account
  • CPU_PER_SESSION CPU time (hundredths of seconds)
  • CPU_PER_CALL CPU per single SQL call
  • LOGICAL_READS_PER_SESSION Block reads per session
  • LOGICAL_READS_PER_CALL Block reads per SQL call
  • IDLE_TIME Minutes before idle disconnect
  • CONNECT_TIME Total minutes per session
  • PRIVATE_SGA SGA memory (bytes) per session
  • COMPOSITE_LIMIT Weighted sum of CPU + reads

Password Verify Functions — What They Check

Oracle ships PL/SQL functions that validate password complexity when a user sets their password. These must be created by running a script from $ORACLE_HOME/rdbms/admin/catpvf.sql (12.2+) or utlpwdmg.sql (older versions). They are installed in the SYS schema.

ora12c_stig_verify_function

Strictest — for STIG compliance. Minimum 15 characters, must contain uppercase, lowercase, digit, and special character. Checks against username. Used by government and defense.

ora12c_strong_verify_function

Strong but practical. Minimum 8 characters, requires at least 1 uppercase, 1 lowercase, 1 digit, 1 special character. Common in enterprise environments.

ora_complexity_check

Helper function called by the above. Can also be used directly. Configurable minimum lengths and character requirements for custom verify functions.

-- Create the password verify functions (run as SYSDBA)
@$ORACLE_HOME/rdbms/admin/catpvf.sql

-- Verify functions are now in SYS schema
SELECT object_name FROM DBA_OBJECTS
WHERE  owner = 'SYS' AND object_type = 'FUNCTION'
AND    object_name LIKE 'ORA%VERIFY%';

INACTIVE_ACCOUNT_TIME (Oracle 12.2+)

Automatically locks an account that has not been used for the specified number of days. Range: 15 to 24,855 days. This is a key control for dormant accounts — one of the most common security vulnerabilities in Oracle databases.

Example: Set to 35 days (STIG requirement)

-- Find dormant accounts (not logged in recently)
SELECT username, last_login, account_status
FROM   DBA_USERS
WHERE  last_login < SYSDATE - 90
OR     last_login IS NULL
ORDER BY last_login;

LOCKED(TIMED)Account locked by inactivity timer
OPENAccount is active and accessible
EXPIRED & LOCKEDPassword expired and account locked
EXPIRED(GRACE)In grace period — must change password
Section 7

CDB / PDB User Management

Oracle 12c introduced Multitenant architecture — one Container Database (CDB) hosting multiple Pluggable Databases (PDBs). User management changes significantly in this architecture: you can create users at the CDB level (common users) or at the PDB level (local users).

Common users (C## prefix) exist across all PDBs. Local users exist only in their own PDB.

CDB / PDB user management commands
-- 1. Create a common user (must use C## prefix, created in CDB$ROOT)
--    Must connect to CDB$ROOT as SYSDBA first
ALTER SESSION SET CONTAINER = CDB$ROOT;

CREATE USER C##DBA_JONES
  IDENTIFIED BY "SecureP@ss2024"
  CONTAINER = ALL;                  -- exists in all current + future PDBs

GRANT CREATE SESSION TO C##DBA_JONES CONTAINER=ALL;
GRANT DBA TO C##DBA_JONES CONTAINER=ALL;

-- 2. Create a local user (inside a specific PDB)
ALTER SESSION SET CONTAINER = HRPDB;

CREATE USER hr_analyst                 -- no C## prefix for local users
  IDENTIFIED BY "HrPass2024!"
  DEFAULT TABLESPACE users
  QUOTA 500M ON users;

GRANT CREATE SESSION, SELECT ON hr.employees TO hr_analyst;

-- 3. Grant privilege to common user in ONE PDB only
ALTER SESSION SET CONTAINER = HRPDB;
GRANT CREATE TABLE TO C##DBA_JONES CONTAINER=CURRENT;

-- 4. Switch containers from inside SQL*Plus
ALTER SESSION SET CONTAINER = SALESPDB;

-- 5. Show current container
SELECT SYS_CONTEXT('USERENV','CON_NAME') AS current_container FROM DUAL;

-- 6. List all PDBs in the CDB
SELECT pdb_id, pdb_name, status, open_mode
FROM   DBA_PDBS
ORDER BY pdb_id;

-- 7. View common users vs local users
SELECT username, common, con_id, account_status
FROM   CDB_USERS
WHERE  common = 'YES'  -- common users
ORDER BY username;

SELECT username, common, con_id, account_status
FROM   CDB_USERS
WHERE  common = 'NO'   -- local PDB users
ORDER BY con_id, username;

Common User Rules

  • Name must start with C## (case-insensitive)
  • Created in CDB$ROOT — visible in all PDBs
  • Privileges granted with CONTAINER=ALL apply everywhere
  • Privileges granted with CONTAINER=CURRENT apply only in that PDB
  • Can connect to both CDB$ROOT and any PDB they have CREATE SESSION for

Local User Rules

  • Name must NOT start with C## (enforced by Oracle)
  • Exists only in the PDB where created
  • Cannot connect to CDB$ROOT
  • Cannot be granted CONTAINER=ALL privileges
  • Preferred for application accounts — isolated per PDB
Section 8

Oracle Security Best Practices

Security in Oracle is not a one-time configuration — it is an ongoing practice. This section covers the key controls recommended by Oracle documentation and STIG (Security Technical Implementation Guide) standards used by enterprises and government agencies.

1. Principle of Least Privilege

Every user and application account should have only the privileges required to perform their job — no more. This limits the "blast radius" of a compromised account.

Wrong approach

GRANT DBA TO app_user — "It works, ship it."

Wrong approach

GRANT SELECT ANY TABLE TO reporting_user — "They need to see all data."

Wrong approach

Sharing one application user account among multiple team members.

Correct approach

Grant only CREATE SESSION + specific object privileges needed for the job.

Correct approach

Use views to expose only required columns/rows, then GRANT SELECT on the view.

Correct approach

One database account per person — enables individual auditing and accountability.

2. Lock and Expire Default Oracle Accounts

Oracle ships with many pre-defined accounts — sample schemas (HR, OE, PM, SH), internal accounts (ANONYMOUS, DBSNMP), and utility accounts. Any account not actively used should be locked and expired.

Finding and locking default accounts
-- Find users with KNOWN DEFAULT passwords (Oracle maintains this view)
SELECT username, account_status
FROM   DBA_USERS_WITH_DEFPWD
ORDER BY username;

-- Lock sample schema accounts that are open
ALTER USER HR        ACCOUNT LOCK PASSWORD EXPIRE;
ALTER USER OE        ACCOUNT LOCK PASSWORD EXPIRE;
ALTER USER PM        ACCOUNT LOCK PASSWORD EXPIRE;
ALTER USER SH        ACCOUNT LOCK PASSWORD EXPIRE;
ALTER USER IX        ACCOUNT LOCK PASSWORD EXPIRE;
ALTER USER SCOTT     ACCOUNT LOCK PASSWORD EXPIRE;
ALTER USER ANONYMOUS ACCOUNT LOCK;
ALTER USER DBSNMP    ACCOUNT LOCK PASSWORD EXPIRE;  -- only lock if not using OEM

-- Find all accounts that are currently OPEN (should be minimal set)
SELECT username, account_status, last_login, profile
FROM   DBA_USERS
WHERE  account_status = 'OPEN'
ORDER BY username;

SYSTEM account best practice

Never use SYSTEM for day-to-day DBA work. Create named DBA accounts (john_dba, jane_dba). Grant DBA role or grant SYSDBA via password file. The SYSTEM account should only be used for emergencies and its use should trigger an alert.

3. Enable and Configure Unified Auditing (12c+)

Oracle Unified Auditing (introduced in 12c) replaces traditional auditing. It captures all audit events in UNIFIED_AUDIT_TRAIL and provides predefined audit policies for common compliance requirements.

ORA_SECURECONFIG Default ON

Audits sensitive system configuration changes — ALTER SYSTEM, CREATE/ALTER/DROP ROLE, GRANT/REVOKE ANY PRIVILEGE, CREATE/ALTER PROFILE, and other security-sensitive DDL.

ORA_DATABASE_PARAMETER Default ON

Audits changes to database initialization parameters using ALTER SYSTEM. Critical for detecting unauthorized performance or security parameter changes.

ORA_ACCOUNT_MGMT Configurable

Audits user account management — CREATE/ALTER/DROP USER, GRANT ROLE, failed logins. Essential for access management compliance.

Unified Audit policy commands
-- Check which unified audit policies are enabled
SELECT policy_name, enabled_opt, user_name
FROM   AUDIT_UNIFIED_ENABLED_POLICIES
ORDER BY policy_name;

-- Enable the account management audit policy for all users
AUDIT POLICY ORA_ACCOUNT_MGMT;

-- Create a custom audit policy for DML on a sensitive table
CREATE AUDIT POLICY audit_payroll_dml
  ACTIONS SELECT, INSERT, UPDATE, DELETE
  ON hr.payroll
  WHEN 'SYS_CONTEXT(''USERENV'',''SESSION_USER'') != ''HR'''
  EVALUATE PER SESSION;
AUDIT POLICY audit_payroll_dml;

-- Query the audit trail for failed logins
SELECT event_timestamp, db_user_name, client_ip, action_name,
       return_code, unified_audit_policies
FROM   UNIFIED_AUDIT_TRAIL
WHERE  action_name = 'LOGON'
AND    return_code != 0
AND    event_timestamp > SYSDATE - 1
ORDER BY event_timestamp DESC;

4. Separation of Duties

No single person should have unchecked end-to-end control. Apply SoD to your Oracle DBA team:

DBA (Database Administrator)

Instance management, storage, performance tuning, backup. Has SYSDBA but not security policy control.

Security Administrator

Manages users, roles, profiles, audit policies. Has GRANT ANY PRIVILEGE but not SYSDBA.

Audit Administrator

Reviews audit trails, creates audit policies. READ-ONLY access to UNIFIED_AUDIT_TRAIL. Cannot modify database config.

5. Regular Privilege Reviews

Privileges accumulate over time ("privilege creep"). Schedule quarterly reviews:

-- Users with DBA role (non-standard)
SELECT grantee FROM DBA_ROLE_PRIVS
WHERE  granted_role='DBA'
AND    grantee NOT IN('SYS','SYSTEM');

-- Unused accounts (90 days no login)
SELECT username, last_login
FROM   DBA_USERS
WHERE  last_login < SYSDATE-90
AND    account_status='OPEN';

-- Default password accounts still open
SELECT username FROM DBA_USERS_WITH_DEFPWD
WHERE  account_status='OPEN';

A schema-only account (introduced in Oracle 18c) cannot log in to the database. It owns objects, but application code connects as a separate service account and accesses the schema via synonyms or explicit schema prefixes. This is a modern security best practice.

Schema-only account pattern (Oracle 18c+)
-- 1. Create the schema-only account (NO AUTHENTICATION = cannot log in)
CREATE USER inventory_schema
  NO AUTHENTICATION              -- no password, cannot log in directly
  DEFAULT TABLESPACE app_data
  QUOTA UNLIMITED ON app_data;

-- 2. Create the objects in the schema
-- (Connect as DBA and create tables on behalf of schema_owner)
CREATE TABLE inventory_schema.products (
  product_id   NUMBER        PRIMARY KEY,
  product_name VARCHAR2(200) NOT NULL,
  qty_on_hand  NUMBER        DEFAULT 0
);

-- 3. Create the service account that the app actually uses
CREATE USER svc_inventory_app
  IDENTIFIED BY "Inv@ppS3rv1ce#"
  PROFILE svc_account_profile
  DEFAULT TABLESPACE users
  QUOTA 0 ON users;

GRANT CREATE SESSION TO svc_inventory_app;

-- 4. Grant the service account access to schema_owner's objects
GRANT SELECT, INSERT, UPDATE ON inventory_schema.products TO svc_inventory_app;

-- 5. App accesses via explicit prefix: inventory_schema.products
-- Or create synonyms in app's schema for convenience
CREATE SYNONYM svc_inventory_app.products
  FOR inventory_schema.products;

-- Verify: account_status = 'NONE' for schema-only accounts
SELECT username, authentication_type, account_status
FROM   DBA_USERS
WHERE  username = 'INVENTORY_SCHEMA';

Interview Q&A

User & Security Management — Interview Questions

Top Oracle security and user management questions asked in DBA interviews covering schemas, profiles, privileges, and VPD.

In Oracle, a user and a schema are tightly coupled — when you create a user, Oracle automatically creates a schema of the same name. However, they represent different concepts:

  • A user is a database account with credentials (password, profile, default tablespace) that can connect to the database.
  • A schema is the logical namespace that owns database objects (tables, indexes, views, procedures). It has the same name as its owner user.

You can have a schema without a live user (if the account is locked) — the objects still exist. In some organizations, schema owners are locked accounts used only for object ownership, while separate application users (with limited privileges) do the actual connecting. This is a security best practice.

Oracle implements password policies through Profiles assigned to users. The PASSWORD_VERIFY_FUNCTION in the profile points to a PL/SQL function that validates password complexity.

Oracle provides built-in functions: ORA12C_STRONG_PASSWORD_VERIFY_FUNCTION (12c+) enforces: minimum 9 characters, mixed case, at least 1 digit, at least 1 special character, cannot contain username or DB name. Profile also controls:

  • PASSWORD_LIFE_TIME — days before expiry
  • FAILED_LOGIN_ATTEMPTS — lock after N failures
  • PASSWORD_REUSE_TIME / PASSWORD_REUSE_MAX — prevent reuse
  • PASSWORD_LOCK_TIME — how long account stays locked

System privileges grant the ability to perform database-wide operations: CREATE SESSION, CREATE TABLE, CREATE ANY TABLE, ALTER DATABASE. The ANY variants (e.g., SELECT ANY TABLE) are dangerous — grant sparingly. Tracked in DBA_SYS_PRIVS.

Object privileges grant specific access to individual objects: SELECT ON hr.employees, EXECUTE ON dbms_stats. Tracked in DBA_TAB_PRIVS. The WITH GRANT OPTION allows the grantee to further grant the privilege — use carefully.

Best practice: Use roles to group related privileges. Grant roles rather than direct system privileges. Follow principle of least privilege — grant only what the application needs.

Virtual Private Database (VPD), also called Fine-Grained Access Control (FGAC), allows Oracle to transparently append a WHERE clause predicate to every query against a protected table — based on the session context (e.g., user's department, region, or role).

You implement VPD by creating a PL/SQL policy function that returns a predicate string, then attaching it to a table via DBMS_RLS.ADD_POLICY. For example:

FUNCTION dept_filter(p_schema IN VARCHAR2, p_object IN VARCHAR2)
RETURN VARCHAR2 IS
BEGIN
  RETURN 'department_id = SYS_CONTEXT(''USERENV'',''CLIENT_INFO'')';
END;
-- Every SELECT on employees auto-gets: WHERE department_id = :user_dept

VPD is transparent to the application — users cannot see or bypass the predicate. The filtering happens in the kernel before results are returned.

Oracle ships with dozens of pre-created accounts for its built-in components (XDB, APEX, SYSMAN, etc.) — many with well-known default passwords. If an attacker can reach your listener port, they may connect using default credentials and gain DBA or schema access.

Security hardening steps: (1) Change passwords for SYS, SYSTEM, DBSNMP immediately; (2) Lock all unused accounts with ALTER USER <user> ACCOUNT LOCK PASSWORD EXPIRE; (3) Check for accounts with default passwords:

SELECT username, account_status FROM dba_users_with_defpwd
WHERE account_status NOT LIKE '%LOCKED%';
