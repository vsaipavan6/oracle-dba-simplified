Section 1

SPFILE vs PFILE

Always use SPFILE in production — it persists dynamic parameter changes and survives restarts without manual editing.

Key Differences

FeatureSPFILEPFILE
FormatBinaryText (editable)
ALTER SYSTEM SETPersistsLost on restart
RAC SupportYes (shared)Per-node only
Manual EditNot directlyYes (vi/notepad)
ASM StorageSupportedLocal FS only
Production UseAlwaysTesting/recovery

SPFILE Management

-- Create SPFILE from PFILE
CREATE SPFILE FROM PFILE='/tmp/init.ora';

-- Create PFILE from SPFILE (for backup/editing)
CREATE PFILE='/tmp/init_backup.ora'
FROM SPFILE;

-- Alter parameter — both memory and spfile
ALTER SYSTEM SET db_cache_size=2G SCOPE=BOTH;

-- Scope options:
-- MEMORY  — current instance only (no restart)
-- SPFILE  — persists after restart (no immediate effect)
-- BOTH    — now + persists (for dynamic parameters)

-- Reset a parameter to default
ALTER SYSTEM RESET db_cache_size SCOPE=SPFILE;

Section 3

Memory Configuration

Oracle offers three memory management modes. ASMM (Automatic Shared Memory Management) is recommended for most production environments.

Manual Memory

Set each SGA component individually (db_cache_size, shared_pool_size, etc.). Full control but requires constant tuning.

Legacy

ASMM (Recommended)

Set SGA_TARGET + PGA_AGGREGATE_TARGET. Oracle auto-resizes SGA components based on workload demand.

Best Practice

AMM (MEMORY_TARGET)

Oracle manages total SGA+PGA automatically. Not recommended on Linux with HugePages (incompatible).

Avoid on Linux
ASMM Configuration 
-- Configure ASMM (recommended)
-- Set SGA_TARGET — Oracle auto-sizes components
ALTER SYSTEM SET sga_target=8G SCOPE=BOTH;

-- Set PGA_AGGREGATE_TARGET — workarea limit for all sessions
ALTER SYSTEM SET pga_aggregate_target=2G SCOPE=BOTH;

-- Make sure MEMORY_TARGET=0 (disable AMM)
ALTER SYSTEM SET memory_target=0 SCOPE=SPFILE;

-- View current SGA component sizes
SELECT component,
       ROUND(current_size/1024/1024,0) current_mb,
       ROUND(min_size/1024/1024,0) min_mb,
       ROUND(max_size/1024/1024,0) max_mb,
       last_oper_type, last_oper_mode
FROM   v$sga_dynamic_components
WHERE  current_size > 0;
Section 4

Undo Management

Undo enables read consistency, flashback, and transaction rollback. Always use Automatic Undo Management (AUM) in production.

Undo Key Concepts

  • Read Consistency: Long-running queries see a consistent snapshot. Undo holds the before-image of modified rows.
  • ORA-01555 (Snapshot Too Old): Undo was overwritten before query could read it. Fix: increase UNDO_RETENTION or undo tablespace size.
  • UNDO_RETENTION: Minimum seconds Oracle tries to keep undo. Not guaranteed unless RETENTION GUARANTEE is set.
  • Retention Guarantee: ALTER TABLESPACE undotbs1 RETENTION GUARANTEE — never overwrites unexpired undo, may cause "can't extend" errors.

Undo Sizing & Monitoring

-- Check undo retention and usage
SELECT tablespace_name,
       status, retention,
       ROUND(blocks*8192/1024/1024,1) size_mb
FROM   dba_tablespaces
WHERE  contents = 'UNDO';

-- Monitor undo usage and expiry
SELECT status,
       SUM(blocks)*8/1024 mb,
       COUNT(*) extents
FROM   dba_undo_extents
GROUP BY status;

-- Calculate recommended undo size
-- Formula: (undo_retention * undo_block_rate * block_size) + overhead
SELECT ROUND((MAX(undoblks/DECODE(tuned_undoretention,0,1,tuned_undoretention))
       * 900 * 8192/1024/1024/1024),2) recommended_gb
FROM   v$undostat;
Section 5

Online Redo Log Configuration

Redo logs protect committed transactions. Proper sizing eliminates log switch contention — the #1 redo bottleneck.

Redo Log Best Practices

  • Minimum 3 log groups — never fewer
  • 2 members per group (multiplexing) — on different disks for protection
  • Target log switches every 15-30 minutes under normal load
  • OLTP: 200MB-500MB per member; DW: 1-4GB
  • Watch for checkpoint not complete in alert log — add groups or increase size

Redo Log Management

-- View current log groups and size
SELECT l.group#, l.members, l.status,
       ROUND(l.bytes/1024/1024,0) size_mb,
       lf.member
FROM   v$log l JOIN v$logfile lf ON l.group# = lf.group#;

-- Add a new log group (500MB)
ALTER DATABASE ADD LOGFILE GROUP 4
  ('/u03/redo/redo04a.log', '/u04/redo/redo04b.log')
  SIZE 500M;

-- Drop old (INACTIVE) group
ALTER DATABASE DROP LOGFILE GROUP 1;

-- Check log switch frequency
SELECT TO_CHAR(first_time,'YYYY-MM-DD HH24') hour,
       COUNT(*) switches
FROM   v$log_history
WHERE  first_time > SYSDATE-1
GROUP BY TO_CHAR(first_time,'YYYY-MM-DD HH24')
ORDER BY 1;
Section 6

Database Configuration — Interview Q&A

PFILE (init.ora) is a text file — readable and directly editable but changes made via ALTER SYSTEM are lost on restart. SPFILE (spfile.ora) is binary — not directly editable but persists all ALTER SYSTEM SET changes automatically. In production, always use SPFILE. If SPFILE is corrupted, create a new one from a PFILE backup using CREATE SPFILE FROM PFILE.

ORA-01555 "snapshot too old" means a long-running query could not reconstruct the read-consistent snapshot of a row because the undo data was overwritten. Fixes: (1) Increase UNDO_RETENTION (e.g., ALTER SYSTEM SET undo_retention=3600); (2) Add space to the undo tablespace so undo is retained longer; (3) Set RETENTION GUARANTEE on the undo tablespace; (4) Optimize the long-running query to complete faster; (5) Avoid fetching across commits in application code.

"Log file sync" means sessions are waiting for LGWR to write redo to the online redo log — triggered by COMMIT. Causes: (1) LGWR I/O is slow — move redo logs to faster storage (SSD/NVMe); (2) Too many commits — batch commits in application; (3) Redo log size too small causing frequent switches — increase log size; (4) LGWR competing with other I/O — dedicate storage. Monitor with: SELECT event, total_waits, time_waited FROM v$system_event WHERE event='log file sync'.

  • SCOPE=MEMORY: Takes effect immediately in current instance but not saved to SPFILE — lost on restart
  • SCOPE=SPFILE: Saved to SPFILE (persists across restarts) but doesn't take effect until next startup — used for static parameters
  • SCOPE=BOTH: Takes effect immediately AND saved to SPFILE — use for dynamic parameters you want to persist
  • If using PFILE (no SPFILE), only SCOPE=MEMORY is valid
