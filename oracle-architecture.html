Instance vs Database

What Is an Oracle Database?

Oracle separates two fundamental concepts that beginners often confuse — the Instance (memory + processes) and the Database (physical files on disk).

Oracle Instance

Memory + Background Processes

An instance is a set of memory structures and background processes that manage database files. It exists only in memory — when you shut down the instance, it disappears. An instance can exist without database files, and vice versa.

SGA — System Global Area (shared memory)
PGA — Program Global Area (per-process memory)
Background Processes — PMON, SMON, DBWn, LGWR…
Server Processes — handle client SQL requests
SQL*Plus
SELECT instance_name, status, version
FROM   v$instance;

-- OUTPUT:
-- INSTANCE_NAME  STATUS   VERSION
-- ORCL           OPEN     19.0.0.0.0

Oracle Database

Physical Files on Disk

The database is a set of physical files on disk — data files, control files, redo log files. It persists even when the instance is shut down. The database can exist independently of any running instance.

Data Files (.dbf) — SYSTEM, SYSAUX, USERS, UNDO, TEMP
Control Files — metadata about the database structure
Online Redo Logs — record every change made
Archive Logs — historical redo for point-in-time recovery
SQL*Plus
SELECT name, db_unique_name, open_mode
FROM   v$database;

-- OUTPUT:
-- NAME  DB_UNIQUE_NAME  OPEN_MODE
-- ORCL  ORCL            READ WRITE

Key Insight: 1 Instance ↔ 1 Database (or N Instances in RAC)

In a single-instance setup, one instance manages one database. In Oracle RAC (Real Application Clusters), multiple instances running on separate server machines share a single database — providing high availability and horizontal scalability.

Memory Architecture

System Global Area (SGA)

The SGA is the heart of the Oracle instance — a shared read/write memory area allocated at instance startup and shared by ALL server and background processes.

Check SGA at startup
-- View all SGA components
SELECT name, ROUND(bytes/1024/1024,1) AS mb
FROM   v$sgainfo ORDER BY bytes DESC;

SHOW parameter sga_target;
SHOW parameter memory_target;
-- Example output:
NAME                     MB
------------------------ ------
Maximum SGA Size         8192.0
Total SGA Size           8000.0
Database Buffers         5120.0
Shared Pool Size         1536.0
Large Pool Size          128.0
Java Pool Size            64.0
Redo Buffers              16.8

Shared Pool

Involved in EVERY database operation

Caches parsed SQL, PL/SQL code, system parameters, and data dictionary information. A soft parse (library cache hit) reuses existing parsed code. A hard parse (miss) rebuilds execution plan from scratch — expensive.

Library Cache

Stores executable SQL and PL/SQL code. Multiple private SQL areas in separate PGAs can point to one shared SQL area here. Contains shared SQL areas, PL/SQL code, locks, and library cache handles.

Data Dictionary Cache (Row Cache)

Stores rows of database object information — tables, columns, users, privileges. Called "row cache" because it holds data as rows, not blocks. Hit on every SQL parse.

Server Result Cache

Holds complete result sets of SQL queries and PL/SQL functions. If underlying data unchanged, returns cached result instantly — zero I/O, zero CPU recalculation.

Reserved Pool

Small area for large contiguous memory allocations (>5 KB). Prevents fragmentation for large PL/SQL packages, Java classes, and large cursors.

-- Library cache hit ratio (target >99%)
SELECT ROUND((1 - SUM(reloads) /
       SUM(pins)) * 100, 2) "Hit%"
FROM   v$librarycache;

-- Top shared pool consumers
SELECT name, ROUND(bytes/1024/1024,1) mb
FROM   v$sgastat
WHERE  pool = 'shared pool'
ORDER BY bytes DESC FETCH FIRST 10 ROWS ONLY;

-- Hard parse rate
SELECT name, value FROM v$sysstat
WHERE  name IN ('parse count (hard)',
                'parse count (total)');

-- Flush (use with care in production!)
ALTER SYSTEM FLUSH shared_pool;

Use bind variables to convert hard parses to soft parses. One SQL template with bind variables = one shared SQL area for thousands of executions.

Database Buffer Cache

Largest SGA component · caches 8KB data blocks from disk

Stores copies of data blocks read from data files. All users share the same cache. Goal: keep frequently accessed blocks in memory (cache hit = fast), write cold blocks to disk (cache miss = read from disk = slow). Uses LRU + touch count algorithm.

Default Pool

Normal caching. Default block size 8KB. LRU manages eviction. Hot blocks stay; cold blocks age out.

Keep Pool

For frequently accessed blocks that age out of default pool. Pin critical small lookup tables. ALTER TABLE t STORAGE (BUFFER_POOL KEEP);

Recycle Pool

For infrequently used blocks. Prevents large FTS blocks from flushing your working set. ALTER TABLE t STORAGE (BUFFER_POOL RECYCLE);

Buffer States

UnusedAvailable — never used or currently free
CleanIdentical to disk — can be reused immediately
DirtyModified — DBWn must write to disk before reuse
PinnedIn use right now — cannot be evicted
-- Buffer cache hit ratio (target >95%)
SELECT ROUND((1-(phyrds/(dbg+cg+phyrds)))*100,2) hit
FROM (SELECT SUM(value) phyrds FROM v$sysstat
      WHERE name='physical reads'),
     (SELECT SUM(value) dbg FROM v$sysstat
      WHERE name='db block gets'),
     (SELECT SUM(value) cg FROM v$sysstat
      WHERE name='consistent gets');

-- Buffer pools
SELECT name, block_size, current_size mb
FROM   v$buffer_pool;

-- Objects in keep pool
SELECT owner, segment_name, buffer_pool
FROM   dba_segments
WHERE  buffer_pool = 'KEEP';

Redo Log Buffer

Circular buffer · server processes write · LGWR flushes to disk

A circular buffer holding redo entries — records of every change made to the database. Contains information to reconstruct changes (DML, DDL, internal ops) for database recovery. Server processes write here; LGWR writes to online redo log files on disk.

LGWR Writes When:

1User issues COMMIT (immediate, synchronous write)
2Buffer is one-third full or contains 1 MB of data
3Every 3 seconds automatically
4Before DBWn writes dirty buffers (write-ahead logging)
5Online redo log switch occurs

Fast Commit: When you COMMIT, Oracle writes redo to disk and returns success — even though data blocks may still be in the buffer cache (dirty). On crash recovery, redo is replayed to bring the DB forward.

-- Redo buffer allocation retries (target ~0)
SELECT name, value FROM v$sysstat
WHERE  name='redo buffer allocation retries';

-- Log buffer size
SHOW parameter log_buffer;

-- Online redo log groups
SELECT group#, members,
       bytes/1024/1024 mb, status, archived
FROM   v$log;

-- Log switch frequency (should be <4/hr)
SELECT TO_CHAR(first_time,'YYYY-MM-DD HH24') hr,
       COUNT(*) switches
FROM   v$log_history
GROUP BY TO_CHAR(first_time,'YYYY-MM-DD HH24')
ORDER BY 1 DESC FETCH FIRST 24 ROWS ONLY;

Large Pool

Optional · no LRU · large memory allocations

Optional area for large memory allocations that would cause fragmentation in the shared pool. Has no LRU list — memory is allocated and held until the using process releases it. Pieces freed immediately become available to other processes.

RMAN I/O Slaves

Backup/restore I/O buffers. Recommended: at least 8 MB × number of channels.

Parallel Query Buffers

Inter-process message buffers for parallel execution operations.

Shared Server UGA

In shared server mode, User Global Area (UGA) moves from PGA to large pool so any shared server process can access session data.

Deferred Inserts (MEMOPTIMIZE FOR WRITE)

IoT-style high-frequency inserts buffered here. SMCO/Wnnn flush to disk asynchronously after 1 MB per session or 60 seconds.

-- Large pool size
SHOW parameter large_pool_size;

-- Large pool current usage
SELECT name, ROUND(bytes/1024/1024,1) mb
FROM   v$sgastat
WHERE  pool = 'large pool';

-- Resize dynamically
ALTER SYSTEM SET large_pool_size=256M SCOPE=both;

-- ORA-04031 = out of memory in pools
-- Check if large pool is undersized
SELECT * FROM v$shared_pool_advice;

In-Memory Column Store (IM)

Optional · columnar format · analytic acceleration

Stores tables/partitions in memory simultaneously in row format (buffer cache, for OLTP) AND columnar format (IM column store, for analytics). Oracle transparently routes queries. Does not double memory requirements — buffer cache runs much smaller than full DB size.

IMCU
In-Memory Compression Unit

Compressed, read-only storage unit for columnar data. One IMCU per set of rows for all columns.

SMU
Snapshot Metadata Unit

Tracks transactional changes for its associated IMCU. Every IMCU has exactly one SMU.

IMEU
In-Memory Expression Unit

Materialized virtual columns and IM expressions — logical extension of its parent IMCU.

-- Enable (requires Oracle In-Memory option)
ALTER SYSTEM SET inmemory_size=2G SCOPE=spfile; -- restart

-- Populate a table
ALTER TABLE sales INMEMORY;

-- Check population status
SELECT owner, segment_name, populate_status,
       ROUND(bytes/1024/1024,1) disk_mb,
       ROUND(inmemory_size/1024/1024,1) mem_mb
FROM   v$im_segments;

-- Force populate immediately
EXEC DBMS_INMEMORY.POPULATE('HR','EMPLOYEES');

-- Increase IM size on-the-fly (12.2+)
ALTER SYSTEM SET inmemory_size=4G SCOPE=both;

Other SGA Components

Java Pool

Stores session-specific Java code and data in the JVM. Shared part of each Java class (methods, read-only code vectors). Separate per-session state stays in PGA (dedicated) or SGA (shared server).

SHOW parameter java_pool_size;
Streams Pool

Used by Oracle Streams, Data Pump, GoldenGate integrated capture/apply. Stores buffered queue messages. Starts at zero, grows dynamically when Streams is used.

SHOW parameter streams_pool_size;
Fixed SGA

Internal housekeeping area. Size set by Oracle — cannot be altered. Contains database/instance state info and lock information shared between processes.

SELECT * FROM v$sgainfo WHERE name='Fixed SGA Size';
Memoptimize Pool

High-performance key-based queries for MEMOPTIMIZE FOR READ tables. 75% buffer area (permanently pinned) + 25% hash index. Cannot grow/shrink dynamically — requires instance restart.

SHOW parameter memoptimize_pool_size;
Per-Process Memory

Program Global Area (PGA)

A private, non-shared memory region exclusive to each server process and background process. One PGA per process. Never allocated in the SGA.

PGA Structure (Dedicated Server)

Private SQL Area
Persistent Area
Bind variable values. Freed only when cursor is closed by the client.
Run-Time Area
Query execution state — rows fetched, position in scan. Freed when statement closes.
SQL Work Areas
Sort Area
ORDER BY / GROUP BY
Hash Area
Hash join builds hash table from left input
Bitmap Area
Merges multiple bitmap indexes
User Global Area (UGA)
Session variables, logon info, OLAP pool. In dedicated server → in PGA. In shared server → moved to SGA Large Pool so any shared server process can access it.
Stack Space + Hash/Bitmap Areas
OS-level stack for session variables and arrays. Hash area for hash joins, bitmap merge area for bitmap index operations.
PGA Monitoring
-- PGA aggregate stats
SELECT name, ROUND(value/1024/1024,1) mb
FROM   v$pgastat
WHERE  name IN (
  'aggregate PGA target parameter',
  'total PGA allocated',
  'total PGA inuse',
  'cache hit percentage'  -- target >90%
);

-- Top PGA consumers
SELECT s.sid, s.username,
       ROUND(p.pga_alloc_mem/1024/1024,1) mb
FROM   v$session s JOIN v$process p
       ON s.paddr = p.addr
ORDER BY p.pga_alloc_mem DESC
FETCH FIRST 10 ROWS ONLY;

-- PGA advisor
SELECT pga_target_for_estimate/1024/1024 tgt_mb,
       estd_pga_cache_hit_percentage hit_pct
FROM   v$pga_target_advice
ORDER BY 1;

Tuning: If work areas spill to temp disk, sorts/hash joins are dramatically slower. Monitor cache hit percentage in v$pgastat — target >90%. Set PGA_AGGREGATE_TARGET to ~20% of RAM (OLTP) or ~50% (analytics).

Process Architecture

Background Processes

Background processes start automatically when the instance starts. Each performs a unique task, but all work together. They consolidate functions that would otherwise require multiple programs per connected user.

List all running background processes
SELECT pname, description FROM v$bgprocess WHERE paddr != '00' ORDER BY pname;
-- or
SELECT spid, stid, program FROM v$process WHERE pname IS NOT NULL ORDER BY pname;

Mandatory Background Processes

PMON
Process Monitor
Mandatory · runs as OS process

Periodically scans all processes to find any that died abnormally. Coordinates cleanup work via CLMN and CLnn slave processes. Responsible for resetting active transaction table, releasing locks, removing dead process IDs.

Detects dead server/dispatcher processes
Initiates cleanup of terminated sessions
Can quarantine corrupted resources (v$quarantine)
SELECT * FROM v$cleanup_process;
SELECT * FROM v$dead_cleanup;
SMON
System Monitor
Mandatory · system-level cleanup

Performs instance recovery at startup if needed. In RAC, SMON on one instance can recover another failed instance. Cleans temporary segments, coalesces free extents, maintains SCN-to-time mapping.

Instance recovery on startup (roll forward + rollback)
Cleans orphaned temporary segments
Maintains SCN-to-time mapping (Flashback)
-- Temp segment cleanup
SELECT * FROM v$sort_usage;
SELECT tablespace_name, contents
FROM   dba_tablespaces
WHERE  contents='TEMPORARY';
DBWn
Database Writer
DBW0-DBW9, DBWa-z, BW36-BW99

Writes dirty (modified) buffers from the buffer cache to data files on disk. Performs scattered multi-block writes. Up to 100 DBW processes (DB_WRITER_PROCESSES). Writes are slower than LGWR's sequential writes.

Writes when free buffer threshold is crossed
Writes to advance checkpoint position
Also writes to Smart Flash Cache if configured
SHOW parameter db_writer_processes;
-- DBW I/O stats
SELECT name, value FROM v$sysstat
WHERE name LIKE 'physical write%';
LGWR
Log Writer
Most critical background process

Writes redo log buffer to online redo log files on disk. Performs fast sequential writes (unlike DBWn's scattered writes). The atomic write of the commit record is the single event that confirms a transaction has committed.

On COMMIT — immediate, synchronous write to disk
Every 3 seconds or when buffer 1/3 full
Group commits — batches multiple transactions' redo
-- Log write waits (should be near 0)
SELECT name, value FROM v$sysstat
WHERE name='log file sync';
-- v$log shows current log group
SELECT * FROM v$log;
CKPT
Checkpoint Process
Updates control file & data file headers

At specific checkpoint events, signals DBWn to write dirty buffers, then updates the control file and all data file headers with the checkpoint SCN. Checks every 3 seconds whether PGA_AGGREGATE_LIMIT is exceeded.

Signals DBWn to write dirty buffers to disk
Updates control file with checkpoint position
Does NOT write data blocks or redo logs itself
-- Force a checkpoint
ALTER SYSTEM CHECKPOINT;
-- Checkpoint info in control file
SELECT checkpoint_change# FROM v$database;
MMON
Manageability Monitor
AWR snapshots + MMNL for ASH

MMON gathers SGA statistics and creates AWR snapshots every 60 minutes. Runs ADDM analysis and threshold alerts. MMNL samples v$session every second into ASH buffer, flushes to DBA_HIST_ACTIVE_SESS_HISTORY when full.

-- AWR snapshots
SELECT snap_id, begin_interval_time
FROM   dba_hist_snapshot
ORDER BY snap_id DESC FETCH FIRST 5 ROWS ONLY;
-- ASH live
SELECT * FROM v$active_session_history
WHERE rownum <= 10;

Optional Background Processes

ARCn
Archiver Process

Copies online redo logs to archive destination after a log switch. Exists only in ARCHIVELOG mode. Can also transmit redo to Data Guard standby destinations.

ARCHIVE LOG LIST;
LREG
Listener Registration

Registers the instance, services, handlers, and endpoints with the Oracle Net Listener. In 12c+, LREG replaced PMON for listener registration. Polls listener at startup.

lsnrctl status LISTENER
RECO
Recoverer Process

Automatically resolves in-doubt distributed transactions. Connects to remote databases, resolves hanging two-phase commits, removes rows from pending transaction tables.

SELECT * FROM dba_2pc_pending;
PMAN
Process Manager

Monitors, spawns, and stops shared server processes, connection brokers, job queue processes (CJQ0/Jnnn), and restartable background processes.

SHOW parameter job_queue_processes;
Physical Storage

Database Storage Architecture

The database is a set of physical files that persist on disk — independent of any running instance. Understanding these files is essential for backup, recovery, and troubleshooting.

Data Files (.dbf)
Required

Contain actual user data — tables, indexes, sequences. Organized into tablespaces: SYSTEM (data dictionary), SYSAUX (auxiliary), USERS, TEMP (sorting), UNDO (rollback segments).

SELECT file_name, tablespace_name,
       ROUND(bytes/1024/1024/1024,2) gb,
       status, autoextensible
FROM   dba_data_files
ORDER BY tablespace_name;
Control File (.ctl)
Required · multiplex!

Binary file containing metadata about the database structure — database name, data file/redo log locations and statuses, checkpoint info, backup records. Lost control file = cannot open database.

SELECT name, status FROM v$controlfile;
-- Always multiplex to 3+ copies!
SHOW parameter control_files;
Online Redo Logs
Required · circular · multiplex!

Record every change made to the database as it occurs. Circular — filled sequentially, then reused. At least 2 groups required. When a group fills, a log switch occurs and ARCn archives it (in ARCHIVELOG mode).

SELECT group#, sequence#, members,
       bytes/1048576 mb, status
FROM   v$log;
-- Add a redo log group
ALTER DATABASE ADD LOGFILE GROUP 4
('/u01/redo04a.log') SIZE 500M;
Archive Log Files
Optional but essential for recovery

Copies of filled online redo logs. Enable point-in-time recovery — restore a backup, apply archive logs forward to recover to any point. Required for Data Guard, GoldenGate, and RMAN incremental backups.

ARCHIVE LOG LIST;
SELECT dest_name, status, target
FROM   v$archive_dest
WHERE  status='VALID';
SELECT * FROM v$archived_log
WHERE  standby_dest='NO'
ORDER BY sequence# DESC FETCH FIRST 5 ROWS ONLY;
SPFILE / PFILE
Required for startup

SPFILE (server parameter file) — binary file storing initialization parameters. Supports dynamic changes via ALTER SYSTEM. PFILE (init.ora) — text version. SPFILE is preferred in production.

SHOW parameter spfile;
-- Create PFILE from SPFILE
CREATE PFILE='/tmp/init.ora' FROM SPFILE;
-- Edit and create SPFILE back
CREATE SPFILE FROM PFILE='/tmp/init.ora';
Alert Log / ADR
Automatic Diagnostic Repository

The alert log is your first stop for any issue — chronological log of messages, errors, and events. ADR contains trace files, dumps, health monitor reports, and incident packages. Always check it first on any problem.

SHOW parameter diagnostic_dest;
-- Alert log location:
-- $ADR_HOME/alert/log.xml
-- OR: $ADR_HOME/trace/alert_SID.log
tail -200f $ORACLE_BASE/diag/rdbms/orcl/orcl/trace/alert_orcl.log

-- Tablespace usage (most important monitoring query)
SELECT t.tablespace_name,
       ROUND(t.total_mb,1)     total_mb,
       ROUND(f.free_mb,1)      free_mb,
       ROUND(t.total_mb - f.free_mb,1) used_mb,
       ROUND((1 - f.free_mb/t.total_mb)*100,1) pct_used
FROM (SELECT tablespace_name, SUM(bytes)/1024/1024 total_mb FROM dba_data_files GROUP BY tablespace_name) t
JOIN (SELECT tablespace_name, SUM(bytes)/1024/1024 free_mb  FROM dba_free_space   GROUP BY tablespace_name) f
  ON t.tablespace_name = f.tablespace_name
ORDER BY pct_used DESC;

-- Add datafile when tablespace is full
ALTER TABLESPACE users ADD DATAFILE '+DATA' SIZE 10G AUTOEXTEND ON NEXT 1G MAXSIZE 50G;
End-to-End Flow

What Happens When You Run a SQL Statement?

Trace the exact path a SELECT and a COMMIT take through the Oracle architecture — from client all the way to disk.

SELECT Statement Flow

What happens step by step when you run a query

1
Client sends SQL to Server Process

Application sends SQL via Oracle Net. Listener accepts the connection, spawns or assigns a dedicated server process, and hands off the connection.

2
Parse — Check Shared Pool

Soft parse: identical SQL found in library cache → reuse plan. Hard parse: not found → syntax check, semantic check (data dictionary cache), CBO optimization, store new plan.

3
Bind — Substitute Bind Variables

Server process substitutes bind variable values from the PGA persistent area into the execution plan before execution begins.

4
Execute — Run the Plan (Buffer Cache)

For each data block: (a) check buffer cache — cache hit → logical read (fast). (b) Not found → read from data file into buffer cache, then logical read (physical read = slow path).

5
Consistent Read (Read Consistency)

Server reads blocks in consistent mode — uses undo segments to reconstruct data as it appeared at the query's start SCN. You never see another session's uncommitted changes.

6
Fetch — Return Rows to Client

Server process sends result rows back via Oracle Net. Array fetch — multiple rows per round-trip. OPEN_CURSORS parameter limits private SQL areas per session.

COMMIT — The Fast Commit Mechanism

Why Oracle is fast and durable at the same time

1
DML Modifies Buffer Cache Blocks

Server process changes data blocks in the buffer cache (dirty buffers). Generates redo records in the redo log buffer. Undo records stored in undo segments for rollback capability.

2
COMMIT — SCN Assigned

Transaction gets a System Change Number (SCN) — Oracle's global logical clock. The commit SCN + all redo entries for this transaction go into the redo log buffer.

3
LGWR Writes Redo to Disk (Synchronous)

LGWR immediately writes the commit record + redo entries from the buffer to the online redo log on disk. This single atomic write IS the commit point. Transaction is now permanently durable.

4
Oracle Returns "Commit Complete"

Oracle signals success to the application immediately — even though the modified data blocks are still dirty in the buffer cache, NOT yet written to data files on disk.

5
DBWn Eventually Writes Dirty Blocks to Disk

DBWn writes dirty buffers to data files asynchronously at checkpoint time. Much later than the commit. Safe because redo log already has everything needed to replay the changes on recovery.

!!
Instance Crashes Before DBWn Writes?

No problem. On next startup, SMON performs instance recovery: replays redo (roll forward) to bring committed changes forward, then rolls back all uncommitted transactions. The redo log is the safety net.

Production DBA

Essential Monitoring SQL Queries

The queries every Oracle DBA must know by heart. These will be used daily in any production DBA role.

Database Health CheckDaily
-- Instance status
SELECT instance_name, status, version,
       startup_time FROM v$instance;

-- Database mode
SELECT name, open_mode, log_mode,
       db_unique_name FROM v$database;

-- All SGA components
SELECT name, ROUND(value/1024/1024,1) mb
FROM   v$sga;

-- Session count by status
SELECT status, COUNT(*) FROM v$session
GROUP BY status;
Memory Hit RatiosWeekly
-- Buffer cache hit ratio (target >95%)
SELECT ROUND((1-(phyrds/(dbg+cg+phyrds)))*100,2) hit_pct
FROM (SELECT SUM(value) phyrds FROM v$sysstat
      WHERE name='physical reads'),
     (SELECT SUM(value) dbg FROM v$sysstat
      WHERE name='db block gets'),
     (SELECT SUM(value) cg FROM v$sysstat
      WHERE name='consistent gets');

-- Library cache hit ratio (target >99%)
SELECT ROUND((1-SUM(reloads)/SUM(pins))*100,2)
FROM   v$librarycache;

-- PGA cache hit pct (target >90%)
SELECT name, value FROM v$pgastat
WHERE  name='cache hit percentage';
Tablespace UsageDaily
-- Tablespace usage % (alert when >80%)
SELECT t.tablespace_name,
       ROUND((1-f.free_mb/t.total_mb)*100,1) pct_used,
       ROUND(t.total_mb,0)   total_mb,
       ROUND(f.free_mb,0)    free_mb
FROM (SELECT tablespace_name,
             SUM(bytes)/1048576 total_mb
      FROM dba_data_files
      GROUP BY tablespace_name) t
JOIN (SELECT tablespace_name,
             SUM(bytes)/1048576 free_mb
      FROM dba_free_space
      GROUP BY tablespace_name) f
  ON t.tablespace_name=f.tablespace_name
ORDER BY pct_used DESC;
Top SQL & Blocking SessionsOn-Demand
-- Top SQL by elapsed time
SELECT sql_id, executions,
       ROUND(elapsed_time/1e6,2) elapsed_sec,
       ROUND(elapsed_time/
         DECODE(executions,0,1,executions)/1e6,3) avg_sec,
       SUBSTR(sql_text,1,60) preview
FROM   v$sql
ORDER BY elapsed_time DESC
FETCH FIRST 10 ROWS ONLY;

-- Blocking sessions (P1 incident first step)
SELECT blocking_session blk_sid, sid, wait_class,
       seconds_in_wait sec_wait, state
FROM   v$session
WHERE  blocking_session IS NOT NULL
ORDER BY seconds_in_wait DESC;
Background Processes StatusDaily
-- All running background processes
SELECT pname, description
FROM   v$bgprocess
WHERE  paddr != '00'
ORDER BY pname;

-- Check if LGWR, DBWn, PMON etc. are running

FROM   v$process
WHERE  background IS NOT NULL
ORDER BY pname;

-- Archive log destination status
SELECT dest_name, status, target, archiver
FROM   v$archive_dest
WHERE  status != 'INACTIVE';

-- Last 5 AWR snapshots

       TO_CHAR(begin_interval_time,'DD-MON HH24:MI') begin_time

ORDER BY snap_id DESC
FETCH FIRST 5 ROWS ONLY;

       ROUND(space_reclaimable/1024/1024/1024,2) reclaimable_gb,
       number_of_files

Interview Q&A

Oracle Architecture — Interview Questions

Most-asked questions in Oracle DBA interviews covering instance memory, background processes, and SQL execution.

The SGA (System Global Area) is shared memory allocated at instance startup that all server processes and background processes can access. It contains the Buffer Cache, Shared Pool, Redo Log Buffer, Large Pool, Java Pool, and Streams Pool.

The PGA (Program Global Area) is private memory exclusive to each individual server or background process — no sharing occurs. It contains the private SQL area (bind variables, cursor state), SQL work areas (sort, hash join, bitmap merge), and session information. If the PGA work area is too small, sort or hash operations spill to temp disk, causing a dramatic slowdown.

Key distinction: SGA survives across connections; PGA is created when a server process starts and freed when it ends.

  1. Parse: Server process checks Shared Pool for an identical SQL hash (soft parse). If not found, performs a hard parse — syntax check, semantic check (does the table exist?), privilege check, then generates an execution plan via the CBO.
  2. Execute: Server process identifies data blocks needed. Checks the Buffer Cache; if not present (cache miss), issues a physical read from the data file into the buffer cache.
  3. Fetch: Server process retrieves rows from the buffer cache and transmits them back to the client in batches (array fetch). For consistent reads, it may need to reconstruct older versions of blocks using UNDO data.

Key point: DML adds a Fetch step after Execute only for queries. SELECT never touches redo; only DML generates redo log entries.

DBWn (Database Writer) writes modified ("dirty") buffer cache blocks to data files. Oracle uses a write-ahead logging strategy: LGWR must first flush the corresponding redo to the online redo log before DBWn can write the block. This ensures recovery is always possible even if DBWn's write is interrupted.

DBWn writes are triggered by: (1) the buffer cache reaching its dirty threshold, (2) a checkpoint, (3) a tablespace going offline, or (4) a datafile going read-only. DBWn intentionally delays writes so that multiple logical changes to the same block are batched into one physical I/O — this is called write batching and is far more efficient than writing on every COMMIT.

An Instance is memory + processes — specifically the SGA (shared memory) and the background processes (SMON, PMON, DBWn, LGWR, CKPT, etc.). An instance is ephemeral; it exists only while the database is mounted/open.

A Database is the physical set of files on disk: data files (.dbf), online redo log files, and the control file. The database persists independently of whether an instance is running.

Real-world example: In Oracle RAC, multiple instances share a single database — each node runs its own instance (SGA + processes), but all instances read and write the same physical database files on shared storage.

Online redo logs record every change made to the database (before-and-after images). They serve two purposes: (1) Instance recovery — if the database crashes, Oracle replays the redo log from the last checkpoint to bring data files up-to-date, then rolls back uncommitted transactions using UNDO. (2) Data Guard replication — redo is shipped to standby databases for real-time apply.

Redo logs work in a circular group fashion. When the current group fills, LGWR performs a log switch to the next group. If ARCHIVELOG mode is enabled, the ARCn process archives the filled group before it can be reused. If all groups are full and archiving is behind, LGWR will stall — causing all users to hang with a "log file switch" wait event.
