Section 01

What Is GoldenGate?

The fundamentals — what it is, why it exists, and every key term explained in plain language.

🔄 What GoldenGate Does

GoldenGate is a log-based Change Data Capture (CDC) tool. It reads your database's redo logs (the same logs Oracle uses for crash recovery) and captures every INSERT, UPDATE, DELETE as it happens — then applies those changes to one or more target databases, usually within milliseconds.

Unlike physical standby (Data Guard), which replicates at the block level, GoldenGate works at the logical (SQL) level — so source and target can have different schemas, platforms, even database vendors (Oracle → PostgreSQL, MySQL → Oracle, etc.).

🎯 When You Need GoldenGate

  • Zero-downtime migration — move a live database to new hardware/platform with no outage window
  • Active-active replication — two databases accepting writes simultaneously (bidirectional)
  • Reporting offload — replicate OLTP data to a reporting DB in real time
  • Cross-platform migration — Oracle → Autonomous DB, Oracle → PostgreSQL
  • DR without licensing cost — replicated target can be read-only standby

📦 Key Versions

  • OGG 11g/12c Classic Architecture only — GGSCI CLI
  • OGG 18c/19c Microservices introduced; Integrated Extract default
  • OGG 21c Classic Extract removed — Integrated only; Classic Replicat still available
  • OGG 23c Microservices-first, better cloud integration
  • OGG Free Free tier for up to 1 GB/day (trial, non-production)

How It Works — The Data Flow

📁 GoldenGate Directory Structure

  • $OGG_HOME/ — GoldenGate installation root
  • dirprm/ — Parameter files for all processes
  • dirdat/ — Trail files (local and remote)
  • dirrpt/ — Report files (process logs)
  • dirchk/ — Checkpoint files
  • dirpcs/ — Process status files
  • dirtmp/ — Temporary working files
  • GLOBALS — Global parameter file (port, schema)

🔢 Trail File Naming

Trail files follow the pattern: lt000000001

  • lt — Two-character prefix you define (e.g., "lt" for local trail)
  • 000000001 — Nine-digit sequence number, auto-increments
  • Default max size: 500MB per file (configurable)
  • New file created when max size reached or process restarts
  • Manager purges old files based on PURGEOLDEXTRACTS rule

⚡ Classic vs Integrated Extract

Classic Extract (TRANLOG mode): reads redo logs directly from OS — deprecated in 18c, removed in 21c

Integrated Extract: registers with Oracle's LogMiner server (inbound server); Oracle does the log mining and pushes LCRs to Extract. Default since 19c

Integrated Extract requires: ENABLE_GOLDENGATE_REPLICATION=TRUE and STREAMS_POOL_SIZE set appropriately.

Section 02

Architecture Deep Dive

Classic Architecture vs Microservices Architecture — processes, roles, and how they connect.

Classic Architecture (pre-18c, and still available through OGG 19c) — managed entirely through the GGSCI command line. Each component is a standalone process on the OS.

Manager Process

Master controller. Listens on port 7809. Responsibilities:

  • Start/stop/monitor Extract and Replicat
  • Allocate dynamic ports for Collector
  • Purge old trail files (PURGEOLDEXTRACTS)
  • Report lag alarms (LAGREPORTHOURS)
  • Restart failed processes (AUTORESTART)

Collector Process

Target-side server process spawned by Manager when Data Pump connects. It:

  • Receives trail data from Data Pump over TCP
  • Writes data into the remote trail files on the target server
  • One Collector per Data Pump connection
  • Ephemeral — exits when Data Pump disconnects
  • Port allocated dynamically from DYNAMICPORTLIST

Checkpoint Mechanism

Each process maintains checkpoints in two places:

  • Checkpoint file (dirchk/) — on disk, stores read/write position in trail
  • Checkpoint table (in target DB) — used by Replicat; survives DB restarts and provides extra safety

On restart after failure, GoldenGate resumes exactly from the last checkpoint — no data loss, no duplicates (assuming HANDLECOLLISIONS for initial sync).

Microservices Architecture (OGG 18c+) — REST API driven, HTML5 web UI, each function is a separate server process. Recommended for new deployments.

Microservices Advantages

  • HTML5 web UI — no terminal needed for basic ops
  • REST API — integrate with Ansible, Terraform, CI/CD
  • HTTPS encryption between Distribution and Receiver servers
  • Token-based authentication
  • Better suited for cloud and OCI GoldenGate
  • Centralized monitoring via Performance Metrics Server

Still Use GGSCI?

In Microservices, GGSCI is still available for commands, but the recommended approach is:

  • Web UI for day-to-day management
  • REST API for automation
  • adminclient CLI (replaces GGSCI in Microservices)

Classic architecture users continue using GGSCI exclusively.

OCI GoldenGate

Fully managed GoldenGate in Oracle Cloud — no installation needed. Built on Microservices architecture. Supports:

  • Oracle DB (on-prem, RDS, Autonomous)
  • MySQL, PostgreSQL, SQL Server, Kafka
  • BigQuery, Azure SQL, Amazon RDS

Extract reads Oracle redo/archive logs and captures committed DML and DDL changes. In Integrated mode, it registers with Oracle's LogMiner infrastructure (requires STREAMS_POOL_SIZE configured).

Extract process name: up to 8 characters, unique per instance.

Extract parameter file — ext_hr.prm (integrated mode)
EXTRACT ext_hr
USERIDALIAS srcalias
EXTTRAIL ./dirdat/lt
LOGALLSUPCOLS
UPDATERECORDFORMAT COMPACT

TABLE hr.*;
-- Capture all tables in HR schema

-- For DDL capture:
DDL INCLUDE MAPPED OBJTYPE 'TABLE'

Key Extract parameters:

  • EXTTRAIL — local trail file prefix (two chars + path)
  • LOGALLSUPCOLS — write all supplementally logged columns
  • UPDATERECORDFORMAT COMPACT — write before/after images
  • FETCHOPTIONS FETCHPKUPDATECOLS — fetch primary key values on PK updates
  • TRANLOGOPTIONS DBLOGREADER — use direct log reading (for Classic Extract)

Data Pump is a secondary Extract process that reads the local trail and sends data to the target server. It runs on the source server. Benefits of having a separate Data Pump:

  • Primary Extract doesn't wait for network — it writes to local trail and continues
  • If network goes down, Data Pump queues locally without stopping capture
  • Can filter/transform data before sending (MAP, FILTER, COLMAP)
  • Supports multiple targets from one source trail (fan-out)
Data Pump parameter file — dpump_hr.prm
EXTRACT dpump_hr
USERIDALIAS srcalias
RMTHOST target-server, MGRPORT 7809, COMPRESS
RMTTRAIL ./dirdat/rt
PASSTHRU
-- PASSTHRU: don't interpret trail records, pass as-is

TABLE hr.*;

PASSTHRU mode: Data Pump doesn't parse or transform — just routes. Use this when no filtering/mapping is needed (better performance).

Replicat reads the remote trail file and applies changes to the target database using either SQL statements (Classic Replicat) or Oracle's XStream/inbound server API (Integrated Replicat).

Replicat parameter file — rep_hr.prm
REPLICAT rep_hr
USERIDALIAS tgtalias
ASSUMETARGETDEFS
-- If source/target schema identical; else use SOURCEDEFS

HANDLECOLLISIONS
-- Allow duplicate/missing row errors during initial load sync

MAP hr.employees, TARGET hr.employees;
MAP hr.departments, TARGET hr.departments;
MAP hr.jobs, TARGET hr.jobs;

Key Replicat parameters:

  • ASSUMETARGETDEFS — source and target schema identical (no need for defgen)
  • SOURCEDEFS ./dirdef/hr.def — use definition file for heterogeneous targets
  • HANDLECOLLISIONS — silently ignore duplicate key errors (during initial sync)
  • DISCARDFILE ./dirrpt/rep_hr.dsc, APPEND, MEGABYTES 500 — write failed records to discard file
  • BATCHSQL — batch similar DML for better throughput (Classic Replicat)

Section 03

Setup & Configuration

Step-by-step: prerequisites, supplemental logging, credential store, and initial GoldenGate setup from scratch.

These must be in place on the source database before GoldenGate can capture changes:

1

Enable ARCHIVELOG Mode

GoldenGate reads archive logs for committed transactions. The database must be in ARCHIVELOG mode.

-- Check current mode
SELECT log_mode FROM v$database;

-- Enable ARCHIVELOG mode (requires restart)
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE ARCHIVELOG;
ALTER DATABASE OPEN;
2

Enable GoldenGate Replication Parameter

Required for Integrated Extract — tells Oracle to enable LogMiner-based capture.

ALTER SYSTEM SET enable_goldengate_replication = TRUE SCOPE=BOTH;
-- Verify:
SHOW PARAMETER enable_goldengate_replication;
3

Enable Minimal Supplemental Logging

Database-level supplemental logging is the foundation — it adds row identifiers to redo. This is the bare minimum; you also need table-level supplemental logging.

ALTER DATABASE ADD SUPPLEMENTAL LOG DATA;
-- Verify:
SELECT supplemental_log_data_min FROM v$database;
-- Should return: YES
4

Enable FORCE LOGGING (Recommended)

Prevents NOLOGGING operations from generating gaps in GoldenGate's capture stream.

ALTER DATABASE FORCE LOGGING;
-- Verify:
SELECT force_logging FROM v$database;
-- Should return: YES
5

Configure STREAMS_POOL_SIZE (Integrated Extract only)

Integrated Extract uses Oracle's LogMiner server, which needs memory from STREAMS_POOL. Formula: N_extracts × 1 GB × 1.25

-- For 2 Integrated Extracts: 2 × 1GB × 1.25 = 2.5GB
ALTER SYSTEM SET streams_pool_size = 2G SCOPE=BOTH;

-- If using AMM (automatic memory management), Oracle handles this
-- But explicit setting is safer for GoldenGate workloads
6

Create GoldenGate DB User (Source)

-- In Oracle 12c+ CDB (create in CDB$ROOT for Integrated Extract):
CREATE USER c##ggadmin IDENTIFIED BY OGGpasswd1#
  DEFAULT TABLESPACE users
  TEMPORARY TABLESPACE temp
  CONTAINER=ALL;

GRANT CREATE SESSION, CONNECT, RESOURCE TO c##ggadmin CONTAINER=ALL;
GRANT DBA TO c##ggadmin CONTAINER=ALL;
EXEC DBMS_GOLDENGATE_AUTH.GRANT_ADMIN_PRIVILEGE('C##GGADMIN', CONTAINER=>'ALL');

-- For non-CDB / PDB-level (Classic non-CDB):
CREATE USER ggadmin IDENTIFIED BY OGGpasswd1#;
EXEC DBMS_GOLDENGATE_AUTH.GRANT_ADMIN_PRIVILEGE('GGADMIN');
7

Create GoldenGate DB User (Target)

CREATE USER ggadmin IDENTIFIED BY OGGpasswd1#;
GRANT DBA TO ggadmin;
-- Target needs: CREATE SESSION, DBA (or granular: CREATE TABLE, INSERT, UPDATE, DELETE, SELECT on target tables)

-- Grant GOLDENGATE_REPLICATION privilege for Integrated Replicat:
EXEC DBMS_GOLDENGATE_AUTH.GRANT_ADMIN_PRIVILEGE('GGADMIN');

Supplemental logging tells Oracle to write extra column values into the redo log. Without it, GoldenGate can't identify which row to UPDATE or DELETE on the target (because Oracle normally only logs changed columns).

Table-Level Supplemental Logging

-- Add supplemental logging for ALL columns of a table (most common):
DBLOGIN USERIDALIAS srcalias
ADD TRANDATA hr.employees ALLCOLS
ADD TRANDATA hr.departments ALLCOLS

-- Add for all tables in a schema:
ADD SCHEMATRANDATA hr ALLCOLS

-- ALLCOLS: logs all columns (safest; required when no PK or PK changes)
-- Without ALLCOLS: only key columns logged (enough if table has a stable PK)

-- Verify supplemental logging:
INFO TRANDATA hr.employees
INFO SCHEMATRANDATA hr

-- Delete supplemental logging:
DELETE TRANDATA hr.employees
DELETE SCHEMATRANDATA hr
OptionWhat Gets LoggedWhen to Use
ADD TRANDATA tblPrimary key columns onlyTable has stable PK; sufficient for most cases
ADD TRANDATA tbl ALLCOLSAll columns (before + after image)No PK, composite PK, or PK can be updated; bidirectional replication
ADD TRANDATA tbl NOSCHEDULINGCOLSMinimal columns (for scheduling algorithms)Parallel/Coordinated Replicat optimization
ADD SCHEMATRANDATA schema ALLCOLSAll columns for entire schemaBulk enable — easier to manage; auto-covers new tables

⚠️ Common Supplemental Logging Mistakes

  • Forgot ALLCOLS on tables with no PK → Extract abends with OGG-00869 (supplemental log group mismatch)
  • Enabled only DB-level supplemental logging but not table-level → Replicat can't identify rows (UPDATE/DELETE fails)
  • Added new table but didn't run ADD TRANDATA → Extract starts, then abends when it encounters the missing table
  • NOLOGGING operations bypass supplemental logging → Always use FORCE LOGGING at DB level

GoldenGate stores DB credentials in an encrypted wallet (credential store) rather than plain-text passwords in parameter files. This is the recommended and secure approach.

-- Step 1: Create the credential store (once per GoldenGate installation)
GGSCI> CREATE WALLET

-- Step 2: Add credential store
GGSCI> ADD CREDENTIALSTORE

-- Step 3: Add alias for source DB
GGSCI> ALTER CREDENTIALSTORE ADD USER c##ggadmin@srcdb PASSWORD OGGpasswd1# ALIAS srcalias DOMAIN OracleGoldenGate
-- @srcdb is the TNS alias from tnsnames.ora

-- Step 4: Add alias for target DB
GGSCI> ALTER CREDENTIALSTORE ADD USER ggadmin@tgtdb PASSWORD OGGpasswd1# ALIAS tgtalias DOMAIN OracleGoldenGate

-- Step 5: List all stored credentials
GGSCI> INFO CREDENTIALSTORE

-- In parameter files, use USERIDALIAS (never hard-code passwords):
-- USERIDALIAS srcalias   (in Extract param)
-- USERIDALIAS tgtalias   (in Replicat param)

-- Test login works:
GGSCI> DBLOGIN USERIDALIAS srcalias
-- Should print: Successfully logged into database.

Credential Store vs. Plain Text

  • Recommended USERIDALIAS alias — credentials in encrypted wallet, never in parameter file
  • Avoid USERID ggadmin, PASSWORD secret123 — password visible in plain text in dirprm/
  • Credential store files stored in: $OGG_HOME/dircrd/
  • One credential store per GoldenGate installation, multiple aliases supported

How to check GoldenGate health, identify lag, and query the database views for real-time metrics.

Lag = how many seconds behind the target is. Measured at each checkpoint. Two types:

Lag TypeMeaningAcceptable
Lag at ChkptLag measured at the last checkpoint — how far behind the process was when it last checkpointed< 30 seconds for OLTP
Time Since ChkptHow long ago the last checkpoint occurred — if this is high with no lag increase, process might be idle/stuck< 5 minutes

GGSCI> LAG EXTRACT ext_hr
GGSCI> LAG REPLICAT rep_hr
GGSCI> LAG EXTRACT *

-- Detailed INFO shows both lag metrics
GGSCI> INFO EXTRACT ext_hr, DETAIL

-- Manager lag alerting (in mgr.prm)
LAGREPORTHOURS 1        -- report lag every 1 hour in ggserr.log
LAGINFOMINUTES 10       -- lag > 10 min = INFO message
LAGCRITICALMINUTES 30   -- lag > 30 min = CRITICAL message

Common Causes of Lag

Symptoms: Extract lag is low (capturing fine), but Replicat lag is high (applying slowly).

Root causes:

  • Network congestion between source and target → slow trail file delivery
  • Target DB under heavy load → Replicat waits for resources
  • Long-running transaction on target blocking Replicat's DML
  • Replicat applying single-threaded (Classic) but source has high-volume workload

Fix: Switch to Parallel Replicat (MAXAPPLYTHREADS), or Integrated Replicat. Check target DB wait events (v$session_wait where username='GGADMIN').

Symptoms: Extract lag grows; Extract is running but falling behind source DB.

Root causes:

  • Source DB generating redo very fast (high DML) — Extract can't keep up
  • STREAMS_POOL_SIZE too small → LogMiner swapping
  • Archive logs being purged before Extract reads them (OGG-00869)
  • Extract scanning too many tables (wildcard TABLE clause)

Fix: Increase STREAMS_POOL_SIZE. Archive log retention must be longer than Extract's furthest lag. Consider schema-based filtering to reduce Extract scope.

Typical cause: Large batch job on source (bulk insert, data load). GoldenGate captures the entire batch transaction (which may span many redo records) and must apply it all at once on target.

Signs: Lag jumps during batch window, then drops back to near-zero after batch completes.

Fix options: BATCHSQL in Replicat (batch similar DML), Parallel Replicat, or schedule batch jobs during low-replication windows. For very large initial loads, use SOURCEISTABLE instead of CDC.

Troubleshooting — Day-to-Day Scenarios

Real problems DBAs face in production — what breaks, why, and exactly how to fix it.

Error: OGG-00664 OCI Error ORA-01017: invalid username/password; logon denied

Why it happens:

  • Wrong password in credential store or USERID parameter
  • User account locked (too many failed logins)
  • User doesn't exist in the database
  • TNS alias in credential store doesn't match tnsnames.ora entry
  • For Integrated Extract: user doesn't have GOLDENGATE_REPLICATION privilege (DBMS_GOLDENGATE_AUTH not run)

Fix:

-- Test the credential directly
GGSCI> DBLOGIN USERIDALIAS srcalias
-- If fails: check the alias
GGSCI> INFO CREDENTIALSTORE

-- Update password in credential store
GGSCI> ALTER CREDENTIALSTORE ADD USER c##ggadmin@srcdb PASSWORD NewPass1# ALIAS srcalias DOMAIN OracleGoldenGate

-- Unlock user if locked
ALTER USER c##ggadmin ACCOUNT UNLOCK;
ALTER USER c##ggadmin IDENTIFIED BY NewPass1#;

-- Verify GOLDENGATE_REPLICATION privilege
SELECT grantee, privilege FROM dba_sys_privs WHERE grantee = 'C##GGADMIN';
EXEC DBMS_GOLDENGATE_AUTH.GRANT_ADMIN_PRIVILEGE('C##GGADMIN', CONTAINER=>'ALL');

Error: OGG-01044 Could not open file ./dirdat/lt000000005: No such file or directory
or: OGG-01668 PROCESS ABENDED at current position (cannot open next trail file)

Why it happens:

  • Data Pump or Replicat is looking for a trail file that was deleted (purged too aggressively)
  • Trail files manually deleted while process was running
  • Wrong trail prefix in Data Pump / Replicat parameter file (mismatch with EXTTRAIL / RMTTRAIL)

Fix:

-- Check which trail file it's looking for
GGSCI> INFO EXTRACT dpump_hr, DETAIL
GGSCI> INFO REPLICAT rep_hr, DETAIL

-- Option 1: Reposition to the latest available trail file
GGSCI> STOP REPLICAT rep_hr
GGSCI> ALTER REPLICAT rep_hr, BEGIN NOW
GGSCI> START REPLICAT rep_hr
-- WARNING: Records from missing trail will be lost — use HANDLECOLLISIONS

-- Option 2: Restore from archived trail (if you have backups)
-- Copy the missing trail file back to dirdat/
cp /backup/dirdat/lt000000005 ./dirdat/

-- Option 3: If Data Pump lost its trail, resync:
GGSCI> STOP EXTRACT dpump_hr
GGSCI> ALTER EXTRACT dpump_hr, EXTSEQNO 6, EXTRBA 0  -- jump to next available
GGSCI> START EXTRACT dpump_hr

-- Prevention: Set MINKEEPDAYS in Manager to retain trail files longer
PURGEOLDEXTRACTS ./dirdat/*, USECHECKPOINTS, MINKEEPDAYS 7

Error: OGG-00869 No unique key is defined for table HR.ORDERS. All viable columns will be used to represent the key, but may not guarantee uniqueness.

Why it happens:

  • Table has no primary key AND supplemental logging for all columns not enabled
  • ADD TRANDATA was done without ALLCOLS on a table with composite unique key
  • A new table was added to the TABLE clause but TRANDATA wasn't added for it

Fix:

-- Login and add ALLCOLS supplemental logging
GGSCI> DBLOGIN USERIDALIAS srcalias
GGSCI> ADD TRANDATA hr.orders ALLCOLS

-- Verify it's set
GGSCI> INFO TRANDATA hr.orders
-- Should show: Log Group: All Columns

-- For all tables missing a PK, use schema-level command
GGSCI> ADD SCHEMATRANDATA hr ALLCOLS

-- If you can add a PK (best long-term fix):
ALTER TABLE hr.orders ADD CONSTRAINT orders_pk PRIMARY KEY (order_id);

-- Then reduce supplemental logging scope:
GGSCI> DELETE TRANDATA hr.orders
GGSCI> ADD TRANDATA hr.orders  -- PK columns only now sufficient

Error (in report file): ORA-00001: unique constraint (HR.EMPLOYEES_PK) violated
or: ORA-01403: no data found (UPDATE/DELETE target row not found)

Why it happens:

  • During initial sync: rows were loaded via Data Pump/import but GoldenGate also captured the same inserts — resulting in duplicates on target when Replicat applies them
  • Row was already deleted on target before Replicat tried to delete it (out-of-sync state)
  • Bidirectional replication loops (changes going back and forth)

Fix — temporary: use HANDLECOLLISIONS

-- Add HANDLECOLLISIONS to Replicat parameter file during initial sync
REPLICAT rep_hr
USERIDALIAS tgtalias
ASSUMETARGETDEFS
HANDLECOLLISIONS   -- ignore ORA-00001 (duplicate) and ORA-01403 (no data)

MAP hr.employees, TARGET hr.employees;

-- IMPORTANT: Remove HANDLECOLLISIONS after initial sync is complete!
-- Leaving it on permanently can hide real data issues.

-- View rejected records (discard file)
GGSCI> SEND REPLICAT rep_hr, REPORT
-- or check: cat ./dirrpt/rep_hr.dsc

or: Extract needs to read redo log: sequence 45, but that log has been deleted

Why it happens:

  • RMAN deleted archive logs before Extract could process them (archive log retention policy too short)
  • Extract was stopped for longer than the archive log retention window
  • OS-level disk cleanup removed archive logs

Fix and Prevention:

-- Check what SCN Extract is at vs current SCN
GGSCI> INFO EXTRACT ext_hr, DETAIL

GGSCI> ALTER EXTRACT ext_hr, TRANLOG, SCN 1099999  -- SCN after the gap

RMAN> DELETE ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE-7';
-- Keep at least as long as your Extract's maximum possible lag

Advanced Configurations

Bidirectional replication, filtering, column mapping, conflict detection, and fan-out/fan-in topologies.

Bidirectional (active-active) replication means both databases accept writes and replicate changes to each other. This is GoldenGate's most powerful but most complex topology.

-- KEY CHALLENGE: Loop Prevention
-- Without loop prevention, change from DB A replicates to DB B,
-- then Extract on DB B captures it and sends back to DB A → infinite loop!

-- Solution 1: LOGTABLE (Classic Architecture)
-- Extract ignores changes made by the Replicat user
-- In Extract A (on DB A) param file:
TRANLOGOPTIONS EXCLUDEUSER GGADMIN
-- Any changes committed by GGADMIN (Replicat user) are excluded from capture

-- Solution 2: GGS_EXCLUDED_TAG (Integrated Extract, 12c+)
-- Replicat tags its transactions; Extract ignores tagged transactions
-- Set in Replicat A's param file:
DBOPTIONS SETTAG 10
-- Set in Extract A's param file:
TRANLOGOPTIONS EXCLUDETAG 10

-- ALLCOLS is REQUIRED for bidirectional — use UPDATERECORDFORMAT COMPACT
LOGALLSUPCOLS
UPDATERECORDFORMAT COMPACT

⚠️ Bidirectional Challenges

  • Conflict detection is mandatory — same row updated on both sides simultaneously
  • Sequence conflicts — SEQUENCE-based PKs must be disjoint (e.g., DB A uses even numbers, DB B uses odd)
  • Transaction ordering — without CDR, last-write-wins by default
  • Not recommended for OLTP databases unless conflict handling is fully designed

GoldenGate can filter rows, map to different table/column names, transform column values, and selectively replicate.

-- =============================================
  TABLE / MAP: Basic Mapping
-- =============================================

-- In Extract: which tables to capture
TABLE hr.*;                    -- all tables in HR schema
TABLE hr.employees;            -- specific table
TABLE hr.emp*, TARGET hr.*;    -- wildcard match

-- In Replicat: MAP source to target
MAP hr.employees, TARGET hr_report.employees;   -- different schema
MAP hr.employees, TARGET reporting.emp;          -- different schema + table name

-- =============================================
  ROW FILTERING
-- =============================================

-- Replicate only active employees:
MAP hr.employees, TARGET hr.employees,
  WHERE (status = 'ACTIVE');

-- Filter with multiple conditions:
MAP hr.employees, TARGET hr.employees,
  WHERE (department_id IN (10, 20, 30) AND hire_date > '2020-01-01');

-- =============================================
  COLUMN MAPPING (COLMAP)
-- =============================================

-- Map source columns to different target column names:
MAP hr.employees, TARGET hr_tgt.employees,
  COLMAP (USEDEFAULTS,
    target_emp_id    = employee_id,
    target_full_name = STRCAT(first_name, ' ', last_name),
    load_ts          = DATENOW()
  );

-- USEDEFAULTS: auto-map columns with identical names; then override specifics

-- =============================================
  COLUMN CONVERSION FUNCTIONS
-- =============================================

-- Built-in GoldenGate column conversion functions:
DATENOW()                    -- current timestamp
STRCAT(col1, ' ', col2)      -- string concatenation
STRTRIM(col)                  -- trim whitespace
UPPER(col) / LOWER(col)       -- case conversion
SUBSTR(col, 1, 10)            -- substring
IF(condition, val_true, val_false)  -- conditional
SYSDATE()                    -- Oracle SYSDATE

-- =============================================
  IGNORE SPECIFIC OPERATIONS
-- =============================================

-- Replicate only INSERTs (ignore UPD/DEL):
MAP hr.employees, TARGET hr.employees,
  IGNOREUPDATES, IGNOREDELETES;

-- Ignore INSERTs only:
MAP hr.employees, TARGET hr.employees,
  IGNOREINSERTS;

Replicate from one source to multiple targets simultaneously. Common use: replicate production OLTP to multiple reporting databases or datawarehouses.

EXTRACT dp_report

One primary Extract writes one local trail. Two Data Pumps read the same local trail independently and send to different targets.

Fan-In (Multiple Sources → One Target)

Consolidate changes from multiple source databases into one target. Common use: consolidate regional databases into a central reporting store.

-- Target has TWO Replicat groups:
-- rep_us: applies trail from US source
-- rep_eu: applies trail from EU source

REPLICAT rep_us
USERIDALIAS tgtalias
EXTTRAIL ./dirdat/us
MAP sales.orders, TARGET global.orders;

REPLICAT rep_eu
USERIDALIAS tgtalias
EXTTRAIL ./dirdat/eu
MAP sales.orders, TARGET global.orders;

Each Replicat is independent. PKs must be globally unique to avoid conflicts (use DBMS_SEQUENCE with different starting points, or add source-identifier column).

Cascading (A → B → C)

Source A replicates to B, and B replicates to C. Used when networks don't allow direct A→C connectivity, or when B performs transformations.

-- On B: Replicat applies from A
-- On B: Extract captures the applied changes
-- (Loop prevention: EXCLUDEUSER ggadmin)

TRANLOGOPTIONS EXCLUDEUSER ggadmin
-- B's Extract ignores Replicat's own apply
PASSTHRU  -- If no transformation on B

Conflict Detection and Resolution (CDR) — needed for bidirectional/active-active replication where the same row might be updated on both sides concurrently.

-- GoldenGate CDR uses RESOLVECONFLICT in Replicat params
-- CDR requires ALLCOLS supplemental logging to compare before-images

REPLICAT rep_bidir

-- Conflict Resolution Algorithms:

-- 1. USEMAX — use the row with the highest value in specified column (e.g., timestamp)
MAP hr.employees, TARGET hr.employees,
  RESOLVECONFLICT(UPDATEROWEXISTS,
    (DEFAULT, USEMAX(last_updated_ts)));

-- 2. USEMIN — use the row with the lowest value
MAP hr.orders, TARGET hr.orders,
  RESOLVECONFLICT(INSERTROWEXISTS,
    (DEFAULT, USEMIN(order_amount)));

-- 3. USEDELTA — apply the arithmetic delta of the change (for numeric columns)
MAP hr.account_balance, TARGET hr.account_balance,
  RESOLVECONFLICT(UPDATEROWEXISTS,
    (balance, USEDELTA));

-- 4. OVERWRITE — last write wins (source overwrites target regardless)
MAP hr.employees, TARGET hr.employees,
  RESOLVECONFLICT(UPDATEROWEXISTS,
    (DEFAULT, OVERWRITE));

-- 5. DISCARD — discard the conflicting record (write to discard file)
MAP hr.employees, TARGET hr.employees,
  RESOLVECONFLICT(UPDATEROWEXISTS,
    (DEFAULT, DISCARD));

-- Conflict scenarios to handle:
-- INSERTROWEXISTS — INSERT but row already exists (duplicate key)
-- UPDATEROWEXISTS — UPDATE conflicts with concurrent update
-- UPDATEROWMISSING — UPDATE but target row doesn't exist
-- DELETEROWEXISTS — DELETE conflicts with update
-- DELETEROWMISSING — DELETE but row doesn't exist
Section 08

Zero-Downtime Migration

Using GoldenGate to migrate a live production database with zero (or near-zero) downtime — the most valuable real-world use case.

🎯 Migration Scenarios

  • Oracle 11g/12c → Oracle 19c (upgrade)
  • On-premises Oracle → Oracle Autonomous DB
  • Oracle → PostgreSQL (heterogeneous)
  • Physical server → AWS EC2 / OCI (platform move)
  • Single instance → RAC
  • Exadata replatforming

⏱ Why Zero Downtime?

  • Traditional methods (Data Pump export/import) require hours of downtime for large DBs
  • GoldenGate initial load + CDC sync means source stays live
  • Only downtime: final cutover (minutes, not hours)
  • Can verify target data quality before cutover
  • Can roll back by keeping source live until confident

Migration Phases — Step by Step

1

Phase 1: Setup & Supplemental Logging (1-2 hours)

Install and configure GoldenGate on both source and target. Enable supplemental logging, configure credentials, set ENABLE_GOLDENGATE_REPLICATION=TRUE. Set up Manager on both sides. Note the current SCN — this becomes your "start SCN".

-- Record start SCN
SELECT current_scn FROM v$database;
-- Example: 987654321  ← remember this
2

Phase 2: Start Extract at Start SCN

Start Extract from the noted SCN so no changes during initial load are missed. Extract begins writing to trail files — it can queue days worth of changes if the initial load takes time.

GGSCI> ADD EXTRACT ext_hr, INTEGRATED TRANLOG, SCN 987654321
GGSCI> ADD EXTTRAIL ./dirdat/lt, EXTRACT ext_hr
GGSCI> REGISTER EXTRACT ext_hr DATABASE
GGSCI> START EXTRACT ext_hr
3

Phase 3: Initial Data Load (hours to days)

Load the bulk data from source to target. Multiple options:

  • Option A (SOURCEISTABLE): GoldenGate's built-in initial load — Export from source using SOURCEISTABLE Extract, apply via Special-Run Replicat on target
  • Option B (Data Pump export/import): Use expdp/impdp for the bulk load (while CDC Extract queues changes)
  • Option C (Oracle ZDM): Oracle Zero Downtime Migration tool (handles GoldenGate orchestration automatically)
-- SOURCEISTABLE initial load approach:
GGSCI> ADD EXTRACT e_init, SOURCEISTABLE
GGSCI> ADD RMTTRAIL ./dirdat/il, EXTRACT e_init
GGSCI> EDIT PARAMS e_init
-- e_init.prm:

Stop writes to source (brief maintenance window), wait for Replicat to drain to zero lag, then redirect application connections to target. This is the only "downtime" — typically 1-10 minutes.

--    (put load balancer in maintenance mode)

-- 2. Wait for Extract to drain
GGSCI> SEND EXTRACT ext_hr, LOGEND
GGSCI> LAG EXTRACT ext_hr  -- wait until 0

-- 8. REMOVE HANDLECOLLISIONS from Replicat params

Phase 7: Post-Cutover (optional reverse replication)

Keep reverse replication running for a rollback window — if target has issues, you can fail back to source. Set up reverse replication (target → source) before cutover for safety. Once satisfied, decommission source and reverse replication.

GoldenGate is a log-based Change Data Capture tool that replicates at the logical (SQL row) level. It reads redo logs, captures individual DML/DDL changes, and applies them to a target database using SQL. It supports heterogeneous replication (Oracle → PostgreSQL, MySQL, etc.), schema transformations, filtering, and bidirectional active-active setups.

Data Guard replicates at the physical (redo block) level — it ships entire redo log streams and applies them to a standby database that is a block-for-block copy of the primary. It requires source and target to be the same Oracle version and platform. It doesn't support heterogeneous targets, filtering, or transformations.

Key difference: Data Guard is Oracle-to-Oracle block-level DR; GoldenGate is logical, heterogeneous, transformational replication. Both can coexist — many shops run Data Guard for HA/DR and GoldenGate for migration or reporting offload.

Manager — Master controller process. Runs on both source and target. Listens on port 7809. Starts, stops, and monitors Extract and Replicat. Purges old trail files. Allocates dynamic ports for Collector processes. Must be running before any other process can start.

Extract — Runs on source server. Reads Oracle redo/archive logs (via LogMiner in Integrated mode) and captures committed DML and DDL changes. Writes captured changes to local trail files. Two types: Primary Extract (reads logs) and Data Pump (reads trail, sends to target).

Data Pump — A secondary Extract process on the source server. Reads local trail files and transmits them over TCP/IP to the target server's Collector, which writes them as remote trail files. Decouples primary Extract from network latency.

Replicat — Runs on target server. Reads remote trail files and applies changes to the target database using SQL (Classic) or via Oracle's XStream inbound server (Integrated). Maintains a checkpoint table in the target DB for restart recovery.

Oracle's redo log normally records only the changed columns for an UPDATE — not the full row. This is sufficient for crash recovery (Oracle knows the before-state from rollback segments), but GoldenGate needs to identify which row on the target to update or delete.

Without supplemental logging, GoldenGate can't determine the WHERE clause for UPDATE/DELETE statements on the target, because the redo log might only contain "salary was changed to 5000" without identifying which employee.

Supplemental logging adds before-image column values to the redo log so GoldenGate can reconstruct the full row identifier. There are two levels:

  • DB-level minimal: ALTER DATABASE ADD SUPPLEMENTAL LOG DATA — adds redo-level support (bare minimum)
  • Table-level: ADD TRANDATA table ALLCOLS — adds all column values so GoldenGate can identify rows without a PK

Classic Extract (TRANLOG mode) — reads Oracle redo/archive log files directly from the OS file system using Oracle's OCI/log reader interface. It accesses the physical redo log files. This mode is deprecated in Oracle 18c and removed in Oracle 21c.

Integrated Extract — registers with Oracle's LogMiner server (via REGISTER EXTRACT ... DATABASE). Oracle's LogMiner infrastructure mines the redo logs and pushes Logical Change Records (LCRs) to GoldenGate Extract as a mining client. This requires ENABLE_GOLDENGATE_REPLICATION=TRUE and adequate STREAMS_POOL_SIZE.

Advantages of Integrated: supports CDB/PDB architecture (12c+), handles LOBs and other complex datatypes better, supports all Oracle compression types, and is the only option in Oracle 21c+.

A trail file is a flat binary file that stores captured change records — it's the hand-off point between GoldenGate processes. Extract writes to trail, Data Pump and Replicat read from trail.

Naming: two-character user-defined prefix (e.g., "lt" for local trail, "rt" for remote trail) + nine-digit sequence number: lt000000001, lt000000002, etc.

Location: dirdat/ directory under $OGG_HOME. Default max size: 500 MB. A new file is created when the current one reaches max size or when Extract restarts.

Purging: Manager's PURGEOLDEXTRACTS parameter with USECHECKPOINTS safely deletes trail files that all downstream processes (Data Pump, Replicat) have already consumed and checkpointed. Never manually delete trail files while processes are running.

In bidirectional replication, if DB A's Extract captures Replicat's own changes (changes applied by Replicat from DB B), those changes will be sent back to DB B — creating an infinite loop.

Two methods:

  • Classic — EXCLUDEUSER: Add TRANLOGOPTIONS EXCLUDEUSER ggadmin to Extract on each side. Extract ignores any changes committed by the GoldenGate Replicat user (ggadmin), since Replicat always commits under its own DB user.
  • Integrated — Transaction Tagging: Add DBOPTIONS SETTAG 10 in the Replicat parameter file. Replicat marks each transaction it applies with tag value 10. Then in Extract parameter file: TRANLOGOPTIONS EXCLUDETAG 10 — Extract ignores all transactions tagged with value 10.

Transaction tagging is preferred for Integrated Extract because EXCLUDEUSER only works if all Replicat applies are done under the same Oracle user.

HANDLECOLLISIONS is a Replicat parameter that tells GoldenGate to silently handle two common apply errors instead of abending:

  • ORA-00001 (unique constraint violated on INSERT) — treated as an UPDATE instead
  • ORA-01403 (no data found on UPDATE/DELETE) — the operation is silently discarded

When to use: During initial data load synchronization. When you use Data Pump (expdp) to load the initial dataset while GoldenGate is already capturing changes from that SCN, some rows captured by Extract were already loaded by Data Pump — so Replicat would get ORA-00001 when trying to re-INSERT them. HANDLECOLLISIONS resolves this.

Important: Remove HANDLECOLLISIONS after initial sync is complete. Leaving it permanently ON will silently hide real data integrity errors in production.

The process has three phases:

  1. Start GoldenGate at a baseline SCN — note the current SCN, start Extract from that SCN. GoldenGate now captures every change going forward into trail files.
  2. Initial load — while Extract queues changes in trail files, do a full bulk load of the existing data (Data Pump expdp/impdp, SOURCEISTABLE, or direct path). Source stays fully live throughout this phase.
  3. CDC sync + cutover — start Replicat. It applies the backlog of queued changes (catching up from the initial-load SCN to current). Lag drops to near-zero. Stop application writes briefly, drain remaining lag, point application to target. This "downtime" is typically 1-10 minutes regardless of database size.

This works because GoldenGate decouples the "bulk data movement" phase from the "change catch-up" phase. The source never needs to stop accepting writes during the bulk load.

Lag can occur at three points:

  • Extract lag — Extract falling behind the source DB redo log. Causes: high DML volume exceeding log mining speed, STREAMS_POOL_SIZE too small, archive logs being deleted before Extract reads them. Fix: increase STREAMS_POOL, extend archive retention, consider table filtering.
  • Network lag — Data Pump can't send trail data fast enough. Trail files build up on source. Causes: network bandwidth, latency, WAN links. Fix: add COMPRESS to RMTHOST in Data Pump param; use Microservices Distribution Server with HTTPS compression.
  • Replicat lag — Replicat applying slower than Extract captures. Causes: target DB under load, blocking on target sessions, single-threaded Classic Replicat. Fix: switch to Parallel or Integrated Replicat, add BATCHSQL, increase MAXAPPLYTHREADS.

Diagnosis: LAG EXTRACT * and LAG REPLICAT * — if only Replicat is lagging, the bottleneck is on the target side.

The checkpoint table (e.g., ggadmin.gg_checkpoint) is a table created in the target database that stores Replicat's current read position in the trail file. It records the trail file sequence number and byte offset (RBA) of the last successfully committed transaction.

Why important: If the target DB or Replicat crashes, Replicat reads its checkpoint from the table on restart to determine exactly where to resume. Without it (or if using only the file-based checkpoint in dirchk/), a crash mid-transaction could result in partial applies or duplicates.

The checkpoint table survives database restarts, which the in-memory checkpoint state does not. It provides transactional recovery semantics — Replicat only updates the checkpoint after each transaction is fully committed to the target.

Create it with: ADD CHECKPOINTTABLE ggadmin.gg_checkpoint; reference it in ADD REPLICAT ... CHECKPOINTTABLE ggadmin.gg_checkpoint.

Classic Architecture: All processes (Manager, Extract, Replicat, Data Pump, Collector) are standalone OS-level executables managed via the GGSCI command-line tool. Configuration is through parameter files in dirprm/. This is the traditional architecture available since early OGG versions.

Microservices Architecture (OGG 18c+): Each component is a RESTful web service — Service Manager, Administration Server, Distribution Server (replaces Data Pump), Receiver Server (replaces Collector), and Performance Metrics Server. Managed via HTML5 web UI or REST API. Uses HTTPS for inter-service communication. The adminclient CLI replaces GGSCI.

Key differences: Microservices supports REST API automation, HTTP/HTTPS trail delivery, OAuth2/token authentication, and is the architecture used by OCI GoldenGate (fully managed cloud service). Classic is still available for 19c but Microservices is recommended for all new deployments.

DDL replication is NOT enabled by default in GoldenGate — it requires explicit configuration in both Extract and Replicat parameter files.

In Extract: Add DDL clause to capture DDL. You can filter by object type:

DDL INCLUDE MAPPED OBJTYPE 'TABLE'
DDL INCLUDE MAPPED OBJTYPE 'INDEX'

In Replicat: Add DDL clause to apply DDL, and optionally DDLERROR DEFAULT DISCARD to handle DDL errors gracefully.

DDL replication is particularly useful when the target needs to stay schema-synchronized with the source over time (e.g., during an extended migration window). However, some DDL types (like TRUNCATE) need special handling, and DDL that changes column types can break replication if target definitions diverge.

CDR is needed in bidirectional (active-active) replication when the same row might be updated simultaneously on both databases. Without CDR, whichever update arrives last wins — which may not be the correct business outcome.

GoldenGate CDR is configured via RESOLVECONFLICT in the Replicat parameter file. Resolution algorithms:

  • USEMAX(column) — the record with the highest value in the specified column wins (usually a timestamp or version number)
  • USEMIN(column) — the record with the lowest value wins
  • USEDELTA — apply the arithmetic difference (for running totals / counters)
  • OVERWRITE — last write always wins (source overwrites target)
  • DISCARD — conflicting record written to discard file, not applied

CDR requires ALLCOLS supplemental logging so GoldenGate has before-image values to compare.

  • Classic Replicat — single-threaded, applies SQL directly via OCI. Strict transaction ordering. Best for: small-medium workloads where ordering is critical, heterogeneous targets. Simple to set up.
  • Integrated Replicat — Oracle-to-Oracle only; uses XStream inbound server for parallel apply. Oracle manages apply coordination internally. Best for: high-volume Oracle-to-Oracle replication where target is 12c+.
  • Parallel Replicat — multiple apply threads managed by GoldenGate (not Oracle). Configurable via MAXAPPLYTHREADS and MAPPARALLELISM. Works for heterogeneous targets. Best for: highest throughput scenarios, cross-platform migration.
  • Coordinated Replicat — multiple Replicat groups coordinated by a coordinator process. Used for extremely large schemas split across multiple trail readers. Best for: very high-volume fan-in scenarios.
  • Special-Run Replicat — runs once and exits when it reaches end of trail. Used with SOURCEISTABLE initial loads.

Key monitoring points:

  • Process status — all processes should be RUNNING. Any ABENDED status requires immediate investigation (INFO ALL).
  • Extract lag — should be < 30 seconds for OLTP. Growing lag signals a capture or archive log issue (LAG EXTRACT *).
  • Replicat lag — should be < 30 seconds. Growing lag signals apply or target DB issue (LAG REPLICAT *).
  • Heartbeat table — query GG_LAG_HISTORY; flat line means replication is broken even if GGSCI shows RUNNING.
  • Trail file disk space — if Replicat falls behind, trail files accumulate. Monitor df -h /u01 and INFO EXTTRAIL ... DETAIL.
  • Discard file size — a growing discard file means Replicat is silently dropping rows (data integrity issue).
  • ggserr.log — master error log; check for WARNING and ERROR entries daily.
  • STATS throughput — STATS EXTRACT/REPLICAT gives operations/second; significant drops indicate issues.

In production, integrate with OEM (Oracle Enterprise Manager with GoldenGate Management Pack), Prometheus/Grafana using the Metrics Server API, or set up shell scripts querying GGSCI and alerting via PagerDuty/Nagios.

Interview Q&A

Oracle GoldenGate — Interview Questions

Commonly asked GoldenGate interview questions covering architecture, trail files, parameter files, and replication best practices.

EXTRACT runs on the source database system. It mines the Oracle redo/archive logs (or supplemental log data) to capture all committed DML and DDL changes. It writes these changes in GoldenGate's proprietary binary format to Trail files on the local filesystem.

REPLICAT runs on the target system. It reads the Trail files (either local or received from a Data Pump) and applies the changes to the target database using standard SQL (or batch apply for performance). Replicat maintains its own checkpoint so it can restart exactly where it left off after a failure.

Key distinction: Extract captures; Replicat applies. The Data Pump process (optional) transports trail files between Extract and Replicat.

Trail files are the backbone of GoldenGate replication — they are sequential binary files that store captured change records (insert/update/delete/DDL). Each record includes the table name, operation type, before/after images, and timestamp.

Trail files serve as the persistence and buffer layer between Extract and Replicat. If Replicat falls behind or the target is temporarily unavailable, trail files accumulate changes without blocking the source. They also enable multiple Replicat processes to consume the same trail for fan-out replication to multiple targets.

Trail files are created in segments (typically 100MB each) with a 2-character prefix (e.g., lt). Older trails are purged via the PURGEOLDEXTRACTS parameter in the Manager's prm file.

The GoldenGate Data Pump (not to be confused with Oracle Data Pump expdp/impdp) is a secondary Extract group that reads local trail files and sends them to a remote trail on the target server.

Benefits of using a Data Pump: (1) Decoupling — network issues don't impact the primary Extract; Extract writes to local trail and Data Pump picks up when the network recovers. (2) Fan-out — one Data Pump can send to multiple remote trails simultaneously. (3) Filtering & transformation — can apply column mappings or filtering between source and target trail.

Without a Data Pump, EXTRACT would write directly to the remote trail — meaning a network failure would stall Extract and potentially impact source database performance.

HANDLECOLLISIONS is a Replicat parameter that tells GoldenGate to ignore or resolve conflicts that arise during the initial load phase when both source changes and the initial data load are being applied simultaneously.

Specifically: duplicate-key errors on INSERT are handled by converting to UPDATE, and "row not found" errors on UPDATE or DELETE are silently ignored. This allows replication to start while data is still being loaded, without errors stopping the Replicat.

Important: HANDLECOLLISIONS should only be used during the initial load period. Once all data is synchronized and replication is confirmed current, remove this parameter. Leaving it on permanently will silently mask legitimate replication errors.

Oracle's redo logs, by default, only record the minimal information needed for instance recovery — typically just the rowid and changed column values. GoldenGate's Extract needs more: the before image (original column values) to identify the row on the target and to detect conflicts.

Supplemental logging adds additional column data to the redo records. Minimum supplemental logging (ALTER DATABASE ADD SUPPLEMENTAL LOG DATA) adds primary key columns to every redo entry. ALL COLUMNS supplemental logging adds all columns — required when the target schema has different key structures.

For bi-directional (active-active) replication, you typically need ALL COLUMNS supplemental logging plus a LOGALLSUPCOLS parameter to ensure sufficient data is available for conflict detection and resolution.
