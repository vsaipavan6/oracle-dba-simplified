Section 1

Oracle Patch Types

Oracle releases different patch types on different schedules. Understanding them is essential for planning maintenance windows.

Patch TypeFrequencyScopeRequires Downtime
Release Update (RU)Quarterly (Jan/Apr/Jul/Oct)Bug fixes + security + PSEYes — ORACLE_HOME outage
Release Update Revision (RUR)Between RUsSecurity-only subset of RUYes — smaller patch
One-off PatchOn demandSingle bug fixYes — may conflict with RU
Critical Patch Update (CPU)QuarterlySecurity fixes onlyYes
Diagnostic PatchOn demandTracing/diagnosability onlySometimes
Data Patch (datapatch)After RU applyDictionary SQL changesDB must be open

Oracle Quarterly Patch Schedule

Release Updates (RUs) are released on the third Tuesday of January, April, July, and October. Known as the "Critical Patch Update (CPU) calendar." Most production shops apply RUs 1-2 quarters behind latest to allow stabilization.

Patch Conflict Resolution

Before applying, run opatch prereq CheckConflictAgainstOHWithDetail to detect conflicts. Use Patch Conflict Matrix on My Oracle Support or merge conflicting patches via a Custom Patch Set (contact Oracle Support).

Section 2

OPatch Utility — Complete Reference

OPatch is Oracle's patch management tool. Always use the latest OPatch compatible with your Oracle version.

OPatch Command Reference 
# Verify OPatch installation
$ORACLE_HOME/OPatch/opatch version

# List all installed patches (patch IDs)
$ORACLE_HOME/OPatch/opatch lspatches

# Check inventory for a specific patch ID
$ORACLE_HOME/OPatch/opatch lsinventory -patch_id 35648110

# Pre-check before applying (must pass before patching)
$ORACLE_HOME/OPatch/opatch prereq CheckConflictAgainstOHWithDetail \
  -phBaseDir /tmp/patch/35648110

# Apply a patch (ORACLE_HOME must be down for binary patches)
$ORACLE_HOME/OPatch/opatch apply /tmp/patch/35648110

# Rollback a specific patch
$ORACLE_HOME/OPatch/opatch rollback -id 35648110

# Apply RU using OPatch auto (handles complex bundles)
$ORACLE_HOME/OPatch/opatch auto /tmp/patch/35648110 \
  -oh $ORACLE_HOME -ocmrf /tmp/ocm.rsp
Section 3

Applying a Release Update — Step by Step

The complete patching procedure: from pre-checks to post-validation. Never skip steps in production.

1

Download & Stage Patch

Download from My Oracle Support. Unzip to /tmp/patch. Verify checksum with md5sum.

2

Backup ORACLE_HOME

cp -rp $ORACLE_HOME $ORACLE_HOME.bak — essential for quick rollback if patch fails.

3

RMAN Backup

Full RMAN backup before any patching. Non-negotiable for production.

4

Stop Database & Listener

shutdown immediate + lsnrctl stop. Verify no processes remain: ps -ef | grep pmon.

5

Apply OPatch

opatch apply or opatch auto. Capture full output to log file.

6

Run Datapatch

Start DB, then $ORACLE_HOME/OPatch/datapatch -verbose to apply data dictionary changes.

7

Run utlrp.sql

Recompile invalid objects: @?/rdbms/admin/utlrp.sql. Check count of INVALID objects before/after.

8

Validate Patch

opatch lspatches + query registry$sqlpatch. Check alert log for ORA- errors.

9

Run Post-Patch Tests

Execute application smoke tests, check critical query plans, verify connections, confirm no new ORA- errors.

Post-patch validation queries 
-- Verify patch in registry
SELECT patch_id, patch_uid, version, action,
       status, action_time, description
FROM   sys.registry$sqlpatch
ORDER BY action_time DESC;

-- Check for invalid objects (should be 0 after utlrp)
SELECT owner, object_type, COUNT(*)
FROM   dba_objects
WHERE  status = 'INVALID'
GROUP BY owner, object_type
ORDER BY 1;

-- Verify DB component status
SELECT comp_id, comp_name, version, status
FROM   dba_registry
ORDER BY comp_id;
Section 4

Oracle Database Version Upgrade

Upgrading from 11g/12c/18c to 19c — the most common upgrade path. 19c is the Long Term Support Release (LTS) through 2030.

Pre-Upgrade Checklist

  • Run Pre-Upgrade Information Tool (preupgrade.jar) on source DB
  • Fix all fixup scripts generated by preupgrade.jar
  • Gather fresh statistics (DBMS_STATS.GATHER_DATABASE_STATS)
  • Take full RMAN backup of source database
  • Capture SQL Plan Baselines for critical SQL
  • Document current init.ora parameters
  • Verify minimum SYSTEM/SYSAUX tablespace free space (≥1GB)
  • Test upgrade on non-production database first

Pre-Upgrade Tool (preupgrade.jar)

# Run pre-upgrade checks (target ORACLE_HOME)
java -jar $NEW_ORACLE_HOME/rdbms/admin/preupgrade.jar \
  TERMINAL TEXT

# This generates:
# preupgrade.log  — issues and fixups
# preupgrade_fixups.sql — run on SOURCE DB
# postupgrade_fixups.sql — run AFTER upgrade

# Run fixups on source (old ORACLE_HOME)
sqlplus / as sysdba
SQL> @preupgrade_fixups.sql

# Check invalid objects before upgrade
SELECT COUNT(*) FROM dba_objects WHERE status='INVALID';
Section 5

AutoUpgrade Tool (Recommended for 19c)

AutoUpgrade is Oracle's preferred upgrade method for 19c. It handles pre-checks, upgrade, post-fixups, and rollback — all automated.

AutoUpgrade — Analyze, Deploy, Rollback 
# 1. Create config file (config.cfg)
upg1.log_dir=/u01/autoupgrade_logs
upg1.sid=ORCL
upg1.source_home=/u01/app/oracle/product/12.2.0/dbhome_1
upg1.target_home=/u01/app/oracle/product/19c/dbhome_1

# 2. Analyze mode — checks only, no changes
java -jar $ORACLE_HOME/rdbms/admin/autoupgrade.jar \
  -config config.cfg -mode analyze

# 3. Fixup mode — apply pre-upgrade fixups
java -jar $ORACLE_HOME/rdbms/admin/autoupgrade.jar \
  -config config.cfg -mode fixup

# 4. Deploy mode — full upgrade
java -jar $ORACLE_HOME/rdbms/admin/autoupgrade.jar \
  -config config.cfg -mode deploy

# 5. Monitor upgrade from interactive console
# Inside autoupgrade: lsj (list jobs), status -job 100
# Resume after failure: resume -job 100

# If upgrade fails — rollback to source
# Inside console: abort -job 100, then restore from RMAN
Section 6

Patches & Upgrades — Interview Q&A

A Release Update (RU) is a cumulative quarterly patch containing hundreds of bug fixes, security patches, and recommended fixes. It supersedes all previous one-off patches. A one-off (interim) patch targets a single specific bug fix and is applied between RUs. Best practice: apply RUs regularly and avoid one-off patches unless you hit a specific production bug, as one-offs may not be included in the next RU and can cause conflicts.

datapatch applies SQL changes to the data dictionary after binary patches (OPatch) are installed. OPatch updates ORACLE_HOME files (binaries, libraries). datapatch updates the database internals (SYS objects, packages, views). You MUST run datapatch after every RU or one-off patch that includes SQL changes. Run it while the database is open: $ORACLE_HOME/OPatch/datapatch -verbose.

DBUA (Database Upgrade Assistant) is a GUI tool that guides DBAs through an upgrade interactively. AutoUpgrade is a command-line Java tool that automates the entire lifecycle: analyze → fixup → upgrade → postupgrade → optionally time-zone upgrade. AutoUpgrade is Oracle's recommended approach for 19c and later, supports unattended upgrades of multiple databases, provides built-in rollback capability, and handles all pre/post-fixup scripts automatically.

  • If OPatch step failed: opatch rollback -id PATCH_ID — reverses binary changes to ORACLE_HOME
  • If datapatch failed: restore ORACLE_HOME backup, restore database from RMAN pre-patch backup
  • If DB won't start after patch: restore ORACLE_HOME from backup (cp -rp $ORACLE_HOME.bak $ORACLE_HOME)
  • Always have a full RMAN backup and ORACLE_HOME tar backup before patching
  • With AutoUpgrade: the tool creates a guaranteed restore point — use abort -job N for rollback
