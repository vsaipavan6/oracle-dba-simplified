Oracle Architecture
Explained Simply

SGA, PGA, LGWR, DBWn, PMON — finally understood without the Oracle manual headache. Real analogies, real production context.

12 min read June 2025 Oracle DBA Simplified Oracle 19c

It's 2 AM. Your phone rings. "The Oracle database is down." Before you can fix anything, you need to understand what just broke — was it the files on disk? The memory? A background process? This article will give you a mental model of Oracle's architecture so clear, you could draw it on a whiteboard in an interview and explain every box.

1
The Foundation

Database vs Instance — The 60-Second Version

Most people use "Oracle database" to mean everything. But Oracle has a very specific split:

The Database
Files on disk

The physical set of files: datafiles (.dbf), online redo log files, and the control file. These exist permanently on disk. They don't care if any process is running.

The Instance
Memory + Processes

The SGA (shared memory) plus all the background processes (PMON, SMON, DBWn, etc.). The instance exists only while Oracle is running. It accesses the database files to serve users.

🍳
The Restaurant Analogy

Think of the database as the kitchen pantry — all the ingredients (data) are stored there. The instance is the kitchen itself: the chefs (processes), the counters (memory), and the equipment. The pantry exists even when the restaurant is closed. The kitchen only "exists" when there are people in it working.

In Oracle RAC, multiple instances can share one database — multiple kitchens drawing from the same pantry. That's the magic (and complexity) of RAC.

The SGA — Oracle's Shared Brain

Database Buffer Cache — The Speed Trick

Oracle doesn't read data directly from disk on every query. That would be painfully slow. Instead, it loads data blocks from disk into the buffer cache in RAM, and serves subsequent requests from there.

📚
Think of it like a browser cache

When you visit a webpage, your browser saves it locally. The next visit is instant. Oracle's buffer cache does the same for 8KB data blocks. First read = disk (slow). Next read = RAM (fast). This is called a cache hit.

The buffer cache uses an LRU (Least Recently Used) algorithm — blocks that haven't been accessed recently get pushed out to make room for new blocks. Frequently accessed blocks ("hot" blocks) stay in cache. If you check V$BH, you can see exactly which blocks are in your cache right now.

💡
Production Insight

When users complain "the database is slow at 9 AM but fine by 10 AM," it's often because the buffer cache is cold at startup. As queries run and blocks load into cache, performance improves. This is called the "cache warm-up effect."

Shared Pool — The Recipe Book Everyone Shares

The Shared Pool is Oracle's most complex SGA component. It has two main sub-areas:

Library Cache
SQL plans + PL/SQL code

Stores parsed SQL statements and their execution plans. When two users run the same query, the second one reuses the cached plan — no re-parsing needed. This is a soft parse (fast). Having to re-parse from scratch is a hard parse (slow and CPU-expensive).

Data Dictionary Cache
Object metadata

Caches metadata rows from the data dictionary — table definitions, column types, privilege info, etc. Without this, every SQL statement would need to query SYS tables on disk to find out if your table even exists. The cache makes this instantaneous.

⚠️
The Shared Pool Danger Zone

If applications use literal values in SQL instead of bind variables — WHERE id = 1234 vs WHERE id = :id — each value creates a different SQL hash. Oracle can't reuse the cached plan, so every statement is a hard parse. A busy OLTP system doing 1,000 hard parses per second will grind to a halt from Shared Pool latch contention. This is one of the most common performance problems in Oracle.

Redo Log Buffer — The Diary That Saves Lives

Every single change made to the database — every UPDATE, DELETE, INSERT — is first recorded in the Redo Log Buffer in memory. This is Oracle's "write-ahead logging" strategy. You record what you're about to do before you do it.

"The redo log buffer is Oracle's insurance policy. If the power cuts out right after a COMMIT, Oracle can replay everything from the redo log to get your data back. Without redo, a crash would mean permanent data loss."

LGWR (Log Writer — more on this later) flushes the redo log buffer to the online redo log files on disk:

  • On every COMMIT (synchronously — you wait)
  • Every 3 seconds (background flush)
  • When the buffer is 1/3 full
  • Before DBWn writes to datafiles (write-ahead rule)
💡
Why COMMIT feels slightly slow

When you COMMIT, Oracle waits for LGWR to write the redo to disk before returning "commit complete" to your application. This disk write is synchronous. If your redo logs are on slow storage (spinning HDD, NFS), every COMMIT is slow. Move redo logs to fast SSD — it's the single biggest win for OLTP performance.

Memory Architecture

The PGA — Your Private Notepad

While the SGA is shared, the PGA (Program Global Area) is completely private to each server process. No sharing, no contention. Every session gets its own PGA.

PGA — Private per server process
Sort Area
(ORDER BY, GROUP BY)
Hash Join Area
(join operations)
Private SQL Area
(bind variables, cursor state)
Session Memory
(UGA in dedicated mode)

The sort area and hash join area are the most critical — they hold the working data for SQL operations like ORDER BY, GROUP BY, and hash joins. If these fit in PGA memory, the operation runs entirely in RAM. If they don't, Oracle spills to TEMP tablespace on disk, and performance tanks dramatically.

🍳
The Chef's Counter Space

Imagine a chef who needs 10 cutting boards to prepare a complex dish. If the kitchen counter (PGA) only fits 3 boards, the chef has to keep going back and forth to storage (temp disk). It's 10x slower. A chef with more counter space is just faster. That's PGA for Oracle's sorting operations.

SQL — Check PGA usage and advisor 
-- See current PGA allocation
SELECT name, ROUND(value/1024/1024,1) mb
FROM   v$pgastat
WHERE  name IN ('total PGA allocated', 'cache hit percentage',
                'aggregate PGA target parameter');

-- Spill to disk check: if "over allocation count" > 0, PGA is too small
SELECT name, value
FROM   v$pgastat
WHERE  name = 'over allocation count';
4
Background Processes

The Night Shift Crew — Background Processes

Oracle runs dozens of background processes 24/7, each with a specific job. Here are the ones you must know:

PMON — The HR Manager
Process Monitor

PMON constantly scans all processes looking for dead connections. When a user disconnects abnormally (network drop, app crash), PMON sweeps in: rolls back the uncommitted transaction, releases all locks, and frees the server process resources. It also registers database services with the listener so new connections can find the database. In production: PMON is why you don't have to manually kill orphaned sessions after a network blip.

SMON — The Janitor + Paramedic
System Monitor

SMON has two critical jobs: (1) Instance recovery — if Oracle crashes, SMON runs instance recovery on restart: rolls forward the redo log (applies committed transactions that weren't written to disk), then rolls back uncommitted transactions using UNDO. This is completely automatic. (2) Temp cleanup — cleans up orphaned temporary segments (failed sorts, etc.) that are no longer needed. SMON is the reason you can crash Oracle and it comes back clean.

DBWn — The Lazy-Smart Librarian
Database Writer (up to 100 processes)

DBWn writes modified ("dirty") buffer cache blocks to datafiles on disk. The key insight: DBWn does NOT write on every COMMIT. It writes in batches when the buffer cache hits its dirty threshold, during checkpoints, or when tablespaces need to go offline. This lazy-but-smart batching is why Oracle is fast. It does multi-block scattered writes, much more efficient than one-write-per-transaction. Important: LGWR always writes redo to disk before DBWn writes data blocks — write-ahead logging rule.

LGWR — The Anxious Recorder
Log Writer

LGWR writes the redo log buffer to online redo log files on disk. Unlike DBWn, LGWR is not lazy — it writes synchronously on every COMMIT. Your application waits for this write to complete before getting "commit complete." This is the intentional cost of durability: you get a guarantee your data is safely on disk. If LGWR is waiting on slow I/O, all commits are slow. LGWR's speed is the single biggest factor in OLTP commit latency.

CKPT — The Checkpoint Officer
Checkpoint Process

CKPT triggers DBWn to write dirty blocks and updates the datafile headers and control file with the current checkpoint SCN. Why does this matter? It limits crash recovery time. If CKPT runs frequently, the gap between what's on disk and what's in the redo log is small — after a crash, instance recovery only needs to replay a small window of redo. Oracle's FAST_START_MTTR_TARGET parameter controls this tradeoff.

ARCn — The Backup Copyist
Archiver (multiple processes)

When a redo log group fills up and LGWR switches to the next one, ARCn copies the full redo log file to the archive log destination (local disk, ASM, or standby database). Without ARCn (i.e., without ARCHIVELOG mode), you can only recover from the last backup — no point-in-time recovery. With ARCn, you can recover to any point in time within your archive log history. This is why every production database runs in ARCHIVELOG mode.

5
Putting It Together

What Really Happens When You Run SELECT

Here's the full journey of a SELECT statement — from the moment you press Enter to the moment you see results:

  1. Client sends SQL to the Server Process. Your application (JDBC, SQL*Plus) sends the SQL text over Oracle Net to its dedicated server process on the database host.
  2. Parse Phase — check Shared Pool first. The server process generates a hash of your SQL text and searches the Library Cache. If an identical statement with the same execution plan exists → soft parse (reuse plan, fast). If not → hard parse (validate syntax, check privileges, run the Cost-Based Optimizer, generate a plan).
  3. Execute Phase — find the data blocks. The server process looks up which data blocks it needs in the buffer cache. For each block: (a) Cache hit → read from RAM immediately. (b) Cache miss → read the block from the datafile on disk into the buffer cache, then serve it.
  4. Consistency Check via UNDO. If the block has been modified by a concurrent transaction, Oracle constructs a consistent read version of it using UNDO data. You see the data as it was at your query's start time. This is Oracle's MVCC (Multi-Version Concurrency Control).
  5. Fetch Phase — return rows. Server process packages result rows and sends them to the client in batches (array fetch, typically 100 rows at a time). Your application fetches until no more rows.
✅
Important: SELECT never touches redo logs

SELECT statements don't generate redo. They don't modify anything (assuming no flashback queries). The only time a SELECT generates small amounts of redo is when it needs to pin a buffer cache block — but this is a tiny internal mechanism, not data redo.

6
Write Path

What Really Happens on UPDATE + COMMIT

This is where Oracle's durability guarantees come into play. Follow every step — it explains why Oracle can survive crashes:

  1. Parse the UPDATE statement (soft or hard parse as above).
  2. Find the data block in the buffer cache (load from disk if not already there).
  3. Generate an UNDO record — Oracle writes the before image (original row values) into a buffer cache block belonging to the UNDO tablespace. This enables rollback and read consistency for other sessions.
  4. Generate a REDO record — Oracle writes the change (both before and after images) into the Redo Log Buffer in SGA memory. This happens before modifying the data block.
  5. Modify the data block in the buffer cache — the block is now "dirty" (changed in memory, not yet on disk). The change is live in memory.
  6. COMMIT issued. LGWR writes the Redo Log Buffer to the online redo log file on disk — synchronously. Application waits. The moment this write completes, COMMIT returns success. Your data is durable.
  7. DBWn writes dirty blocks later — asynchronously, at its own pace. The data block itself reaches disk minutes (or even longer) after COMMIT. This is safe because redo is already on disk — Oracle can always replay it to reconstruct the data block if needed.

"The actual datafile write happens after COMMIT. That's intentional — it's what makes commits fast. Redo on disk is enough to survive a crash. The data block write is just optimization."

📋
The Project Manager Analogy

Think of COMMIT like a project manager approving a change. They write it in the meeting minutes (redo log) — that's the official record. The actual physical work (DBWn writing to disk) gets done later by the team. But the minutes are the proof it was approved. Even if the office burns down, you have the minutes.

Quick Reference

The Architecture Cheat Sheet

Memory Components
SGA
Shared memory: Buffer Cache + Shared Pool + Redo Buffer + Large Pool + Java Pool
Buffer Cache
Caches data blocks in RAM. LRU managed. Cache hit = fast. Miss = disk read (slow).
Shared Pool
Library Cache (plans) + Data Dictionary Cache (metadata). Bind variables = soft parse = fast.
Redo Log Buffer
Every change recorded here first. LGWR flushes to disk on COMMIT.
PGA
Private per session. Sort area, hash join area. Too small = spill to TEMP disk.
Background Processes
PMON
Cleans up dead sessions (rollback + release locks). Registers services with listener.
SMON
Instance recovery on startup (redo forward → undo uncommitted). Temp cleanup.
DBWn
Writes dirty buffer cache blocks to datafiles. Lazy/batched. Writes AFTER LGWR.
LGWR
Writes redo log buffer to redo log files. Synchronous on COMMIT. Fastest I/O path matters here.
CKPT
Signals DBWn, updates headers with checkpoint SCN. Limits crash recovery time.
ARCn
Archives full redo logs for point-in-time recovery. ARCHIVELOG mode = enabled archiving.
SQL Execution Flows
SELECT
Parse → Execute (buffer cache / disk) → MVCC via UNDO → Fetch to client. No redo.
UPDATE+COMMIT
Parse → UNDO record → REDO record → modify buffer → LGWR flush (sync) → COMMIT done → DBWn writes later.
Crash Recovery
SMON: roll forward redo → roll back uncommitted (using UNDO). Automatic and complete.
