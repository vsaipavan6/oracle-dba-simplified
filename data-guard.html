What Is Data Guard?

Purpose & Core Concepts

Data Guard is not just a backup — it is a continuously synchronized, always-ready replica of your production database that can take over in seconds.

Disaster Recovery

Automatic failover to standby when primary fails. Zero data loss possible with synchronous redo transport. RTO measured in seconds with Fast-Start Failover.

Active Data Guard

Physical standby stays open READ ONLY while applying redo. Offload reporting, backups, and ad-hoc queries to standby — reducing primary workload.

Planned Switchover

Zero-downtime maintenance — switch primary and standby roles gracefully. Useful for patching, upgrades, and data center migrations.

Key Terminology

Redo Data

Transaction log entries documenting every database change. The currency Data Guard uses to keep standbys in sync.

SRL

Standby Redo Logs — placeholder redo log files on the standby that receive redo from the primary before it is archived.

MRP

Managed Recovery Process — background process on physical standby that applies archived/standby redo logs to keep the standby current.

LSP

LogMiner Server Process — applies SQL changes to a logical standby database via SQL Apply.

Switchover

Planned, graceful role transition. Both databases participate — zero data loss. Fully reversible.

Failover

Emergency activation when primary is unavailable. May cause data loss if not fully synchronized. Old primary must be reinstated or dropped.

DGMGRL

Data Guard Manager command-line tool — manages the broker configuration. Simplifies all DG operations with a single interface.

Observer

Separate process that monitors the primary and triggers Fast-Start Failover automatically if the primary fails and is unreachable.

Database Roles

Types of Standby Databases

Three flavors of standby — choose based on your recovery objectives, reporting needs, and testing requirements.

Physical Standby

Most Common

An exact, block-for-block copy of the primary database maintained through Redo Apply (MRP process). Physically identical at the storage level — same datafiles, same block layout, same SCN. The recommended standby type for disaster recovery.

Supports Active Data Guard (READ ONLY + applying redo)
Can support ALL Oracle data types and DDL
Can offload RMAN backups from primary
Simplest to create using RMAN DUPLICATE
Fast-Start Failover supported
Cannot run DML/DDL (read-only unless ADG license)
Key Process: MRP (Managed Recovery Process)
• Reads archived logs / SRL on standby
• Applies changes block-by-block to datafiles
• Runs with ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
Physical Standby — Key Commands
-- Start Redo Apply (MRP)
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  DISCONNECT FROM SESSION;

-- Active Data Guard: read-only + apply
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  USING CURRENT LOGFILE DISCONNECT;

-- Cancel Redo Apply
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  CANCEL;

-- Verify apply is running
SELECT process, status, sequence#
FROM   v$managed_standby
WHERE  process = 'MRP0';

-- Check apply lag
SELECT name, value, unit
FROM   v$dataguard_stats
WHERE  name IN ('apply lag','transport lag');

Logical Standby

SQL Apply

Maintained via SQL Apply — redo is mined using LogMiner, converted to SQL statements, and applied to the standby. The logical standby is always open READ WRITE and can have additional objects not on the primary.

Database always OPEN — run reporting queries
Additional indexes, MVs, and tables allowed
Different physical structure from primary
Not all data types supported by SQL Apply
More complex to set up and maintain
Higher apply lag vs physical standby
Logical Standby — SQL Apply
-- Start SQL Apply
ALTER DATABASE
  START LOGICAL STANDBY APPLY IMMEDIATE;

-- Stop SQL Apply
ALTER DATABASE
  STOP LOGICAL STANDBY APPLY;

-- Monitor SQL Apply
SELECT status, applied_scn, latest_scn
FROM   v$logstdby_progress;

SELECT event, severity, status
FROM   dba_logstdby_events
ORDER BY event_time DESC
FETCH FIRST 20 ROWS ONLY;

-- Skip unsupported tables
EXECUTE DBMS_LOGSTDBY.SKIP(
  'DML', 'SCOTT', 'UNSUPPORTED_TABLE');

Snapshot Standby

Writable for Testing

A physical standby temporarily converted to a READ WRITE state for testing/development. Changes made during snapshot mode are discarded when converted back to physical standby — Flashback Database handles the rewind.

Full READ WRITE access for testing
Continues receiving redo from primary during testing
All test changes discarded on revert
No separate dev database needed
Requires Flashback Database enabled. Archivelog accumulates during snapshot period — ensure FRA has space.
Snapshot Standby Conversion
-- Prerequisites on standby
SELECT flashback_on FROM v$database;
-- Must be YES

-- Step 1: Stop MRP (Redo Apply)
ALTER DATABASE
  RECOVER MANAGED STANDBY DATABASE CANCEL;

-- Step 2: Convert to Snapshot Standby
ALTER DATABASE
  CONVERT TO SNAPSHOT STANDBY;
ALTER DATABASE OPEN;

-- ... do testing, run DML, etc. ...

-- Step 3: Revert back to Physical Standby
ALTER DATABASE
  CONVERT TO PHYSICAL STANDBY;
STARTUP MOUNT;
ALTER DATABASE
  RECOVER MANAGED STANDBY DATABASE
  DISCONNECT;

Data Protection

Protection Modes

Three modes that define the balance between data protection and primary database performance. The mode is set on the primary database.

Zero Data Loss

Maximum Protection

Guarantees zero data loss even if the primary database fails. Every transaction must be written to a standby redo log on at least one synchronized standby before the primary commits.

Redo transport: SYNC + AFFIRM
If standby unavailable: primary SHUTS DOWN
Requires at least 1 synchronized standby
Highest availability cost — primary can stall
ALTER DATABASE
  SET STANDBY DATABASE TO MAXIMIZE
  PROTECTION;

-- Transport: SYNC AFFIRM
LOG_ARCHIVE_DEST_2=
'SERVICE=stby SYNC AFFIRM
 VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE)
 DB_UNIQUE_NAME=stby'
Recommended

Maximum Availability

Best balance of protection and availability. Zero data loss when standby is reachable. If the standby becomes unavailable, the primary continues in Maximum Performance mode rather than shutting down.

Redo transport: SYNC AFFIRM (when available)
If standby fails: primary continues (no shutdown)
Zero data loss when configured correctly
Default recommendation for production
ALTER DATABASE
  SET STANDBY DATABASE TO MAXIMIZE
  AVAILABILITY;

-- Transport: SYNC AFFIRM
-- Primary won't stall if standby unavail
-- FSFO most effective in this mode
Default

Maximum Performance

Default mode. Highest primary database performance. Redo is shipped asynchronously — primary commits without waiting for standby acknowledgment. Some data loss possible if primary fails.

Redo transport: ASYNC NOAFFIRM
Primary performance not impacted by network
Some data loss possible (seconds to minutes)
Best for geographically distant standbys
ALTER DATABASE
  SET STANDBY DATABASE TO MAXIMIZE
  PERFORMANCE;

-- Transport: ASYNC (default)
LOG_ARCHIVE_DEST_2=
'SERVICE=stby ASYNC
 VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE)
 DB_UNIQUE_NAME=stby'

Step-by-Step

Physical Standby Creation

Complete walkthrough using RMAN DUPLICATE — the recommended and simplest method for creating a physical standby database in Oracle 19c.

Prerequisites Checklist

ARCHIVELOG Mode on Primary
SELECT log_mode FROM v$database; — must show ARCHIVELOG
FORCE LOGGING Enabled
ALTER DATABASE FORCE LOGGING; — ensures all changes generate redo
Password File on Both Servers
orapwd file=$ORACLE_HOME/dbs/orapwSID — SYSDG and SYSDBA entries
Same Oracle Version
Primary and standby must have same major release (e.g., 19.3.0.0)
DB_UNIQUE_NAME Must Differ
Primary: DB_NAME=PROD, DB_UNIQUE_NAME=PROD
Standby: DB_NAME=PROD, DB_UNIQUE_NAME=STBY
Standby Redo Logs (SRL) Required
At least (max online redo log groups + 1) per thread. Same or larger size as online redo logs.
Static Listener on Standby
Standby listener.ora must have static entry — DB not running during RMAN duplicate
tnsnames.ora on Both Sides
TNS entries for both PROD (primary) and STBY (standby) on both servers

Configure Primary Database

Primary — SPFILE Parameters & SRL
-- Step 1: Enable ARCHIVELOG mode (if not already)
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE ARCHIVELOG;
ALTER DATABASE OPEN;

-- Step 2: Enable FORCE LOGGING
ALTER DATABASE FORCE LOGGING;

-- Step 3: Set mandatory parameters via SPFILE
ALTER SYSTEM SET db_unique_name='PROD'         SCOPE=SPFILE;
ALTER SYSTEM SET log_archive_config=
  'DG_CONFIG=(PROD,STBY)'                      SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_1=
  'LOCATION=USE_DB_RECOVERY_FILE_DEST
   VALID_FOR=(ALL_LOGFILES,ALL_ROLES)'         SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_2=
  'SERVICE=STBY ASYNC
   VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE)
   DB_UNIQUE_NAME=STBY'                        SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_state_1='ENABLE' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_state_2='ENABLE' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_format='%t_%s_%r.arc' SCOPE=SPFILE;
ALTER SYSTEM SET fal_server='STBY'              SCOPE=BOTH;
ALTER SYSTEM SET fal_client='PROD'              SCOPE=BOTH;
ALTER SYSTEM SET standby_file_management='AUTO' SCOPE=BOTH;
ALTER SYSTEM SET db_file_name_convert=
  '/u02/oradata/STBY/','/u02/oradata/PROD/'    SCOPE=SPFILE;
ALTER SYSTEM SET log_file_name_convert=
  '/u02/oradata/STBY/','/u02/oradata/PROD/'    SCOPE=SPFILE;

-- Step 4: Add Standby Redo Logs on PRIMARY
-- (Needed for primary to become standby after switchover)
-- Count online redo log groups first:
SELECT group#, bytes/1024/1024 mb FROM v$log;
-- Add (groups + 1) SRL groups, same size
ALTER DATABASE ADD STANDBY LOGFILE GROUP 4
  ('/u02/oradata/PROD/srl01.log') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE GROUP 5
  ('/u02/oradata/PROD/srl02.log') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE GROUP 6
  ('/u02/oradata/PROD/srl03.log') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE GROUP 7
  ('/u02/oradata/PROD/srl04.log') SIZE 200M;

RMAN DUPLICATE to Create Standby

Run this from the primary server (or from a third host that can reach both). RMAN connects to both primary (TARGET) and standby (AUXILIARY) simultaneously.

RMAN DUPLICATE FOR STANDBY
-- Method 1: Active duplicate (over network — no backup needed)
$ rman TARGET sys/pass@PROD AUXILIARY sys/pass@STBY

RMAN> DUPLICATE TARGET DATABASE
        FOR STANDBY
        FROM ACTIVE DATABASE
        DORECOVER
        SPFILE
          SET db_unique_name='STBY'
          SET fal_server='PROD'
          SET fal_client='STBY'
          SET log_archive_dest_2='SERVICE=PROD ASYNC
               VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE)
               DB_UNIQUE_NAME=PROD'
        NOFILENAMECHECK;

-- Method 2: From backup (if backup exists on standby)
RMAN> DUPLICATE TARGET DATABASE
        FOR STANDBY
        DORECOVER
        SPFILE
          SET db_unique_name='STBY'
          SET db_file_name_convert=
            '/u02/oradata/PROD/','/u02/oradata/STBY/'
          SET log_file_name_convert=
            '/u02/oradata/PROD/','/u02/oradata/STBY/';

-- RMAN will copy all datafiles, redo logs, and
-- automatically mount the standby database when done

Role Transitions

Switchover & Failover

Two ways to change the primary role — planned (switchover) and emergency (failover). Know both inside out.

Switchover — Planned, Zero Data Loss

A switchover is a controlled role reversal — the primary becomes a standby and the standby becomes the new primary. No data loss. The original primary can be switched back later.

1
Verify switchover readiness
Check switchover_status on primary
2
Initiate switchover on primary
ALTER DATABASE COMMIT TO SWITCHOVER TO STANDBY
3
Mount new standby (old primary)
Old primary now in standby role
4
Complete switchover on new primary
ALTER DATABASE COMMIT TO SWITCHOVER TO PRIMARY
5
Start MRP on new standby
Old primary now receiving redo from new primary
Switchover via SQL
====== ON PRIMARY (PROD) ======

-- Verify readiness
SELECT switchover_status FROM v$database;
-- Must show: TO STANDBY or SESSIONS ACTIVE

-- If SESSIONS ACTIVE disconnect users first, then:
ALTER DATABASE COMMIT TO SWITCHOVER TO STANDBY
  WITH SESSION SHUTDOWN;

-- OR if TO STANDBY (no active sessions):
ALTER DATABASE COMMIT TO SWITCHOVER TO STANDBY;

-- Shut and mount old primary as standby
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;

====== ON NEW PRIMARY (STBY) ======

-- Check readiness on standby
SELECT switchover_status FROM v$database;
-- Must show: TO PRIMARY or SESSIONS ACTIVE

ALTER DATABASE COMMIT TO SWITCHOVER TO PRIMARY
  WITH SESSION SHUTDOWN;
ALTER DATABASE OPEN;

====== ON OLD PRIMARY (now standby) ======
ALTER DATABASE
  RECOVER MANAGED STANDBY DATABASE
  DISCONNECT FROM SESSION;

Switchover using DGMGRL (Recommended)

DGMGRL automates all steps — far simpler and less error-prone than manual SQL. Requires Data Guard Broker to be configured.

DGMGRL Switchover
-- Connect to broker
$ dgmgrl sys/password@PROD

-- Check configuration health
DGMGRL> SHOW CONFIGURATION;
DGMGRL> SHOW DATABASE 'PROD';
DGMGRL> SHOW DATABASE 'STBY';

-- Validate switchover
DGMGRL> VALIDATE DATABASE 'STBY';

-- Execute switchover (single command!)
DGMGRL> SWITCHOVER TO 'STBY';

-- Verify new configuration
DGMGRL> SHOW CONFIGURATION;

-- Expected output after switchover:
-- Configuration - PROD_DG
--   Protection Mode: MaxAvailability
--   Members:
--   STBY - Primary database
--   PROD - Physical standby database
-- Fast-Start Failover: Disabled
-- Configuration Status: SUCCESS

Graceful Failover

Used when primary is still accessible but must be decommissioned urgently. Allows final log flush before switching — zero data loss possible.
1
Flush final redo from primary
ALTER SYSTEM FLUSH REDO TO standby
2
Verify standby fully applied
Check V$DATAGUARD_STATS apply lag = 0
3
Cancel MRP on standby
Stop apply before activating
4
Activate standby as new primary
ACTIVATE STANDBY DATABASE
5
Open new primary
RESETLOGS if required
Graceful Failover — SQL
====== ON PRIMARY (if still accessible) ======
-- Flush remaining redo to standby
ALTER SYSTEM FLUSH REDO TO 'STBY';

====== ON STANDBY ======
-- Verify apply lag is 0
SELECT name, value FROM v$dataguard_stats
WHERE  name = 'apply lag';

-- Cancel MRP
ALTER DATABASE
  RECOVER MANAGED STANDBY DATABASE CANCEL;

-- Apply remaining logs
ALTER DATABASE
  RECOVER STANDBY DATABASE;

-- Activate standby as primary
ALTER DATABASE ACTIVATE STANDBY DATABASE;

-- Open new primary
ALTER DATABASE OPEN;

-- If RESETLOGS needed:
ALTER DATABASE OPEN RESETLOGS;

Immediate Failover (Emergency)

Primary is completely unavailable. Cannot flush redo — some data loss expected if not in Max Protection/Availability mode. Activate immediately.
After failover: The old primary database MUST be reinstated or dropped from the DG configuration before it can be used again. Never try to open old primary as primary.
Immediate Failover
====== ON STANDBY ONLY ======

-- Cancel MRP
ALTER DATABASE
  RECOVER MANAGED STANDBY DATABASE CANCEL;

-- Finish applying received logs
ALTER DATABASE
  RECOVER STANDBY DATABASE;

-- Activate as primary
ALTER DATABASE ACTIVATE STANDBY DATABASE;

-- Open new primary
ALTER DATABASE OPEN;

-- Via DGMGRL (recommended):
DGMGRL> FAILOVER TO 'STBY';

-- Or immediate failover:
DGMGRL> FAILOVER TO 'STBY' IMMEDIATE;

-- Old primary CANNOT be reused without
-- reinstating it via RMAN or DGMGRL

Reinstate Old Primary After Failover

After failover, the old primary is orphaned. You can reinstate it as a new standby using Flashback Database (fastest) or by re-creating it with RMAN DUPLICATE. DGMGRL REINSTATE makes this a single command.

Reinstate Old Primary
-- Method 1: DGMGRL REINSTATE (requires Flashback DB)
-- On old primary — start in MOUNT state
STARTUP MOUNT;

-- From DGMGRL on new primary
$ dgmgrl sys/pass@STBY   -- connect to new primary
DGMGRL> REINSTATE DATABASE 'PROD';

-- DGMGRL will automatically:
-- 1. Flashback old primary to failover SCN
-- 2. Mount it as physical standby
-- 3. Start redo apply

-- Method 2: Manual Flashback (if Flashback DB enabled)
-- On old primary:
STARTUP MOUNT;
FLASHBACK DATABASE TO SCN <failover_scn>;
ALTER DATABASE CONVERT TO PHYSICAL STANDBY;
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE
  RECOVER MANAGED STANDBY DATABASE
  DISCONNECT;

-- Method 3: RMAN DUPLICATE (if Flashback not available)
-- Re-create old primary as standby using RMAN duplicate
-- (same as initial creation steps)
Management Interface

Data Guard Broker (DGMGRL)

The broker automates and centralizes all Data Guard management — configuration, monitoring, role transitions, and health checks — from a single command-line interface.

Broker Configuration Setup

Enable & Configure Broker
-- Step 1: Enable broker on BOTH primary and standby
ALTER SYSTEM SET dg_broker_start=TRUE SCOPE=BOTH;

-- Step 2: Set broker config file locations (optional)
ALTER SYSTEM SET
  dg_broker_config_file1=
    '/u01/app/oracle/product/19c/db/dbs/dr1PROD.dat'
  SCOPE=BOTH;
ALTER SYSTEM SET
  dg_broker_config_file2=
    '/u02/oradata/PROD/dr2PROD.dat'
  SCOPE=BOTH;

-- Step 3: Connect to DGMGRL from primary
$ dgmgrl sys/password@PROD

-- Step 4: Create configuration
DGMGRL> CREATE CONFIGURATION 'PROD_DG'
          AS PRIMARY DATABASE IS 'PROD'
          CONNECT IDENTIFIER IS PROD;

-- Step 5: Add standby to configuration
DGMGRL> ADD DATABASE 'STBY'
          AS CONNECT IDENTIFIER IS STBY
          MAINTAINED AS PHYSICAL;

-- Step 6: Enable configuration
DGMGRL> ENABLE CONFIGURATION;

-- Verify
DGMGRL> SHOW CONFIGURATION;

Automated HA

Fast-Start Failover (FSFO)

FSFO enables automatic failover without DBA intervention. An Observer process continuously monitors the primary and triggers failover if it becomes unreachable.

How FSFO Works

1
Observer installed on 3rd host
Separate from both primary and standby servers. Connected to both via Oracle Net.
2
Observer pings primary every few seconds
Default threshold: 30 seconds of unresponsiveness before FSFO triggers.
3
Observer verifies standby is synchronized
Only triggers failover if standby is healthy and has applied all available redo.
4
Automatic failover executes
Standby becomes new primary. Applications reconnect via FCF (Fast Connection Failover) or TAF.
Requirements for FSFO
  • • Broker must be enabled and configured
  • • Protection mode: Max Availability or Max Performance
  • • Observer running on 3rd server
  • • Flashback Database recommended (for reinstatement)

FSFO Configuration

DGMGRL — FSFO Setup
-- Set protection mode to MaxAvailability
DGMGRL> EDIT CONFIGURATION SET PROTECTION MODE
          AS MaxAvailability;

-- Configure transport mode for standby
DGMGRL> EDIT DATABASE 'STBY'
          SET PROPERTY LogXptMode='SYNC';

-- Set FSFO threshold (seconds)
DGMGRL> EDIT CONFIGURATION
          SET PROPERTY
          FastStartFailoverThreshold=30;

-- Enable FSFO
DGMGRL> ENABLE FAST_START FAILOVER;

-- Start Observer (on 3rd server)
$ dgmgrl sys/password@PROD

DGMGRL> START OBSERVER;
-- Observer process stays running in foreground
-- or use: START OBSERVER FILE='observer.dat'

-- Check Observer and FSFO status
DGMGRL> SHOW FAST_START FAILOVER;
DGMGRL> SHOW OBSERVERS;

-- Disable FSFO
DGMGRL> DISABLE FAST_START FAILOVER;

Active Data Guard (ADG)

Separately Licensed

Active Data Guard allows the physical standby to remain open in READ ONLY mode while simultaneously applying redo. This means you can run reporting queries, backups, and ad-hoc analysis on the standby without impacting the primary — reducing primary workload and maximizing hardware ROI.

Reporting Queries
Run BI/analytics on standby — offload primary
RMAN Backups
Take backups from standby — zero primary impact
Real-Time Query
See near-real-time data (seconds lag)
Enable Active Data Guard

Interview Q&A

Data Guard — Interview Questions

Critical Data Guard questions asked in Oracle DBA interviews covering protection modes, switchover vs failover, and Active Data Guard.

Physical Standby maintains an exact, block-for-block copy of the primary database. It applies redo changes using Media Recovery (MRP process). It can be opened read-only with Active Data Guard, but is otherwise in managed recovery mode. Supports all data types, indexes, and structures automatically.

Logical Standby applies SQL (reconstructed from LogMiner) instead of redo blocks. The standby schema is open read-write and can have additional indexes, materialized views, or even different storage. Supports only Oracle-supported SQL types (some object types, LOBs, and certain DDLs are not supported). Primarily used for reporting while primary handles OLTP. Much more complex to manage and has more restrictions.

Bottom line: Physical Standby is preferred for DR and read-only offloading (via Active Data Guard). Logical Standby is used for open standby with DDL transformations — a niche use case.

  • Maximum Performance (default): Redo is shipped asynchronously (ASYNC). Primary never waits for standby acknowledgment. Zero performance impact; RPO is small but non-zero (lag = time to last shipped redo).
  • Maximum Availability: Redo is shipped synchronously (SYNC with AFFIRM). The primary waits for standby to confirm it has written the redo to disk. If the standby becomes unreachable, the primary automatically degrades to Maximum Performance mode — no production outage. This is the recommended mode for most enterprises.
  • Maximum Protection: Like Maximum Availability but the primary shuts down rather than degrading if the standby is unreachable. Guarantees zero data loss. Requires at least two standbys for practicality; rarely used due to availability risk on primary.

Switchover is a planned role reversal — both the primary and standby are available. The primary gracefully transfers its role to the standby with no data loss. The old primary becomes the new standby. Used for planned maintenance, Oracle upgrades, or datacenter migrations. Reversible at any time.

Failover is an emergency role change when the primary is unavailable (crash, datacenter failure). The standby is activated as the new primary. Data loss is possible (depending on protection mode and redo lag at the time of failure). The old primary cannot automatically rejoin as standby — it must be reinstated using DGMGRL's REINSTATE DATABASE command or rebuilt using RMAN Duplicate from the new primary.

Active Data Guard (ADG) allows a Physical Standby database to be open in READ ONLY mode while MRP continues to apply redo. This means the standby is always current and fully synchronized, yet still serves read-only queries simultaneously — offloading reporting and analytics from the primary.

ADG is a licensed option in Oracle Enterprise Edition — it is not included in the base EE license. Without ADG, opening the standby read-only stops the MRP process. ADG features also include Far Sync (redo forwarding relay), Automatic Block Repair (standby fixes primary block corruptions), and Global Temporary Table DML on standby.

Monitor lag using V$DATAGUARD_STATS on the standby (shows transport lag and apply lag) or via DGMGRL: SHOW DATABASE VERBOSE <standby_name>.

Common causes of apply lag: (1) Network bandwidth saturation — primary is generating more redo than the network can ship; (2) I/O bottleneck on standby — standby's storage is too slow to write redo fast enough; (3) Too few MRP workers — increase with RECOVER MANAGED STANDBY DATABASE USING CURRENT LOGFILE PARALLEL 8; (4) Standby under-resourced — standby should have comparable hardware to primary for zero-lag performance.
