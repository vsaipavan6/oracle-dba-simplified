RMAN Level 0 vs Level 1
Backup Explained

What's the real difference? Differential vs cumulative, block change tracking, and which strategy is right for your database size. No Oracle manual required.

10 min read June 2025 Oracle DBA Simplified Oracle 19c

Picture this: Your 500GB production database crashes at 9 AM Monday. Your last backup was Sunday night. You have two paths: restore the full 500GB from scratch and wait 4 hours, or restore a 15GB incremental file from this morning and be done in 30 minutes. That's the whole point of RMAN incremental backups. Let's understand exactly how Level 0 and Level 1 work.

1
The Problem

Why Full Backups Alone Are Wasteful

A full backup — what RMAN calls a "whole database backup" — copies every single block in your database, whether it changed recently or not. For a 1TB database that changes 5% per day, you're copying the same 950GB of unchanged data every night. That's:

950GB
wasted I/O per night
3-4 hrs
backup window needed
7TB/week
storage consumed

The smarter approach: take one complete baseline, then only backup what changed since that baseline. This is Oracle's incremental backup strategy, and it's built around two levels.

2
The Foundation

Level 0 — The Starting Point

This is where most people get confused. A Level 0 backup is NOT just a regular full backup with a different name. It's specifically designed to be the parent for incremental backups.

📖
The Book Analogy

Imagine your database is a book that gets new chapters added every day. A Level 0 is making a complete photocopy of the entire book — including all chapters written so far. This is your reference copy. Every day after that, you only photocopy the new pages added today. That's your Level 1.

What does Level 0 actually copy?

  • Every data block that has ever been used (not every allocated block, just used ones)
  • Backup is stored in RMAN's proprietary format (compressed if specified)
  • Sets the baseline SCN for all subsequent Level 1 backups
  • Without a Level 0, you cannot take a Level 1 — RMAN will fall back to a Level 0 automatically if none exists
RMAN — Level 0 Backup 
-- Take a Level 0 (the base for all incrementals)
RMAN> BACKUP INCREMENTAL LEVEL 0 DATABASE
        PLUS ARCHIVELOG DELETE INPUT
        FORMAT '/rman/backup/%d_L0_%T_%s_%p.bkp'
        TAG 'WEEKLY_L0';

-- Verify what was backed up
RMAN> LIST BACKUP OF DATABASE SUMMARY;
-- Look for: Incremental Level = 0

Copies all blocks changed since the last Level 0 — regardless of any Level 1s taken in between. Each day's backup builds on the Level 0 and includes everything since then.

The "New Chapters" Analogy

Monday: book has 1 new chapter → differential copies 1 chapter, cumulative copies 1 chapter. 4
The Comparison

Differential vs Cumulative — Head to Head

What You're Comparing Level 1 Differential Level 1 Cumulative
What it copies Changed since last backup (any level) Changed since last Level 0 (baseline)
Daily backup size ✓ Smallest (only that day's changes) ✗ Grows through the week
Backup storage needed ✓ Less total storage ✗ More total storage
Backup window per day ✓ Fastest backup (less to write) ✗ Grows each day
Files to apply on recovery ✗ L0 + every L1 since L0 (can be 6+ files) ✓ Always just L0 + latest L1C (2 files)
Recovery time ✗ Slower (apply each incremental in sequence) ✓ Faster (only 2 backups to apply)
Best for Small daily changes, large backup windows, storage is expensive Strict RTO requirements, large databases, fast recovery is critical

"Differential saves storage. Cumulative saves time when restoring. The bigger your RTO requirement, the more you should lean towards cumulative."

5
The Speedup

Block Change Tracking — The Hidden Multiplier

Here's something that almost no beginner article covers: even with Level 1 incremental backups, RMAN still reads every single block in your database to figure out which ones changed since the last backup. For a 1TB database, that's 1TB of reads just to find the 15GB that changed.

⚠️
The Hidden Performance Problem

Without Block Change Tracking, a Level 1 backup on a 500GB database still reads all 500GB from disk. The backup file is small, but the I/O impact is the same as a full backup. On busy production systems during business hours, this full-read I/O can cause performance problems.

Block Change Tracking (BCT) solves this by maintaining a small bitmap file that records which blocks changed since the last backup. RMAN checks this file first, skips unchanged blocks, and only reads the changed ones.

❌ Without BCT

RMAN reads entire 1TB database to find which blocks changed. Level 1 backup window = nearly same as full backup.

✅ With BCT

RMAN checks the BCT bitmap, reads only the 50GB that changed. Level 1 backup window = 70-90% faster.

SQL — Enable Block Change Tracking 
-- Enable BCT (do this once — it's persistent)
ALTER DATABASE ENABLE BLOCK CHANGE TRACKING
  USING FILE '/u03/rman/bct/bct.dbf' REUSE;

-- Verify it's active
SELECT status, filename,
       ROUND(bytes/1024/1024,1) mb
FROM   v$block_change_tracking;
-- STATUS should be 'ENABLED'

-- Check BCT effectiveness on recent backups
SELECT file#,
       ROUND(datafile_blocks * 8192 / 1024 / 1024) total_mb,
       ROUND(blocks_read * 8192 / 1024 / 1024) read_mb,
       ROUND(100 - (blocks_read / datafile_blocks * 100), 1) pct_saved
FROM   v$backup_datafile
WHERE  used_change_tracking = 'YES'
AND    incremental_level = 1
ORDER BY file#;
✅
Enable BCT immediately on any database over 100GB

The BCT file is tiny (roughly 1MB per 10GB of database data) and the performance gain for Level 1 backups is massive. There is almost no reason not to enable it.

6
Real World

Recovery Scenario — "It Crashed on Thursday"

Let's make this concrete. Your 200GB database crashed Thursday afternoon. Your backup strategy is: Level 0 every Sunday, Level 1 Monday–Saturday. Here's what recovery looks like:

With Differential Strategy

  1. Restore Level 0 (Sunday backup). Copy 200GB from backup media → datafiles. ~45 minutes.
  2. Apply Level 1 Differential — Monday. Apply ~8GB incremental. ~12 minutes.
  3. Apply Level 1 Differential — Tuesday. Apply ~6GB incremental. ~9 minutes.
  4. Apply Level 1 Differential — Wednesday. Apply ~10GB incremental. ~14 minutes.
  5. Apply archive logs to bring to exact crash point. ~20 minutes.

Total recovery time: ~1 hour 40 minutes — and that includes applying 3 incremental backups in sequence.

With Cumulative Strategy

  1. Restore Level 0 (Sunday backup). Same ~45 minutes.
  2. Apply Level 1 Cumulative — Wednesday. This one file contains ALL changes since Sunday. Apply ~24GB. ~25 minutes.
  3. Apply archive logs to bring to exact crash point. ~20 minutes.

Total recovery time: ~1 hour 30 minutes — fewer files to apply means less recovery work. The gap grows larger as the week progresses.

8
Strategy Guide

Which Strategy Should You Choose?

DB Size < 50GB
Just take a full backup nightly

For small databases, incremental complexity isn't worth it. A full backup every night is simple, reliable, and fast enough. Use RMAN compression to keep storage manageable.

DB Size 50GB – 500GB
Level 0 weekly + Level 1 Differential daily

The classic strategy. Small daily backups, manageable storage. Enable BCT. Recovery might take slightly longer as the week goes on, but acceptable for most businesses.

DB Size > 500GB, strict RTO
Level 0 weekly + Level 1 Cumulative daily

When recovery time is the priority. You always know exactly what to apply (L0 + latest cumulative). Slightly more storage but much more predictable recovery window.

Very Large DB (multi-TB) + SSD storage
Incremental Forever + Image Copy strategy

Advanced technique: take one L0 image copy, then apply L1 differential to the copy daily using RECOVER COPY. The copy is always current. Near-instant recovery: just switch to the copy. No traditional "restore" needed.

Quick Reference

The Backup Cheat Sheet

Backup Levels
Level 0
All used blocks. The base. Must exist before any Level 1. Taken weekly.
Level 1 Differential
Changed since last backup (any level). Smallest daily. Longer recovery chain.
Level 1 Cumulative
Changed since last Level 0. Grows through week. Always 2 files for recovery.
Storage vs Recovery Tradeoff
Differential
Saves storage. Uses shorter backup window. Longer recovery (many files to apply).
Cumulative
Uses more storage. Longer backup window. Faster recovery (always 2 files to apply).
Key Parameters & Views
BCT file
ALTER DATABASE ENABLE BLOCK CHANGE TRACKING. Makes Level 1 reads 70-90% faster.
V$BACKUP_DATAFILE
Shows BCT effectiveness per backup: blocks_read vs datafile_blocks, pct_saved.
V$BLOCK_CHANGE_TRACKING
Shows BCT status: ENABLED/DISABLED and filename.
LIST BACKUP SUMMARY
RMAN command to see all backups, their levels, sizes, and completion times.
