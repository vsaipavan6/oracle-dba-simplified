What Is It?

Amazon RDS for Oracle — The Big Picture

RDS is AWS's managed relational database service. For Oracle, it means AWS provisions the server, installs Oracle, handles OS patching, automates backups, and monitors hardware — while you run your database workloads normally.

AWS Manages

You don't touch any of this

Hardware provisioning and replacement
OS installation, patching, and maintenance
Oracle software installation and upgrades
Automated backups and point-in-time restore
Multi-AZ failover (automatic, under 120s)
Storage scaling and IOPS management
Monitoring, metrics, and alerting via CloudWatch

You Manage

Your responsibilities on RDS

Database schema, users, and grants
Oracle parameters (via parameter groups)
Option groups (features: TDE, SSL, OEM, etc.)
VPC, subnets, and security groups
Application-level queries, indexes, and tuning
Maintenance window scheduling
Snapshot lifecycle and retention policies

How RDS Oracle Fits Inside AWS — Architecture Overview

Your app connects to a single DNS endpoint. AWS handles everything beneath it — replication, failover, backups, and monitoring.

Comparison

RDS Oracle vs On-Premises Oracle

Before moving to RDS, understand exactly what changes. Many DBA superpowers are removed — but AWS replaces them with managed alternatives.

What You CAN Still Do

Connect via SQL*Plus, SQL Developer, JDBC

Standard Oracle client connections work exactly the same way.

Create users, roles, and grant privileges

Full DDL access as the master user (which has DBA role).

Run AWR, ASH, ADDM reports

Diagnostics Pack features available with EE + diagnostics license.

Use most Oracle database features

Partitioning, Advanced Compression, Spatial, Text, XML DB, etc.

Take manual snapshots anytime

Unlike automated backups, manual snapshots persist until you delete them.

Import data via Data Pump (expdp/impdp)

Using Amazon S3 integration or database links to transfer dump files.

What You CANNOT Do

Connect as SYSDBA or SYS

AWS locks the SYS/SYSTEM accounts. You use the master user (admin) which has DBA privileges but NOT SYSDBA.

OS-level access (no SSH to the server)

You never touch the underlying EC2 instance. No cron jobs, no alert log via OS, no OS files.

Run STARTUP / SHUTDOWN database commands

AWS manages instance lifecycle. Use the RDS Console/CLI to stop/start the DB instance.

Use RMAN directly (standard RDS)

AWS uses its own backup mechanism. RMAN is available in RDS Custom or for migration purposes via S3.

Create or manage listener / tnsnames.ora

AWS manages the listener. The endpoint is the connection string. No lsnrctl access.

Access certain V$ views (some blocked)

V$LOGFILE, V$CONTROLFILE, V$DATAFILE return AWS-managed paths. Some SYS-only views unavailable.

Sizing Rule

Start with db.r6i. Oracle SGA must fit in RAM with room to spare. For a 50 GB SGA → pick r6i.2xlarge (64 GB). Leave 25% RAM beyond SGA_TARGET for OS overhead and PGA.

Oracle Licensing Math

With BYOL, Oracle charges 0.5 processor license per vCPU. A r6i.4xlarge (16 vCPU) needs 8 Oracle processor licenses. Use db.z1d to minimize vCPUs at highest clock speed.

Scaling

Scale via Console or CLI (modify-db-instance). Applies at maintenance window or immediately with ~60s restart. Storage can only grow, never shrink — enable autoscaling as a safety net.

General Purpose SSD (gp3) Recommended
  • Baseline 3,000 IOPS and 125 MB/s throughput — included
  • Configurable up to 16,000 IOPS and 1,000 MB/s independently
  • 20 GB to 64 TB storage range
  • 20% cheaper than gp2 at same IOPS
  • Use for most OLTP workloads
Provisioned IOPS SSD (io2 Block Express) High I/O
  • Up to 256,000 IOPS per DB instance
  • Up to 4,000 MB/s throughput

VPC Placement

Always deploy in a private subnet. Use a DB subnet group spanning at least 2 AZs. The RDS instance gets a private IP — never expose it publicly unless absolutely required (and even then, use security groups tightly).

Security Groups

The RDS security group should only allow inbound TCP port 1521 from your application server's security group — not from 0.0.0.0/0. Treat the DB security group as a VPC-level firewall.

Public Accessibility

Set publicly-accessible=false for production. If you need external access for migration or tooling, use a bastion host or AWS Systems Manager Session Manager instead.

Parameter groups replace the traditional init.ora / spfile. They are applied to one or more DB instances. Changes to static parameters require a reboot.

Parameter group management
# Create a custom parameter group for Oracle 19c EE
aws rds create-db-parameter-group \
  --db-parameter-group-name   oracle19c-prod-params \
  --db-parameter-group-family oracle-ee-19 \
  --description               "Oracle 19c EE production params"

# Modify a parameter (dynamic — no reboot needed)
aws rds modify-db-parameter-group \
  --db-parameter-group-name oracle19c-prod-params \
  --parameters "ParameterName=open_cursors,ParameterValue=1000,ApplyMethod=immediate" \
               "ParameterName=sessions,ParameterValue=500,ApplyMethod=pending-reboot"

# View all modifiable parameters
aws rds describe-db-parameters \
  --db-parameter-group-name oracle19c-prod-params \
  --query "Parameters[?IsModifiable==\`true\`].[ParameterName,ParameterValue]" \
  --output table

-- From within the DB: check current parameter values
SELECT name, value, description
FROM   v$parameter
WHERE  name IN ('sga_target','pga_aggregate_target',
                'open_cursors','sessions','processes');

-- Important: SGA_TARGET in RDS is set to ~75% of instance RAM
-- db.r6i.2xlarge = 64GB RAM → SGA ~ 48GB

Commonly Modified Parameters

  • open_cursors — default 300, increase for busy OLTP
  • sessions — max concurrent sessions
  • processes — max OS processes (sessions * 1.1 + 5)
  • sga_target — total SGA size
  • pga_aggregate_target — total PGA budget
  • archive_lag_target — force redo flush interval (seconds)
  • db_files — max datafiles (default 200)
  • undo_retention — undo retention in seconds

Parameters You Cannot Change on RDS

  • enable_pluggable_database — no CDB/PDB on standard RDS
  • db_recovery_file_dest — AWS manages FRA location
  • audit_trail — some audit settings AWS-managed
  • log_archive_dest_* — archive destinations AWS-managed
  • db_create_file_dest — datafile locations AWS-managed
  • cluster_database — no RAC on standard RDS

Option groups are Oracle-specific — they enable additional Oracle features beyond the base database. Think of them as AWS's way of managing Oracle options/packs.

Available Oracle Options

SSLOracle SSL/TLS

Encrypts data in transit. Requires configuring the client wallet and sqlnet.ora on the client side.

TDETransparent Data Encryption

Encrypts tablespaces/columns at rest using Oracle Wallet. Alternative to AWS KMS encryption (they're different layers).

OEMOracle Enterprise Manager

Enables EM Database Express (not full Cloud Control) for GUI-based monitoring on port 5500.

S3Amazon S3 Integration

Enables direct read/write of S3 objects from Oracle (UTL_FILE to/from S3). Critical for Data Pump imports/exports.

NNENative Network Encryption

Oracle's proprietary network encryption (no PKI required). Simpler than SSL for in-VPC traffic encryption.

Managing Option Groups

# Create option group
aws rds create-option-group \
  --option-group-name   oracle-options \
  --engine-name         oracle-ee \
  --major-engine-version 19 \
  --option-group-description "EE options"

# Add S3 integration option
aws rds add-option-to-option-group \

# Apply option group to instance
aws rds modify-db-instance \
  --db-instance-identifier prod-oracle \

High Availability & Backups

Always On, Always Safe

AWS replicates your data automatically. You define the rules — AWS does the heavy lifting when things go wrong.

Multi-AZ DB Instance

Classic standby — the safe default
Synchronous replication
Every write confirmed on both primary and standby before returning success
Automatic failover ~60–120 s
CNAME DNS endpoint flips to standby. Your app reconnects to the same endpoint — no config change needed
Standby is NOT readable
It exists only for failover. Add Read Replicas separately for read scaling
99.95% availability SLA
AWS guarantees < 4.4 hours downtime per year with Multi-AZ enabled

Multi-AZ DB Cluster Newer

1 writer + 2 readable standbys across 3 AZs
Faster failover ~35 s
Semi-synchronous replication allows quicker promotion of a standby
2 reader endpoints
Offload reporting queries to the readable standbys via separate reader endpoints
3 separate AZs
Each node in a different availability zone — survives an entire data center failure
Higher cost, fewer instance types
Not all RDS Oracle instance classes support DB Cluster mode — check before adopting

Multi-AZ Failover — What Actually Happens

When the primary fails, AWS handles everything automatically. Your app reconnects to the same endpoint — no config changes needed.

Automated Backups

AWS takes a daily storage snapshot plus continuous transaction logs every 5 minutes.

  • Retention: 1–35 days (default 7)
  • Stored in S3 — you don't see or manage them
  • Taken during backup window (set it during low traffic)
  • Multi-AZ backups from standby (no I/O impact on primary)

Point-in-Time Recovery (PITR)

Restore to any second within your retention window. Drop a table at 2:47:33 PM? Restore to 2:47:32 PM.

  • Creates a brand-new DB instance
  • Original instance keeps running untouched
  • Then copy data from restored instance to original
  • Uses latest restorable time (near real-time)

Manual Snapshots

You trigger these. They persist until YOU delete them — even after the instance is gone.

  • Copy snapshots cross-region for DR
  • Share snapshots with other AWS accounts
  • Encrypt snapshots (can copy unencrypted → encrypted)
  • Billed at S3 storage rate per GB

Backup & Restore Commands

# Take a manual snapshot before a major change
aws rds create-db-snapshot \
  --db-instance-identifier prod-oracle \
  --db-snapshot-identifier before-upgrade-2026-05-14

# Restore to a point in time (new instance)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-oracle \
  --target-db-instance-identifier prod-oracle-restored \
  --restore-time                   2026-05-14T14:47:32Z

# Restore from manual snapshot
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier  prod-oracle-from-snap \
  --db-snapshot-identifier before-upgrade-2026-05-14

# Copy snapshot to another region for DR
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier arn:aws:rds:us-east-1:123:snapshot:before-upgrade-2026-05-14 \
  --target-db-snapshot-identifier before-upgrade-dr-copy \
  --kms-key-id                    alias/rds-key \
  --region                        us-west-2

# Modify backup retention (1-35 days)
aws rds modify-db-instance \
  --db-instance-identifier  prod-oracle \
  --backup-retention-period 14 \
  --preferred-backup-window 02:00-03:00 \
  --apply-immediately
Security

Defense in Depth

RDS Oracle has multiple independent security layers. Use all of them — they complement each other.

Encryption at Rest (KMS)

Data on disk, automated backups, snapshots, and replicas are all encrypted using AWS KMS keys.

Important:

Must enable at creation time. Cannot enable on an existing unencrypted instance — you must snapshot, copy encrypted, restore.

TDE (Transparent Data Encryption)

Oracle's own TDE encrypts data files at the tablespace level. Enabled via Option Group (TDE option).

TDE vs KMS encryption:

They work at different layers. KMS encrypts the whole storage volume; TDE encrypts at Oracle data file level. Many compliance frameworks require TDE specifically.

SSL/TLS in Transit

Encrypt the wire between your app and RDS Oracle. Use the RDS CA certificate bundle.

-- Force SSL (SQL*Net parameter)
SQLNET.SSL_VERSION = 1.2
# Connect with wallet
sqlplus user/pass@(DESCRIPTION=
  (ADDRESS=(PROTOCOL=tcps)...))

IAM Database Authentication

Use AWS IAM credentials instead of Oracle passwords. Short-lived auth tokens (15-min expiry).

  • No password stored in DB
  • Centrally revoke via IAM policy
  • Max 200 concurrent IAM-auth connections

VPC Network Isolation

RDS lives inside your VPC subnet group. Control access with Security Groups (port 1521).

  • Disable Public Accessibility in production
  • Use private subnets only
  • VPC peering or PrivateLink for cross-VPC

Kerberos / Active Directory

Integrate RDS Oracle with AWS Managed Microsoft AD for Windows SSO and centralized user management.

  • Users log in with domain credentials
  • No Oracle passwords for AD users
  • Requires NNE option in option group

Enable TDE + NNE via Option Group (SQL)

Migration

Moving Your Database to RDS

Four supported paths — each with trade-offs. Data Pump via S3 is the recommended approach for most migrations.

Data Pump via S3 Recommended

Export on-prem using expdp, upload to S3, import on RDS using rdsadmin_s3_tasks. Works for full DB, schema, or table level.

Database Link

Create a DB link from RDS to on-prem and pull data directly. Good for smaller datasets or ongoing sync during cutover.

AWS DMS

AWS Database Migration Service for continuous replication. Supports homogeneous (Oracle→Oracle) and heterogeneous migrations.

SQL*Loader

For flat-file bulk loads. Generate CSV from source, upload to S3, use rdsadmin to access S3, run sqlldr from app server.

Data Pump via S3 — Complete Walkthrough

This is the recommended path. It's fully managed, reliable, and works even across firewalls because it uses S3.

STEP 1 — Export from On-Premises

-- On-prem: Create export directory
CREATE OR REPLACE DIRECTORY dp_dir
  AS '/exports/oracle';

-- Full schema export (run as DBA)
expdp system/password
  DIRECTORY=dp_dir
  DUMPFILE=myschema_%U.dmp
  LOGFILE=expdp.log
  SCHEMAS=HR,FINANCE
  PARALLEL=4
  COMPRESSION=ALL

-- Or full database export
expdp system/password
  FULL=Y
  DIRECTORY=dp_dir
  DUMPFILE=fulldb_%U.dmp
  PARALLEL=8
  EXCLUDE=STATISTICS

STEP 2 — Upload to S3

# Upload dump files to S3
aws s3 cp /exports/oracle/ \
  s3://my-migration-bucket/oracle-dumps/ \
  --recursive

# Verify upload
aws s3 ls s3://my-migration-bucket/oracle-dumps/

# Ensure RDS instance IAM role
# has s3:GetObject on the bucket
aws rds add-role-to-db-instance \
  --db-instance-identifier prod-oracle \
  --role-arn arn:aws:iam::123:role/rds-s3-role \
  --feature-name S3_INTEGRATION

STEP 3 — Download from S3 to RDS

-- Download dump from S3 to RDS DATA_PUMP_DIR
SELECT rdsadmin.rdsadmin_s3_tasks.download_from_s3(
  p_bucket_name  => 'my-migration-bucket',
  p_s3_prefix    => 'oracle-dumps/',
  p_directory_name => 'DATA_PUMP_DIR'
) AS task_id
FROM DUAL;

-- Check download task status
SELECT text
FROM  TABLE(rdsadmin.rds_file_util.read_text_file(
        'BDUMP','dbtask-1234567890123-456.log'));

-- List files in DATA_PUMP_DIR
SELECT * FROM TABLE(
  rdsadmin.rds_file_util.listdir('DATA_PUMP_DIR'));

STEP 4 — Import into RDS

-- Run impdp (from app server connecting to RDS)
impdp admin/password@rds-endpoint:1521/ORCL
  DIRECTORY=DATA_PUMP_DIR
  DUMPFILE=myschema_%U.dmp
  LOGFILE=impdp.log
  SCHEMAS=HR,FINANCE
  PARALLEL=4
  TABLE_EXISTS_ACTION=REPLACE
  TRANSFORM=SEGMENT_ATTRIBUTES:N

-- If remapping schemas or tablespaces:
impdp admin/password@rds-endpoint:1521/ORCL
  DIRECTORY=DATA_PUMP_DIR
  DUMPFILE=myschema_%U.dmp
  REMAP_SCHEMA=OLD_HR:HR
  REMAP_TABLESPACE=OLD_TBS:USERS
  EXCLUDE=STATISTICS

Database Link Migration (for smaller datasets)

-- On RDS: Create database link pointing to on-prem
CREATE DATABASE LINK onprem_link
  CONNECT TO remote_user IDENTIFIED BY "password"
  USING '(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)
    (HOST=10.0.1.50)(PORT=1521))
    (CONNECT_DATA=(SERVICE_NAME=PROD)))';

-- Copy entire table from on-prem to RDS
CREATE TABLE hr.employees AS
  SELECT * FROM hr.employees@onprem_link;

-- Copy data in batches to avoid undo issues on large tables
BEGIN
  FOR i IN 1..10 LOOP
    INSERT INTO hr.employees
    SELECT * FROM hr.employees@onprem_link
    WHERE  MOD(employee_id,10)+1 = i;
    COMMIT;
  END LOOP;
END;
/

-- Verify row counts match
SELECT 'RDS' src, COUNT(*) cnt FROM hr.employees
UNION ALL
SELECT 'OnPrem', COUNT(*) FROM hr.employees@onprem_link;

    l_inst_num => 1,
    l_bid     => 100,  -- begin snap_id
    l_eid     => 120   -- end snap_id
  ));

-- List available AWR snapshots
SELECT snap_id, begin_interval_time, end_interval_time
FROM   dba_hist_snapshot
ORDER BY snap_id DESC
FETCH FIRST 10 ROWS ONLY;

RDS Custom

When You Need OS Access

RDS Custom is the middle ground between full-managed RDS and running Oracle on EC2 yourself. Use it only when standard RDS cannot support your workload.

Shared Responsibility: EC2 vs RDS Custom vs Standard RDS

Who manages what? Green = you, Blue = AWS, Yellow = shared

Responsibility EC2 + Oracle RDS Custom Standard RDS
Hardware / Virtualization AWS AWS AWS
OS Installation & Patching You Shared AWS
Oracle Software Install You AWS AWS
Oracle DB Patching You Shared AWS
Backups & PITR You AWS AWS
HA / Failover You AWS AWS
SSH / OS Access Full Full None
Custom File System / 3rd-party Agents Yes Yes No

Use RDS Custom When...

Legacy app requires OS-level Oracle features
Oracle Application Express, Oracle Fusion, apps that write directly to the OS filesystem
Custom monitoring or security agents
Requirement to install Qualys, Rapid7, or custom APM agents on the DB host
Custom Oracle patches or one-off fixes
Applying Oracle CPU patches or interim patches not yet available in standard RDS
Custom init.ora parameters blocked by RDS
Parameters that standard RDS locks and won't allow you to change

Stick with Standard RDS When...

Standard web/app workloads on Oracle
No OS dependencies — standard RDS is simpler and cheaper
You want fully automated patching
With RDS Custom, you take partial responsibility for patches
Cost is a primary constraint
RDS Custom uses larger instance types and costs more than standard RDS
Team lacks OS-level DBA skills
RDS Custom expects you to manage the OS — if you can't, use standard RDS

RDS gp3 storage supports autoscaling — but you need to enable it. Here's the immediate response and long-term fix:

# IMMEDIATE: Enable storage auto-scaling (if not already)
aws rds modify-db-instance \
  --db-instance-identifier   prod-oracle \
  --max-allocated-storage    500 \
  --apply-immediately

-- Find what's consuming space (from SQL*Plus)
SELECT owner, segment_type,
       ROUND(SUM(bytes)/1073741824,2) gb
FROM   dba_segments
GROUP BY owner, segment_type
ORDER BY gb DESC FETCH FIRST 15 ROWS ONLY;

-- Check TEMP tablespace usage (large sorts filling space)
SELECT tablespace_name, total_blocks*8192/1073741824 total_gb,
       used_blocks*8192/1073741824 used_gb
FROM   v$sort_segment;

-- Purge recyclebin to reclaim space instantly
PURGE DBA_RECYCLEBIN;

-- Check undo tablespace usage
SELECT tablespace_name, status, SUM(bytes)/1073741824 gb
FROM   dba_undo_extents
GROUP BY tablespace_name, status;

After crisis: investigate whether TEMP or UNDO are oversized, review archivelog accumulation (check automated backups are deleting old logs), and consider adding a data file to the right tablespace.

Check CloudWatch DB Insights first (or Performance Insights if pre-June 2026). Then drill into V$ views:

-- Top SQL by CPU right now
SELECT sql_id, child_number, executions,
       ROUND(cpu_time/1000000,2) cpu_secs,
       ROUND(cpu_time/NULLIF(executions,0)/1000000,4) cpu_per_exec,
       substr(sql_text,1,80) sql_text
FROM   v$sql
ORDER BY cpu_time DESC
FETCH FIRST 10 ROWS ONLY;

-- Active sessions and what they're waiting on
SELECT sid, status, event, sql_id, seconds_in_wait
FROM   v$session
WHERE  status = 'ACTIVE'
ORDER BY seconds_in_wait DESC;

-- Check for missing index (full table scans)
SELECT sql_id, COUNT(*) full_scans
FROM   v$sql_plan
WHERE  operation = 'TABLE ACCESS'
AND    options   = 'FULL'
GROUP BY sql_id
ORDER BY full_scans DESC;

-- If one query is the culprit — kill it
SELECT sid, serial#, username, sql_id
FROM   v$session WHERE sql_id = '&problem_sql_id';
ALTER SYSTEM KILL SESSION 'SID,SERIAL#' IMMEDIATE;

On RDS, Flashback Database is NOT available. But PITR creates a new instance from which you can extract the table using Data Pump.

# Step 1: Create PITR instance — restore to 2:47 PM (before the drop)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-oracle \
  --target-db-instance-identifier prod-oracle-recovery \
  --restore-time                   2026-05-14T14:46:00Z

# Step 2: Wait for instance to become Available (~10-30 min)
aws rds wait db-instance-available \
  --db-instance-identifier prod-oracle-recovery

# Step 3: Export just the dropped table from recovery instance
expdp admin/password@recovery-endpoint:1521/ORCL
  DIRECTORY=DATA_PUMP_DIR
  TABLES=HR.EMPLOYEES
  DUMPFILE=recovered_employees.dmp

# Step 4: Upload dump to S3
aws s3 cp recovered_employees.dmp s3://my-bucket/recovery/

# Step 5: Download to prod RDS DATA_PUMP_DIR and import
-- (Run from SQL*Plus on prod-oracle)
SELECT rdsadmin.rdsadmin_s3_tasks.download_from_s3(
  'my-bucket','recovery/','DATA_PUMP_DIR') FROM DUAL;

impdp admin/password@prod-endpoint:1521/ORCL
  DIRECTORY=DATA_PUMP_DIR
  DUMPFILE=recovered_employees.dmp
  TABLE_EXISTS_ACTION=REPLACE

# Step 6: Delete recovery instance
aws rds delete-db-instance \
  --db-instance-identifier   prod-oracle-recovery \
  --skip-final-snapshot

Pre-migration check (weeks before)
Identify unsupported features (RAC, ASM, Database Vault, Flashback DB). Check tablespace sizes. Identify incompatible init.ora params.
2
Initial full export (during business hours)
Run expdp FULL=Y with TRANSPORTABLE=ALWAYS. 500 GB takes ~2-3 hours. Upload to S3 in parallel.
3
Import to RDS (full restore) before window
Download from S3 to RDS DATA_PUMP_DIR. Run impdp. Fix any errors. Validate row counts.
4
During maintenance window — delta export
Export only rows changed since initial export (use QUERY or SCN-based filter). Import delta to RDS.
5
Switch app connection string
Update JDBC/TNSNAMES to point to RDS endpoint. Test. Enable Multi-AZ on RDS instance.

AWS provides a reboot-with-failover option that promotes the standby as the new primary — safely triggers the full failover path.

# Trigger failover (app keeps running — measure reconnect time)

  --db-instance-identifier prod-oracle \
  --force-failover

# Watch the event log during failover
aws rds describe-events \
  --source-identifier prod-oracle \
  --source-type       db-instance \
  --duration         60

# After failover — confirm new AZ
aws rds describe-db-instances \
  --db-instance-identifier prod-oracle \
  --query "DBInstances[0].AvailabilityZone"

Choose BYOL if:

  • You already own active Oracle EE or SE2 licenses
  • You need Oracle Enterprise Edition (EE) — License Included only offers SE2
  • You have Software Support (annual maintenance) paid
  • Long-term commitment (3+ years)

Choose License Included (LI) if:

  • You don't own Oracle licenses (SE2 is sufficient)
  • You want one AWS bill — no Oracle support contract
  • Dev/test environments (even with EE licenses, LI may be simpler)
  • Short-term or uncertain commitment
Key rule: With BYOL you must have 1 Oracle license per 2 vCPUs (NUP licensing) or per processor. Always get this reviewed by your Oracle License Management rep before migrating — Oracle audits RDS usage too.
